# DE-00000074 기준은 소유자마다 따로 두고 공개 CLI로 그 자리에서 확인해 넘김 글에 싣는다

## Question

사용자가 밝힌 기준을 다른 AI 세션이 현재 버전으로 적용하게 하려면 기록을 어디에 둬야 할까요?
Stage·Distill·Avatar가 서로의 코드와 DB를 쓰지 않는다면 무엇으로 연결해야 할까요?
받는 AI가 옛 기준을 현재로 쓰지 않았고 실제로 읽어 적용했다는 것은 어떻게 확인해야 할까요?

필드, 명령, 오류 코드는 [구현 설계](../../../research/llm-work/implementation-design.md)가 소유합니다. 이 기록에는 선택과 그 이유만 적습니다.

## Options

- **A. Distill의 `knowledge` chunk에 기준 필드를 더합니다.**
  - 기존 recall과 벡터 검색을 그대로 씁니다.
  - 대신 `move()`의 고정 열 목록과 promote의 범위 확대, 저장·추출·crystallize 경로가 모두 새 필드를 다뤄야 합니다.
  - 관계는 AI가 추정한 것입니다.
- **B. Distill 전역 DB에 기준 전용 표를 둡니다.**
  - 범위는 사람이 정한 `project` 키로 정합니다.
  - 개인 기준과 선택은 Avatar가 소유합니다.
  - Stage는 넘기는 순간에 생산자의 공개 CLI를 하위 프로세스로 불러 현재 상태를 확인하고, 그 결과를 넘김 글에 싣습니다.
- **C. Avatar 하나에 모든 기준을 둡니다.**
  - Distill의 저장과 MCP를 다시 만들게 됩니다.
  - Distill만 쓰는 사람은 프로젝트 기준을 쓸 수 없습니다.
- **D. 기준 파일 경로나 snapshot 파일만 넘깁니다.**
  - 앞선 실험 네 번 모두 링크는 열리지 않았습니다.
  - 파일은 만든 뒤에 대체되거나 철회될 수 있습니다.

## Principles applied

- **SSOT**: 프로젝트 기준은 Distill, 개인 기준·선택·돌아보기는 Avatar, 목적·작업·결정·실행 증거는 Stage가 소유합니다. 다른 쪽이 가진 것은 참조와 읽기 전용 투영입니다.
- **MECE**: 원천 상태, 조건 판정, 멱등 결과, 투영 충돌을 각각 경우를 다 나눠 표로 정했습니다.
- **Fail Fast**: 최신 상태를 확인하지 못하면 어떤 이전 기준도 현재로 싣지 않습니다. 조회 실패를 빈 결과로 바꾸지 않습니다.
- **AHA·KISS**: 판정 재사용, 들여오기, 훅 변경은 넣지 않습니다.
- **SoC·Clean Architecture**: 플러그인끼리 import와 DB 접근 없이 공개 CLI 출력으로만 연결합니다.
- **Honesty**: 시점 보장의 범위를 밝힙니다. 도구 입력이 사람을 인증하지 못한다는 것도 밝힙니다. 기존 정적 검사 실패를 면제하지 않고, 외부 저장소의 결과를 noory-ai 드라이버의 검증으로 적지 않습니다.
- **User intent**: 지금 사용자의 명시적 지시가 저장된 기준보다 우선합니다.

## Chosen direction

B를 고릅니다.

2026-10-06: 사용자가 "이 세션에서 직접 구현을 이어가세요"라고 답했습니다. Codex CLI가 사용량 오류로 멈춘 뒤 감독 세션이 남은 구현을 맡았습니다. Claude의 독립 리뷰는 유지했습니다. 이 예외는 직접 구현에 대한 허용이며 제품 커밋·푸시나 미실행 시험의 통과를 뜻하지 않습니다. **User intent·Honesty**를 적용합니다.

2026-10-06: **SSOT·Honesty**에 따라 설계 3절과 7절의 모호한 계약을 명시했습니다. Avatar는 확인 시 N을 보존하고 N+1에 확인 근거를 담습니다. 출력 `scope`의 객체 모양도 적었습니다. 구현 전 검토본의 digest와 변경 이유를 설계에 함께 남겼습니다.

2026-10-05: 작업 소유자 Codex가 Claude의 설계와 수정본을 독립 검토하고 이 방향을 채택했습니다. 구현과 실제 연결 검증을 마친 뒤 공식 기록으로 올릴지 판단합니다.

2026-10-31: 구현 카드 W-00000274~W-00000276 과 실제 연결 검증 카드 W-00000277 을 마쳤습니다. W-00000277 의 세 번째 시험에서 새 수신 세션 여섯 개가 모두 정상 종료했습니다. 사용자가 이 기록을 공식 기록으로 올리기로 정했습니다.

- **저장.** Distill은 기존 전역 DB에 기준 전용 표를 두고, 기존 chunk 경로와 분리합니다. 범위는 경로가 아니라 사람이 정한 `project` 키로 정합니다.
- **시점 보장.** Stage `handoff_packet.py`는 넘기는 순간 `distill criteria current`와 `avatar export`를 부릅니다.
  - packet이 보장하는 것은 그 순간의 `generation`에서 그 기준이 현재였다는 것까지입니다. 계속 최신이라고 주장하지 않습니다.
  - 생산자는 JSON argv 배열로 지정합니다. 첫 원소는 실행 파일의 절대 경로이고, `shell=False`로 실행합니다. 셸 문자열을 나누는 방식은 쓰지 않습니다.
  - 받은 AI는 기준에 기대는 선택 직전마다 packet에 실린 완성된 check argv 배열을 실행합니다.
  - 적용하는 것은 `eligible_current`만입니다. `superseded`, `revoked`, `unconfirmed`, `proposed`, `scope_mismatch`, `unknown`, 실행 실패는 모두 적용하지 않습니다.
- **출처.** 출처는 안정된 `source_ref`, 원문 `quote`와 그 digest, 행위자, 세션 정보를 함께 남깁니다. `stage:` 출처는 Stage가 다시 읽어 바뀌었거나 없어졌는지 표시합니다.
- **확인.** 사람의 확인은 대화에서 나온 원문과 출처를 받는 확인 동작으로 남기고, 어느 호스트에서든 같습니다. 이 동작은 사람을 인증하지 못합니다. 그래서 출처를 남기고, AI 추정(`confirmation: none`)과 사람의 확인을 따로 둡니다. `ai_confidence`는 이 둘과 독립입니다.
- **출처 확인.** `stage:` 출처는 다른 project key이면 `not_checkable`입니다. 절대 경로, `..`, 루트 밖으로 나가는 심볼릭 링크는 `rejected_ref`입니다. H2가 없으면 `missing`, digest가 다르면 `changed`입니다. 결정 출처가 `changed`, `missing`, `rejected_ref`이면 그 기준은 새 확인이 있을 때까지 `unresolved`입니다.
- **같은 요청.** 쓰는 명령은 모두 멱등 키를 받습니다. digest는 동작 이름, 대상 ID와 버전, 검증한 payload 전체를 정규화한 JSON으로 만듭니다. 빼는 것은 전송에만 쓰는 값(키, 저장 위치, 출력 형식, 생산자가 정하는 값)뿐입니다. 조건이 다른 기준은 합치지 않습니다.
- **투영.** Avatar는 바뀌지 않는 버전 digest와 늘어나는 봉투 digest를 나눕니다. 같은 버전의 내용 변경은 거부합니다. 사건이 앞부분을 보존한 채 늘어난 높은 세대는 받습니다. 철회가 사라진 이력은 거부합니다.
- **조건 판정 기록.** `partial`은 고칠 파일 하나로 다시 판정한 결과가 `applies`일 때, `needs_judgment`는 모든 note를 `met`으로 기록했을 때 적용합니다. 조건 항목끼리는 AND, `any` 안에서는 OR로 판정하고 둘을 합치지 않습니다.
- **앞선 결과.** 카드의 증거 줄(파일 sha256, 실행 명령·종료 코드·시각)을 지금 상태와 대조하고, 일치·변경·없음·미재실행을 그대로 적습니다. 인수 검사와 리뷰는 따로 돕니다.
- **충돌.** 기준끼리 충돌하면 지금 지시, 목적, 명시한 `overrides` 순서로 풉니다. 그래도 풀리지 않고 진행에 꼭 필요할 때만 사람에게 묻습니다.

## Reason

**A를 고르지 않은 까닭.** A를 고르면 기존 경로 여섯 곳 이상이 새 필드를 다뤄야 합니다. 하나만 빠져도 이력이 조용히 사라집니다. B는 같은 저장소와 MCP를 다시 쓰면서도 기준을 그 경로들에서 떼어 놓습니다.

**D를 고르지 않은 까닭.** 파일 snapshot은 만든 뒤에 낡을 수 있습니다. 생산자를 그 자리에서 부르고 선택 직전에 check를 부르면 확인 시점이 분명해집니다.

**Avatar를 따로 두는 까닭.** 사람이 확인한 개인 기준과 선택을 돌아보는 일은 AI가 뽑은 지식과 쓰임이 다릅니다.

이 결정을 뒤집는 관측:

- W-00000277에서 받은 AI가 packet과 check가 `superseded`라고 한 v1을 적용하는 경우가 반복됩니다.
- 미리 정한 시험에서 기준이 있는 조건과 없는 조건의 결과가 늘 같습니다. 이때는 넘김 글 방식이 기준 적용을 만들지 못한 것입니다.
- Avatar 기준이 확인 원문이나 선택 기록 없이 Distill chunk와 같은 쓰임으로만 쓰입니다. 이때는 Avatar 기준을 Distill로 합칩니다.
- 같은 프로젝트가 `project` 키 여럿으로 갈립니다. 이때는 범위 설계를 다시 정합니다.

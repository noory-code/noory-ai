# DE-00000011 v4 migration is a user-facing skill; no version strands a v3 user

## Question

How is the v3-to-v4 migration delivered to the real projects that run Stage, and how do we
prevent an intermediate incremental release from breaking a v3 user before the migration
exists?

## Options

- Script-only migration, whole v4 in one big release: simplest, but the migration is not
  discoverable as a lifecycle action and incremental main pushes risk a window where v4 hooks
  exist without a migration path.
- User-facing skill + release-ordering invariant (chosen): migration is a `stage-migrate`
  skill; no shipped version enforces v4 unless it also carries that skill.

## Principles applied

- Postel's Law / Fail Fast: on a v3 project a v4-enforcing build fails closed with a banner
  naming the skill, never silently corrupts.
- SSOT: the skill wraps the one `migrate_stage.py`; no second migration path.
- Honesty / Completion: the migration is a real user deliverable, so it is exposed the way
  users invoke everything else — a skill — not left as an internal script.

## Chosen direction

Amend `stage/docs/SCHEMA_V4.md`: (1) the migration is delivered as a `stage-migrate` skill;
(2) no shipped plugin version enforces schema v4 unless the same version ships that skill and
a completed migration path. C3-C6 ship dormant and v3-compatible; the C7 release activates v4
enforcement and carries the migration skill together.

## Reason

Real projects use Stage, and cards ship to main incrementally. Without the ordering invariant,
a v3 user who pulls a mid-arc version that already enforces v4 would be stranded with no way
to migrate. Delivering the migration as a skill makes it discoverable and invocable like every
other lifecycle action. Requested by Daewook 2026-07-13.

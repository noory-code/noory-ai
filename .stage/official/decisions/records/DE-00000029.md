# DE-00000029 설명 문서를 갱신할 때 무엇을 교체하고 무엇을 남기는가

## Question

DE-00000028은 "낡은 설명 문서를 검사가 찾아내고, 갱신은 명시적 명령으로 한다"까지 정했다.
남은 문제는 갱신 명령이 파일 안에서 어디까지 손대는가다. `.stage/`의 문서 상당수는 플러그인이
준 설명글과 프로젝트가 쌓은 목록이 한 파일에 같이 있다. 통째로 덮으면 프로젝트 데이터가
사라지고, 아무것도 못 덮으면 갱신 자체가 성립하지 않는다.

## Options

- A. 파일마다 "여기부터 여기까지는 프로젝트 것"이라는 표시(주석 마커)를 새로 넣는다.
- B. 표는 무조건 프로젝트 소유로 보고 표 바깥만 교체한다.
- C. 템플릿이 그 표를 어떻게 배포했는지로 판정한다 — 빈 표로 배포했으면 프로젝트가 채우는
  자리, 내용을 채워 배포했으면 플러그인 것.

## Principles applied

- SSOT — 경계를 새로 선언하지 않는다. 템플릿 자체가 이미 답을 갖고 있고, 그것이 유일한
  소유 위치다.
- AHA / KISS — 마커라는 새 장치를 도입하려면 반복되는 필요가 먼저 보여야 한다. 지금은
  기존 파일만으로 판정이 된다.
- MECE — 세 갈래가 대상 파일 전체를 겹치지 않게 덮는다.
- Fail Fast — 판정이 애매한 파일은 덮지 않고 보고한다. 자동화의 편의보다 데이터가 우선이다.

## Chosen direction

C. **템플릿의 표 모양이 경계를 결정한다.** 대상 문서를 세 갈래로 나눈다.

1. **표가 없는 문서** — 각 폴더의 `README.md`, `_template.md`, `state/current.md` 등.
   통째로 현행 템플릿으로 교체한다.
2. **템플릿이 빈 표(제목 줄과 구분선만)를 담은 문서** — 현행 v4 템플릿 기준 12개:
   `work/active.md`, `work/review.md`, `work/planned/index.md`, `decisions/index.md`,
   `proposals/index.md`, `state/questions.md`, `state/assumptions.md`, `state/risks.md`,
   `roadmap/themes/index.md`, `roadmap/milestones/index.md`, `official/decisions/index.md`,
   `official/work/archive/index.md`.
   템플릿을 통째로 가져오되 프로젝트가 쌓은 표의 데이터 줄만 그대로 옮겨 넣는다.
   빈 표가 두 개 이상인 템플릿이 생기면 자동 교체하지 않고 보고만 한다.
3. **템플릿이 내용이 든 표를 담은 문서** — 현행 v4 템플릿 기준 5개: 루트 `index.md`,
   `roadmap/index.md`, `operations/verification.md`, `official/canon/principles.md`,
   `official/canon/vocabulary.md`.
   기본 실행에서 제외한다. 검사는 차이를 보고하고, 사용자가 파일을 콕 집어 지정했을 때만
   통째로 교체한다. 이 경우 프로젝트가 표에 추가한 줄은 사용자가 직접 옮긴다.

`operations/verification.md`가 3번에 속하는 것은 마이그레이션의 기존 처리(`rewrite_verification`,
프로젝트가 추가한 kind 줄을 보존)와 어긋나지 않는다. 마이그레이션은 자기 경로를 유지하고,
갱신 명령은 이 파일을 기본 대상에서 뺀다.

## Reason

A는 반복이 확인되기 전의 장치다. 마커를 넣으려면 모든 템플릿과 이미 배포된 모든 프로젝트
파일을 함께 고쳐야 하고, 그 마커가 또 하나의 갱신 대상이 된다.

B는 사실과 다르다. `roadmap/index.md`의 표는 테마와 마일스톤 인덱스로 가는 링크이고 루트
`index.md`의 표는 라우팅 규칙이다. 둘 다 플러그인이 소유하는 내용이며 프로젝트 데이터가
아니다. "표 = 프로젝트 것"으로 두면 이 파일들은 영원히 낡은 채로 남는다.

C는 새 정보를 요구하지 않는다. 플러그인이 빈 표를 배포했다는 사실 자체가 "여기는 프로젝트가
채운다"는 선언이다. 판정이 파일 하나로 끝나고, 애매한 경우(빈 표 2개 이상)는 덮지 않는 쪽으로
실패한다.

## Follow-up

- W-00000057의 범위에 이 세 갈래를 반영한다.
- 3번 갈래의 파일 목록은 템플릿이 바뀌면 함께 바뀐다. 구현은 목록을 코드에 박지 말고
  템플릿의 표 모양에서 계산한다.

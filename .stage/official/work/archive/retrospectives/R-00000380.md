# R-00000380 Stage 스크립트 테스트 픽스처 비용 줄여 Windows CI 단축

## Decision points

- **바꾸기 전에 쟀다.** strace 로 테스트마다 띄운 프로세스를 세었다. 약 9,500개 가운데 픽스처 몫은 약 1,700개,
  커밋마다 뜨는 `git maintenance run --auto` 가 약 520개였다. 나머지는 테스트 대상인 드라이버 코드의 git
  호출이었다. 그래서 카드가 상정한 수단(픽스처)이 닿는 몫이 작다는 것을 먼저 알았다.
- **가설을 Windows 에서 직접 확인했다.** 임시 진단 워크플로로 git 프로세스 하나(35-46ms, ubuntu 약 1ms),
  `python -c pass`(21ms), Stage 스크립트 기동(171-342ms)을 쟀다. 프로세스 생성 비용이라는 가설은 맞았다.
  다만 그 비용 대부분은 픽스처가 아니라 테스트 대상 코드가 낸다.
- **효과가 노이즈 안이라고 그대로 보고하고 방향을 물었다.** 프로세스를 20% 줄였지만 Windows 샤드 합계는
  main 971/1001초 대 PR 1037/1017초였다. 성공 기준을 고쳐 맞추지 않고, 드라이버 수정(A), Windows 샤드 증설(B),
  미달로 닫기(C)를 메인 세션에 올렸다. 사용자가 B 를 골랐다.
- **샤드 수는 OS 마다 따로 두고, 시험이 OS 마다 보장을 지키게 했다.** Windows 만 6, 나머지는 3 이다.
  `test_ci_workflows.py` 가 매트릭스를 펼쳐 OS 마다 1..총수 번호가 모두 도는지 본다. 총수, 샤드 목록, exclude,
  `--total` 식을 하나씩 일부러 어긋나게 바꿔 시험이 실패하는 것을 확인했다.
- **템플릿 저장소 복사는 하지 않았다.** Windows 에서 `.git` 복사가 init+commit 보다 약 80ms 싸다. 저장소당
  그 정도는 샤드당 몇 초로 노이즈 안이다.

## Context that was missing

- Windows 러너에서 프로세스 하나와 Stage 스크립트 기동이 얼마인지에 대한 수치. 카드를 등록할 때 이것이
  있었다면 성공 기준과 수단을 처음부터 따로 적었을 것이다.
- 워크플로가 `pull_request` 로만 돌아서 main 과 충돌하는 PR 은 실행 자체가 생기지 않는다. 첫 측정을 기다리다
  알았다.
- 결과: PR #92 에서 Windows Scripts suite 의 가장 느린 샤드가 181/212초에서 102초로, stage 워크플로 전체가
  254-286초에서 170초로 줄었다. 드라이버 스냅샷의 git 호출 줄이기와 Windows timeout 버그는 메인 세션이 후속
  카드로 등록한다.

## Rule candidate

- 성능 카드의 성공 기준은 측정한 노이즈 폭을 함께 적는다. 같은 코드의 Windows 샤드가 133-212초로 흔들리는데
  샤드 하나의 최댓값으로 기준을 세우면, 개선이 없어도 통과하거나 개선이 있어도 실패할 수 있다.

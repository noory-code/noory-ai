# R-00000039 Enum gate honors planned-card status enum

## Work

Fixed the PreToolUse enum gate: it validated every work card's `status` against the current-work
enum, denying any new `work/planned/` card in a planned status (triaged/ready/deferred) though the
audit accepts it. Now the gate selects the status set by the card's zone
(`_is_planned_card_path` → `WORK_PLANNED_STATUSES` vs `STATUS_VALUES`), and `enum_validity_blocker`
passes the target's relative path. TDD: red test (planned `triaged` denied) → green. 302 hook +
256 script tests pass. Version 0.31.3 + CHANGELOG.

## Decision points

- **Zone predicate vs new field table**: reused the topology's planned candidate path
  (`resolve_artifact_reference("W-...").candidate_paths[0]`) as the single source for the planned
  prefix, rather than hardcoding `work/planned/` — SSOT with the audit's own zone split.
- **Other enum fields unchanged**: planned cards never carry verification/retrospective/promotion,
  so absent → skipped; one field table still serves both zones (no duplication).

## Principles applied

- **SSOT**: the gate now mirrors the audit's BACKLOG001-vs-WORK005 split instead of contradicting
  it; planned prefix derived from topology, not restated.
- **Fail Fast preserved**: invalid planned status still denies at write time.

## Context that helped

- The audit already had the correct planned/current split (`audit_backlog_items`), giving an exact
  target contract to mirror.
- Existing `test_enum_gate.py` and the v4-project setup pattern in `test_stage_guard.py`.

## Context that was missing

- Origin was a downstream project (novel-workspace O-00000005) running an older cached plugin
  (0.23.0); the bug reproduced identically on latest source (0.31.2), so no version archaeology
  needed.

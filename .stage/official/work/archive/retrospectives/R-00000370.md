# R-00000370 카드에서 회고 칸을 없애고 유지 카드는 두 가지만 묻는다

## Work

새 카드와 새로 시작하는 카드에서 `## Retrospective` 와 `## Promotion decision` 을 뺐다. 유지 카드를 등록하는
`--maintenance` 를 넣고, `stage-work` 스킬이 유지와 성취를 먼저 가르게 했다.

## Decision points

- 유지 카드인지를 카드에 `maintenance: true` 로 적는다. 칸이 없는 것으로 미루어 알게 하면 시작할 때 칸을
  다시 넣을지 판단할 근거가 약하다.
- 유지를 종류(`fix`, `chore`)로 정하지 않고 등록할 때 고르게 했다. 고치는 일도 처음 동작하게 만드는 것이면
  성취라고 철학 문서가 말한다.
- `--maintenance` 와 `--milestone` 을 함께 쓰면 거절한다. 철학 문서는 유지를 매달지 않는다고 하고, 둘을 함께
  허용하면 무엇이 유지인지 다시 흐려진다.
- 유지 카드에도 `## Scope` 와 `## Actions` 는 남겼다. 범위 신호와 계층은 유지에도 필요하다.
- 스키마 v3 양식과 보관 양식은 그대로 뒀다. 보관 양식에는 두 칸이 원래 없다.

## Principles applied

- SSOT: 회고와 승격 결정은 회고 파일 한 곳에 둔다.
- KISS: 유지 카드는 두 질문으로 끝난다.
- Fail Fast: 쓸 수 없는 조합을 카드를 만들기 전에 거절한다.

## Context that helped

- 철학 문서의 한 줄 기준("이 일이 끝나면 제품이 전에 못 하던 걸 하게 되나")이 스킬의 첫 질문이 됐다.
- `tier` 와 `environment` 가 선택 필드를 넣는 방식을 보여 줬다.

## Context that was missing

- 프로젝트가 양식 사본을 `.stage/work/current/` 에 가지고 있고 감사가 그 차이를 본다는 것을 감사를 실행하고
  알았다.
- 보관 양식에 두 칸이 있다고 낱말 검색만 보고 짐작했다. 열어 보니 없었고, 고치는 스크립트가 중간에 멈췄다.

## Next changes

- 다음 유지 카드를 `--maintenance` 로 등록해 실제로 써 본다.
- 스킬을 읽은 세션이 유지와 성취를 어떻게 가르는지 다음 등록 때 본다.

## Rule candidate

- 양식을 고치면 프로젝트의 양식 사본도 `refresh_guidance.py` 로 맞춘다. 한 번 겪었다. 감사가 이미 알려 주므로
  규칙으로 올리지 않는다.

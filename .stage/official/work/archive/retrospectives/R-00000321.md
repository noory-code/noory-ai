# R-00000321 Windows 셸 파서가 드라이브에 붙인 /dev/null 도 장치로 알아본다

## Work

W-00000321. Windows 셸 파서는 드라이브 없는 `/dev/null` 을 상대 경로로 보고 작업 드라이브에 붙여(`C:\dev\null`) 넘긴다.
W-00000319 는 그 앞 단계의 글자만 봐서 Windows CI 가 여전히 범위 넘음을 냈다. 드라이브 뒤의 알려진 장치 이름만 장치로 보게 고쳤다.
외부 결과: Windows 에서 출력을 `/dev/null` 로 버리는 명령에 범위 넘음 경고가 뜨지 않는다. `C:\dev\` 아래 작업 폴더는 영향받지 않는다.
내부 결과: PR 의 CI 가 모든 OS·버전에서 초록이다(2026-11-02, 커밋 `c91f196f`). Stage Windows 3.9·3.12 hooks 시험이 통과했다.

## Decision points

- 셸 파서의 고정 방식을 바꾸지 않고 보고 쪽 판별을 고쳤다. `.stage` 게이트도 그 고정에 기대고 있다.
- 드라이브 뒤에는 알려진 장치 이름만 인정했다. `C:\dev\proj` 같은 흔한 작업 폴더를 장치로 오인하지 않는다.

## Principles applied

Honesty: W-00000319 가 첫 기준을 이뤘다고 닫혔지만 Windows 의 실제 흐름에서는 아니었다. 단위 시험이 셸 파서를 거치지 않은 모양만 봤다.
만든 쪽 ≠ 보는 쪽: 실행 맥락이 없는 별도 Claude 세션이 판정했다. 같은 모델 계열이라 교차 venue 판정은 아니다.

## Context that helped

- CI 로그가 `C:/dev/null` 을 그대로 보여 줘, 셸 파서가 이미 드라이브를 붙인다는 것을 코드로 바로 확인할 수 있었다.

## Context that was missing

- W-00000319 의 시험은 함수에 원래 모양을 넣었고, 실제 호출 경로(셸 파서 → 판별)를 거치지 않았다. Windows 를 직접 돌릴 수 없을 때는
  실제 호출 경로가 만드는 값을 코드에서 따라가 시험에 넣어야 한다.
- 사용자가 PR 을 병합했다고 했을 때 PR 은 실제로 열려 있었다(CI 실패 중). 병합 여부는 GitHub 에서 확인하고 말해야 한다.

# R-00000056 안내 문서 갱신의 소유 경계 확정

## Work

한 파일 안에 플러그인이 준 설명글과 프로젝트가 쌓은 목록이 섞여 있을 때 갱신 명령이 어디까지
손대는지를 DE-00000029로 확정했다. 판정은 템플릿의 표 모양으로 한다 — 빈 표로 배포됐으면
프로젝트가 채우는 자리, 내용이 들어 있으면 플러그인 것. W-00000057의 범위에 반영했다.

## Decision points

- 경계를 새로 표시할 것인가, 이미 있는 것에서 읽어낼 것인가 — 템플릿 17개를 실제로 세어
  보고 나서야 "빈 표 12개 / 내용 든 표 5개"라는 경계가 이미 존재함이 보였다. 마커 도입은
  불필요해졌다.
- "표는 프로젝트 것"으로 단순화할 것인가 — `roadmap/index.md`와 루트 `index.md`의 표는
  플러그인 내용이라 이 단순화는 거짓이다. 조사가 없었으면 그대로 갔을 규칙이다.

## Principles applied

- SSOT — 경계의 소유 위치는 템플릿이다. 두 번째 선언을 만들지 않는다.
- AHA / KISS — 마커라는 새 장치는 반복이 보이기 전에는 만들지 않는다.
- MECE — 세 갈래가 대상 파일 전체를 겹치지 않게 덮는지 파일 수로 확인했다.
- Fail Fast — 애매한 경우(빈 표 2개 이상, 내용 든 표)는 덮지 않고 보고하는 쪽으로 실패한다.

## Context that helped

- 템플릿 디렉터리 자체가 가장 좋은 근거였다. 추측으로 규칙을 세우지 않고 파일을 세었다.
- DE-00000028이 "무엇을 할지"와 "어디까지 손댈지"를 분리해 둔 덕분에 이 카드가 작게 끝났다.

## Context that was missing

- 각 인덱스 문서의 표가 프로젝트 데이터인지 플러그인 내용인지 어디에도 적혀 있지 않다.
  이번엔 표가 비어 있는지로 알아냈지만, 그 사실 자체는 문서화돼 있지 않다. W-00000057 구현
  시 판정 로직에 근거 주석으로 남긴다.

## Next changes

- 사용자 피드백: `.stage` 문서와 대화 모두 영어 직역체를 쓰지 않는다. 새로 쓰는 문서에
  적용하고, 이미 아카이브된 기록은 건드리지 않는다.

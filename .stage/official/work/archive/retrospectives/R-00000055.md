# R-00000055 마이그레이션의 안내 산문 갱신 방식 결정

## Work

Q-00000001이 물은 "마이그레이션이 `.stage` 안내 산문을 갱신하지 않는 문제"를 DE-00000028로
결정했다: 감사가 현행 템플릿과의 드리프트를 감지하고, 갱신은 명시적 명령으로 수행한다.
구현은 W-00000057(`parent: W-00000056`)이 소유한다. Q-00000001은 답을 얻어 닫혔다.

## Decision points

- 후보 3개로 물을 것인가, 근거를 먼저 확인할 것인가 — 코드를 먼저 확인했고, 그 결과 후보
  하나(init 재실행 문서화)가 사실이 아님이 드러났다. `init_stage.py`는 기존 파일을 건너뛰고
  `--force`는 프로젝트 데이터를 덮는다.
- 후보 집합이 완전한가 — 관측된 드리프트를 분류하자 세 종류(스키마 세대, 언어 불일치, 버전 내
  문구 변경)였고, 원래 후보 1(마이그레이션 자동 교체)은 첫 번째만 덮었다. 소유권 자체를
  바꾸는 후보 D(복사본 폐지)를 추가해 4개로 비교했다.
- 사용자에게 물을 것인가 — 질문 게이트가 걸렸고, 목적과 원칙에서 답이 도출되어 질문을 접고
  결정했다.
- 구현 항목의 계보를 무엇으로 표현할 것인가 — 처음에 `parent: W-00000056`으로 등록했더니
  집계 게이트가 완료를 막았다. `parent`는 계층이 아니라 집계 관계이므로(하위가 열려 있는
  동안 상위는 미완) 결정만 소유하는 카드에는 맞지 않는다. 계보를 카드 본문 `Source`로
  옮겼다.

## Principles applied

- Fail Fast — 낡은 산문이 감사 오류 0으로 통과한 것이 문제의 본질이므로, 감지 책임이 없는 안은
  성립하지 않는다. 이것이 후보를 하나로 좁힌 결정적 기준이었다.
- MECE — 드리프트를 세 종류로 분류하자 스키마 경계에서만 작동하는 안의 공백이 드러났다.
- Honesty — 존재하지 않는 절차(init 재실행)를 문서화하지 않는다. 코드로 확인한 뒤에야 후보를
  탈락시켰다.
- AHA / KISS — 프로버넌스 스탬프나 세대별 템플릿 이력 같은 새 장치를 만들지 않고,
  `migrate_operations`의 바이트 비교와 `operations_overrides` 선언 패턴을 확장한다.
- SSOT — 안내 산문의 소유자는 플러그인 템플릿이고 프로젝트 파일은 파생물이라는 관계가
  모든 후보의 판정 기준이었다.
- Question protocol — 상위 목적과 원칙에서 답이 나오는 질문은 하지 않는다.

## Context that helped

- W-00000053의 커밋(e9ed1af4)이 갱신 대상 42개 파일과 드리프트의 실제 성격을 그대로 보여줬다.
  후보 비교를 추측이 아니라 관측 위에서 할 수 있었던 유일한 근거다.
- DE-00000002의 operations 소유권 계약이 "바이트 동일 = 플러그인 소유" 판정의 선례였다.
- 질문 게이트가 후보 나열 대신 원칙 재확인을 강제했다.

## Context that was missing

- 인덱스 문서에서 "플러그인 소유 머리말"과 "프로젝트 소유 표"의 경계가 어디에도 선언돼 있지
  않다. 부분 교체 구현의 핵심 위험이며 W-00000057이 확정해야 한다.
- "결정 카드와 그 구현 카드를 어떤 관계로 묶는가"에 대한 지침이 없다. `parent`(집계)와
  본문 `Source`(계보)의 구분은 README에 흩어져 있고, 계획 카드를 쓰는 사람이 집계 게이트를
  먼저 만나야 알게 된다.
- 이 프로젝트가 언제 어떤 언어로 init됐는지 기록이 없어, 언어 드리프트가 발생한 시점은
  커밋 이력에서 역추적해야 했다.

# R-00000013 Stage documents in the user's language

## Work

Added a project-declared language for human-readable `.stage/` documents: a backward-compatible
`language` setting, locale template overlays with Korean bundled, an injected generation
directive for records created after initialization, localized session-summary labels, audit
validation of the tag, and a structural parity test protecting the machine contract. Released as
Stage 0.20.0.

## Decision points

- Chose overlay-over-canonical (English structural SSOT + prose-only locale files) over full
  per-language trees or a directive-only approach; DE-00000003 records why both alternatives
  fail the backlog's own criteria and risks.
- Drew the machine/human boundary explicitly: record section headings stay English because
  `close_work.py` and skills match them literally; titles, prose, and index labels localize.
- Made hooks fall open to English on malformed tags while only the audit reports them, keeping
  gating behavior independent of localization state.
- Let unbundled tags (e.g. `fr`) initialize with English files while still stamping the tag, so
  the generation directive governs post-initialization records even without bundled templates.

## Principles applied

- SSOT: structure and machine tokens exist once in the canonical English templates; locale files
  carry only translated prose.
- MECE: every string is classified exactly once as machine or human by the DE-00000003 boundary.
- Fail Fast: the parity test fails the build when a locale file drifts; `LANG001` surfaces
  malformed settings.
- AHA: no message-catalog framework; one file overlay plus one in-code label table.
- Honesty: no semantic language detection anywhere — only format validation.

## Context that helped

- The v2 ownership split (DE-00000002) had already removed eleven common docs from the template
  tree, cutting the translation surface to 40 prose files.
- Knowing exactly which headings and table cells code parses (mapped during W-00000012) made the
  machine/human boundary a lookup, not a guess.

## Context that was missing

- No inventory existed of which generated strings reach the user from code (only the session
  summary did); a future audit of user-facing hook output would confirm nothing else needs the
  label table.

## What changes in later behavior

- New template files must ship with a `ko` counterpart or the parity coverage test fails —
  template changes now carry a two-file obligation.
- New user-facing strings generated by hook code must go through `SUMMARY_LABELS`-style tables,
  not inline literals.
- When adding a locale, bundle it as `templates/locales/<tag>/` and extend the summary label
  table; no code changes are needed beyond that.

## Routing

- Everything lives in the released `stage/` plugin; nothing promotes to this repository's
  `official/`. This repository keeps `"language": "en"` implicitly via the default (its records are
  English per the host instruction, consistent with the DE-00000003 boundary).

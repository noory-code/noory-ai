# R-00000004 Venue field — optional frontmatter is non-breaking by parser design

## Work

Added an optional `venue` frontmatter field to the work-item shape and a `Venue` column to the
Active Work index; documented it in `artifacts.md` and added a `Venue` term plus an example
`kind -> venue` routing table to `vocabulary.md`; bumped both plugin manifests 0.12.1 -> 0.13.0.

## Decision points

- `venue` is advisory — a human routing hint, never a hook gate.
- Values are project-defined, like `kind`; no agent names are hardcoded into the harness, so
  the shared harness stays general and the project owns its venue vocabulary.
- The live `official/canon/vocabulary.md` routing table was deferred to the promotion-intent flow
  because the canon subtree is gate-protected.

## Principles applied

- SSOT — the routing signal lives on the work item (the shared work SSOT), not in either chat
  window; and no agent names are baked into the harness.
- Postel's Law — the frontmatter parser ignores/defaults absent keys, which is *why* adding an
  optional field needs no migration; this was verified against the parser, not assumed.

## Context that helped

`hooks/stage_work.py` is a permissive parser that defaults unknown/absent keys — confirming
directly that existing work items without `venue` stay valid.

## Context that was missing

Nothing material.

## Next changes

Canon edits (`official/canon/vocabulary.md`) route through the promotion-intent flow, not direct
edits — this repo's live venue routing table is still pending that intent as a separate
follow-up, distinct from shipping the field in the plugin.

## Promotion decision

`promotion: not_applicable` — the change lives in the `stage/` plugin package, not this repo's
`.stage/official/` canon, so there is nothing to promote here.

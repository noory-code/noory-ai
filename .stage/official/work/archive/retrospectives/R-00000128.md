# R-00000128 드라이버 자식 환경 계약 회고

## Work

드라이버가 자식에게 주는 프로젝트 변수의 계약이 실측으로 갈렸고, 그대로 코드가 됐다. 세션
자식(실행자·리뷰어·사전 점검·close_work)은 `CLAUDE_PROJECT_DIR`·`PROJECT_ROOT` 를 대상
루트로 **박아** 받고, 인수 검사는 두 변수를 **걷어낸** 환경을 받는다. 훅을 띄우는 테스트
스위트는 hermetic 이라 두 변수가 어떤 값이든 — 올바른 루트여도 — 실려 있으면 깨진다.

## Decision points

- **1라운드를 승인 리뷰에도 불구하고 닫지 않았다.** 넷 다 박는 구현이 기준 그대로였고 리뷰도
  승인이었지만, 그 직후의 실측(본 체크아웃에서 변수를 자기 루트로 박자 소비자 테스트 4개가
  깨짐)이 절반이 틀렸음을 보였다. 기준을 실측대로 갈라 다시 돌렸다.
- **2라운드도 드라이버 판정으로는 실패였고, 받지 않았다.** 이 수정은 구조적으로 자기 스텝의
  검사로 검증이 안 된다 — 도는 드라이버는 항상 수정 전 코드라, 자기 인수 검사를 옛 방식
  (변수 박은 채)으로 돌려 스스로 깨진다. 새 프로세스로 두 스위트를 돌려 검증하고(477+343
  전부 통과), 드라이버가 안내하는 수동 닫기로 닫았다.

## Principles applied

- Honesty — 승인 리뷰를 그대로 받지 않았고, 실측이 계약을 바꿨다. 반대로 드라이버의 실패
  판정도 그대로 받지 않았다 — 무엇이 실패했는지 확인하니 판정 도구 자신이었다.
- SSOT — 변수를 지우는 쪽과 박는 쪽의 이유가 카드와 CHANGELOG 에 있다. 코드 주석에 묻지
  않았다.

## Context that helped

- 병렬 첫 실전의 실패 여섯이 전부 이 계약의 실측 근거가 됐다. 실패가 좋은 데이터였다.

## Context that was missing

- **수정을 만든 스텝의 검사는 옛 코드가 돌린다는 것.** 드라이버 자신을 고치는 카드는 항상 이
  자기 참조에 걸린다 — 1라운드 승인 리뷰가 심는 문제를 못 본 이유이고, 2라운드 검사가 걷어낸
  독으로 깨진 이유다. 드라이버를 고치는 카드는 검증을 새 프로세스에서 따로 해야 한다는 것을
  이제 안다.
- 두 변수가 실려 오는 실제 경로는 백그라운드 셸이 아니라 **병렬 명령의 트리별 박기와 사람의
  수동 박기**뿐이었다. 처음 진단(백그라운드 누수)은 틀렸고, 원인을 셋째 시도에서 잡았다.

## Next changes

  변수를 걷는 강화는 실제로 그 경로를 겪으면 카드로 세운다(AHA) — 지금은 실어 보내는 경로가
  없다.

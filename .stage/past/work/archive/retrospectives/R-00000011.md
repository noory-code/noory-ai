# R-00000011 Optional field-driven review — the user's refinement dissolved the over-engineering

## Work

Added an optional `review` frontmatter field (not_required/pending/passed). Review is bypassed by
default; an item that declares `review: pending` cannot complete until `review: passed`, enforced by
the completion gate (so a hand-edited `status: completed` commit is blocked too). `close_work` runs
the configured review only for a pending item; `register_work --review` opts an item in.

## Decision points

- Two prior red-teams flagged the review feature as over-engineering risk. The user's own refinement
  resolved it: make review OPTIONAL and driven by the item's own field ("frontmatter에 있으면 반드시,
  없으면 우회"). That removed the settings-coupling and the always-on enforcement — the field is the
  switch, mirroring `verification` but bypassed by default.
- Enforcement lives in the completion gate (a field check), the one thing a 10s hook can do. It does
  not prevent hand-typing `review: passed` — same limit as `verification` — but it makes a declared
  review mandatory to satisfy before completion.

## Principles applied

- Honesty / Fail Fast — code red-teamed before commit; the headline "set_field wedge" attack was
  shown unreachable (review_passed is only set when the `review:` line provably exists), and
  backward-compat was verified against the 11 archived items.
- KISS / AHA — the user's field-driven framing is far simpler than the settings-gated design and
  matches the proven verification pattern; no new subsystem.
- SSOT — `REVIEW_DONE`/`REVIEW_VALUES` have one home, shared by the enum gate, completion gate, and
  audit.

## Context that helped

The existing `verification` field + `item_completion_blockers` gave the exact pattern to mirror, so
the change was small and low-risk.

## Context that was missing

Nothing. The design churn (settings-gated vs field-driven) came from me over-reaching before the
user stated the simpler intent — a reminder to surface the user's mental model first.

## Next changes

None required. If hook-level enforcement beyond the field is ever wanted, it needs a non-invasive
design (the Stop-hook subprocess attempt in W-7 showed the invasive version breaks the hook contract).

## Promotion decision

`promotion: not_applicable` — changes live in the `stage/` plugin package.

# R-00000012 Plugin-owned common operations, project-owned policy

## Work

Separated Stage's common operational rules from project policy: eleven common docs moved to the
plugin-owned `operations/` directory and stopped being copied into projects, the project surface
narrowed to the `kind -> passed` verification table plus declared `operations_overrides`, the
schema contract bumped to version 2 with new audit drift checks, an idempotent migration script
shipped, and this repository migrated cleanly. Released as Stage 0.19.0.

## Decision points

- Recorded DE-00000002 before touching implementation: the ownership boundary, the resolution
  mechanism (installed plugin, not copies), the minimal project policy surface, the version
  contract, and the never-destructive migration rule.
- Chose plugin-resolution over managed auto-refreshed copies because the backlog's verification
  criteria mandate that fresh initialization copy no identical common rules.
- Kept `.stage/operations/verification.md` at its existing path so the audit's table parser and
  every consumer stay compatible without a rename migration.
- Made overrides a declared list in `settings.json` so an undeclared same-name file is
  distinguishable drift, not an ambiguous intentional edit.
- Rewrote a project `verification.md` only when its prose stays within the known legacy template
  lines; any project-authored prose blocks the rewrite and is reported instead.

## Principles applied

- SSOT: each operational rule now has exactly one owning location; ten byte-identical copies in
  this repository alone were duplication by construction.
- MECE: plugin-common versus project-policy content no longer mixes in one file.
- Fail Fast: stale copies used to fail silently (this repo's `artifacts.md` had lost the venue
  contract); OPS001–OPS004 now surface drift explicitly, and hooks fail closed on nothing new.
- AHA: the override mechanism is a flat declared list, not a merge engine, until real projects
  demonstrate more need.
- Completion: decision record, implementation, tests (377 total), migration, self-migration,
  docs, changelog, and release all closed inside the work item.

## Context that helped

- The consumption map (which code reads which operations doc, structurally vs advisory) gathered
  before the decision made the boundary obvious: only two docs are machine-parsed.
- The byte-level diff of this repository's 12 copies against the templates quantified the
  duplication and exposed the venue drift the backlog described.

## Context that was missing

- No record stated whether this repository's stale `artifacts.md` was an intentional edit or a
  leftover old template; the byte-diff (template strictly ahead, no project additions) resolved
  it, but a declared-override list would have answered it directly — which is what shipped.

## What changes in later behavior

- When a rule feels common to every project, it goes upstream to the plugin's `operations/`, not
  into `.stage/`; `.stage/operations/` additions are project policy only.
- Migration scripts in this plugin follow the DE-00000002 rule: idempotent, dry-runnable, and
  never deleting content that differs from the current plugin copy.
- The retrospective of a future release must check whether `operations_overrides` was ever
  exercised by a real project; if not, consider removing it (AHA follow-up from DE-00000002).

## Routing

- The venue vocabulary entry promotes to `past/canon/vocabulary.md` (declared owner of venue
  values and `kind -> venue` routing for this repository).
- Everything else lives in the released `stage/` plugin and this repository's migrated `.stage/`
  configuration; nothing stays provisional in `present/state`.

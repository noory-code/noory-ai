# DE-00000091 두 세션이 같은 목록 파일을 고쳐도 손으로 합치지 않는 방법

## Question

두 세션이 따로 카드를 등록하고 닫은 뒤 브랜치를 합칠 때, 목록 파일에서 나는 충돌을 어떻게 없앨 것인가?

이 저장소의 머지 136건을 처음 상태에서 다시 실행하면 27건에서 충돌이 난다. 충돌한 파일은 아래와 같다.

| 파일 | 충돌한 횟수 | 줄이 바뀌는 방식 |
|---|---:|---|
| `stage/CHANGELOG.md` | 14 | 줄을 더하기만 한다. |
| `.stage/work/active.md` | 8 | 시작할 때 더하고 닫을 때 지운다. |
| `.stage/work/review.md` | 7 | 닫을 때 더하고 보관할 때 지운다. |
| `.stage/work/planned/index.md` | 2 | 등록할 때 더하고 시작할 때 지운다. |
| `.stage/official/work/archive/index.md` | 2 | 줄을 더하기만 한다. |
| `.stage/decisions/index.md` | 1 | 결정이 승격되면 줄을 지운다. |
| 목록이 아닌 파일 두 개 | 1씩 | 이 결정의 대상이 아니다. |

## Options

| 선택지 | 내용 | 드는 일 |
|---|---|---|
| 모두 union 으로 합친다 | 목록 파일 전부에 `.gitattributes` 의 `merge=union` 을 건다. git 이 양쪽 줄을 모두 남긴다. | 설정 파일 하나 |
| 더하기만 하는 파일은 union, 지우는 파일은 카드에서 만든다 | `CHANGELOG.md` 와 보관 목록은 union 으로 합친다. 줄을 지우는 목록은 git 이 추적하지 않고, 카드의 상태를 읽어서 만든다. | 설정 파일 하나와 목록을 읽고 쓰는 코드 |
| 항목마다 파일을 하나씩 둔다 | 목록 파일을 없애고 항목 하나를 파일 하나로 둔다. 릴리스할 때 합친다. | 릴리스 도구, 양식, 목록을 읽는 코드 전부 |

## Principles applied

- SSOT — 카드의 상태는 카드의 `status` 가 소유한다. 같은 사실을 목록 파일의 줄로 한 번 더 적으면 두 세션이 같은 줄을 고친다.
- Fail Fast — 틀린 목록을 조용히 만드는 방법은 충돌보다 나쁘다. 충돌은 사람이 보고, 되살아난 줄은 아무도 보지 않는다.
- KISS — 더하기만 하는 파일은 git 이 이미 가진 기능으로 합친다.

## Chosen direction

더하기만 하는 목록은 union 으로 합치고, 줄을 지우는 목록은 git 이 추적하지 않는다.

- `CHANGELOG.md`(모든 플러그인)와 `.stage/official/**/archive/index.md` 는 `.gitattributes` 에 `merge=union` 을 건다.
- `.stage/work/active.md`, `.stage/work/review.md`, `.stage/work/planned/index.md` 는 저장소에 두지 않는다. 이 목록이
  필요한 자리는 카드의 `status` 를 읽어서 만든다.
- `.stage/decisions/index.md` 는 이미 `refresh_decision_index.py` 가 기록에서 다시 만든다. 위 세 파일과 같은 방식으로
  다룬다.

### union 이 줄을 지우는 목록에서 닫은 카드를 되살린다

과거 머지 27건을 union 을 걸고 다시 실행해서, 나온 파일을 그때 사람이 커밋한 파일과 비교했다.

| 파일의 종류 | 다시 합친 횟수 | 줄이 사람이 합친 것과 같다 | 줄이 다르다 |
|---|---:|---:|---:|
| 더하기만 하는 파일 (`CHANGELOG.md`, 보관 목록) | 16 | 16 (그중 7번은 줄의 순서만 다르다) | 0 |
| 줄을 지우는 파일 (`active.md`, `review.md`, `planned/index.md`, `decisions/index.md`) | 18 | 5 | 13 |

줄이 다른 13번은 모두 사람이 지운 줄이 남아 있었다. union 은 충돌한 자리에서 양쪽의 줄을 모두 남기므로, 한쪽이
지운 줄을 다른 쪽에서 가져온다. 닫은 카드가 `active.md` 에 다시 나타난다.

union 을 걸면 충돌은 27건에서 2건으로 줄고, 남은 2건은 목록이 아닌 파일이다.

## Reason

목록 파일의 줄은 카드가 이미 가진 사실을 한 번 더 적은 것이다. 한 파일에 모든 카드의 줄이 모이므로 두 세션이
다른 카드를 다뤄도 같은 파일을 고친다. 줄을 지우는 목록은 union 으로 합치면 틀린 결과가 나오므로, 파일을
없애고 카드에서 만드는 방법만 남는다. 세션 시작 글의 "Lifecycle view" 는 이미 카드 폴더를 읽어서 만든다.

더하기만 하는 목록은 줄을 잃거나 되살릴 일이 없어서 union 으로 충분하다.

이 결정이 틀렸다고 볼 일: union 으로 합친 `CHANGELOG.md` 나 보관 목록에서 줄이 빠지거나 두 번 들어간 채로 머지된다.
또는 목록을 카드에서 만드는 데 걸리는 시간 때문에 세션 시작이나 관문이 눈에 띄게 느려진다.

## Follow-up

- 목록을 카드에서 만드는 쪽은 실행해 보지 않았다. 만들어 보려면 이 결정이 정하는 코드를 써야 해서, 구현 카드가
  확인한다.
- 세 목록을 파일로 남겨 두고 `.gitignore` 에 넣을지, 파일을 아예 두지 않을지는 정하지 않았다.
- union 으로 합친 보관 목록은 줄의 순서가 사람이 합친 것과 다를 수 있다. 순서를 보는 점검 규칙이 있는지는
  확인하지 않았다.
- 항목마다 파일을 하나씩 두는 방법은 실행해 보지 않았다.

## 2026-11-22 에 더한 관측

W-00000384 가 실제 `release_plugin.py` 릴리스로 시험했다. union 으로 합친 `CHANGELOG.md` 에서 줄이 빠지거나 두 번 들어간 일은
없었다. 그런데 세 번째 결과가 있었다. 한 브랜치가 릴리스하고 다른 브랜치가 `## Unreleased` 에 줄을 더한 뒤 합치면, 그 줄이
남되 릴리스된 버전 절에 들어갈 수 있다. 충돌은 나지 않는다.

- 원인은 union 이 아니다. 릴리스는 남아 있는 줄 위에 버전 제목만 끼워 넣는다. union 없이 합쳐도 맨 아래에 더한 줄은 같은
  자리로 간다. 그래서 이 결정은 바뀌지 않는다(사용자가 2026-11-22 에 메모로 남기기로 정했다).
- 찾는 방법: `release_plugin.py <plugin> --check-released` 가 각 릴리스 절을 그 릴리스 커밋이 쓴 내용과 비교해 나중에 더해진
  줄을 출력한다(W-00000392). 찾은 줄은 `## Unreleased` 로 옮긴다.
- 이 저장소의 stage 변경 기록은 이 점검에서 0.51.0, 0.49.0, 0.43.5 세 절의 항목 넷이 걸린다. 0.51.0 의 것은 릴리스 뒤에 일부러
  더한 줄이다(커밋 97563cc4). 이 점검을 CI 에 넣기 전에 과거 절을 어떻게 다룰지 정해야 한다.

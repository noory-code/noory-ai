# DE-00000003 Language setting schema and the machine/human content boundary

## Question

How does a project declare the language of human-readable `.stage/` documents, what exactly is
localized versus kept language-neutral, and how do initialization, skills, hooks, and the audit
honor that declaration without breaking the machine contract?

## Options

1. **One setting + locale template overlays + injected generation directive.** English templates
   stay the single structural SSOT; a per-language overlay tree overrides prose-bearing files at
   initialization; a SessionStart directive makes every record-creation skill write in the
   configured language; a parity test pins locale files to the English structure.
2. **Full per-language template trees.** Complete duplicate trees per language; maximal drift
   surface for ~60 files, most of which contain no prose (the SSOT risk B-00000002 itself names).
3. **Directive only, English initialization.** Smallest change, but a Korean initialization would
   not produce Korean human-readable documents, failing the backlog's verification criteria.

## Principles applied

- **SSOT** — structure, frontmatter keys, enum values, and machine tokens exist once, in the
  English canonical templates; locale overlays carry only translated prose.
- **MECE** — an explicit machine/human boundary decides every string exactly once: machine tokens
  are never translated, human surfaces always follow the setting.
- **Fail Fast** — the audit reports a malformed language value; the parity test fails the build
  when a locale file drifts from the canonical structure.
- **AHA** — no translation framework or message-catalog engine; a file overlay and one string
  table for the generated session summary.

## Chosen direction

Option 1, with this contract:

**Setting.** `settings.json` gains `"language"`: a lowercase IETF-style tag
(`^[a-z]{2,8}(-[a-z0-9]{2,8})*$`, e.g. `en`, `ko`, `pt-br`). Missing key → `en`
(backward-compatible: existing projects keep current behavior; no schema bump — the shape only
gains an optional key). The audit warns (`LANG001`) on a malformed or non-string value and never
attempts semantic language detection.

**Machine/human boundary (never translated):** artifact IDs, paths and filenames, frontmatter
keys and enum values, work `kind` and venue tokens, principle names (`SSOT`, `MECE`, …), record
section headings (`## Purpose`, `## Verification`, … — `close_work.py` and skills match them
literally), audit markers in `official/canon/principles.md`, commands, and backtick-quoted tokens.
**Localized surfaces:** document titles after the ID, prose bodies, index and README explanatory
text, non-token table cells, and the generated session-summary labels.

**Initialization.** `templates/project-stage/` remains the canonical English SSOT.
`templates/locales/<lang>/` mirrors only prose-bearing files; `init_stage.py --language <tag>`
copies the locale file when present, falls back to English otherwise, and stamps the setting into
the created `settings.json`. A parity unit test asserts every locale file matches its canonical
counterpart's frontmatter keys, backtick tokens, and token-table first cells, and that no locale
file exists without a canonical counterpart.

**Generation.** SessionStart injects a language directive whenever the effective language is not
English: write human-readable Stage content in the configured language, keep machine tokens
exactly as templates declare. Skills need no per-skill changes. The Stop-hook session summary
resolves its labels from a small in-code string table (`en`, `ko`; unknown tag → `en`).

**Host interaction.** The Stage setting owns the language of human-readable `.stage/` content;
host instructions (CLAUDE.md, AGENTS.md) own everything outside `.stage/`. When a host rule
explicitly dictates a conflicting `.stage/` document language, that is a real conflict: register
an open question with a proposed correction instead of silently obeying either side. This
repository declares `"language": "en"` explicitly, matching its English-artifacts rule.

**Excluded.** No automatic translation of existing records (switching the setting affects newly
generated content only), no per-language duplication of structure-only files, no language
detection in gates.

## Reason

The backlog requires a Korean initialization to produce Korean human-readable documents, which
rules out option 3, while its own risk list rules out wholesale template duplication. An overlay
of only prose-bearing files plus a structural parity test gives deterministic initialization in
both languages with one structural owner, and the injected directive extends the same contract to
everything generated after initialization without touching each skill.

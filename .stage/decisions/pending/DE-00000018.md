# DE-00000018 acceptance 필드 스키마 확정

## Question

DE-00000014가 남긴 follow-up: acceptance 필드의 정확한 스키마, 자율 적격 신호, 기존 `--check`와의 관계를 어떻게 확정하는가? (드라이버·에스컬레이션이 이 스키마를 읽으므로 다른 항목이 의존한다.)

## Options

- 단계 표현: (a) 셸 명령 문자열 리스트 vs (b) 객체 리스트(command + timeout + cwd).
- 자율 적격: (a) 명시 `autonomous` 플래그 vs (b) `acceptance` 유무로 파생.
- `--check` 관계: (a) 통합(acceptance가 저장된 검증, --check는 추가) vs (b) 병존.

## Principles applied

- KISS / AHA — 스키마는 최소로. per-step timeout/cwd는 반복 필요가 보일 때 추가.
- Fail Fast — 자율 적격인데 acceptance가 없으면 등록 시점에 거부한다.
- SSOT — 종료 조건(검증 명령)의 소유 위치는 item의 `acceptance` 필드다.
- DRY — 기존 `run_check()`(close_work.py) 실행 경로를 재사용한다. 새 엔진 없음.

## Chosen direction

- **`acceptance`** = 프론트매터 YAML 리스트, 각 항목은 셸 명령 문자열. 기존 `run_check()`로 실행하고 모든 명령 exit 0이면 통과. per-check 타임아웃은 이미 있는 `--timeout`을 재사용(단계별 timeout/cwd는 도입하지 않음).

  ```yaml
  autonomous: true
  acceptance:
    - "python3 -m unittest discover -s stage/hooks/tests -q"
    - "python3 stage/scripts/audit_stage.py"
  ```

- **`autonomous: true`** 필드로 적격을 명시(기본 false/부재). `autonomous: true`면 `acceptance` 필수 — 없으면 `register_work`/`start_work`가 거부(Fail Fast). 비자율 항목은 현행 그대로 acceptance 없이 동작.
- **통합**: `close_work`가 item의 `acceptance`를 읽어 실행하고, `--check` CLI 인자는 거기에 추가 병합(둘 다 통과 필요). item에 `acceptance`가 있으면 현행 "no --check" 하드 에러를 해제(자율 실행의 핵심).

## Reason

셸 문자열 리스트는 최소이며 기존 `--timeout`으로 충분하다(AHA). 명시 `autonomous` 플래그라야 "자율 의도인데 acceptance 누락"을 등록 시점에 거부할 수 있다(파생 방식은 거부 자체가 불가). `run_check()` 재사용으로 새 실행 엔진을 만들지 않는다(DRY). `acceptance`가 item에 상주해야 드라이버가 사람의 `--check` 입력 없이 종료를 판정할 수 있다.

## Follow-up

- 단계별 timeout/cwd는 반복 필요가 확인되면 OCP로 추가한다.
- `acceptance` 파서는 stdlib 리스트 파싱으로 구현(yaml 의존 없음). WorkItem 데이터클래스/파서에 `acceptance`(list)·`autonomous`(bool) 추가.
- 필드는 planned·current 템플릿 양쪽에 두고 start_work가 carry한다.

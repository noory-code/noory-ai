# DE-00000022 에스컬레이션 출구와 한계 config의 경계

## Question

DE-00000017의 에스컬레이션·폭주 상한을 드라이버(W-47) 이전에 어디까지 만드는가? 시도 카운트·무진전 감지·전역 예산 집행은 대부분 드라이버 런타임인데, W-46의 경계는 어디인가?

## Options

- A. W-46 = 에스컬레이션 출구(항목 → `blocked` + pending decision 생성) + 한계 config 스키마/리더. 실제 카운트·감지·집행은 드라이버(W-47).
- B. W-46이 카운트·무진전 감지·런타임 상태 스키마까지 포함.
- C. W-46을 W-47에 병합.

## Principles applied

- SoC / SRP — "포기 시 무엇을 하는가(출구)"와 "언제 포기하는가(루프 집행)"는 다른 책임.
- AHA — 드라이버가 없는 상태에서 런타임 카운트/진행-지문 스키마를 미리 만들지 않는다.
- Fail Fast / No partial completion — 상한 도달은 `blocked`이지 `completed`가 아니다(불변식).
- SSOT — 한계 값의 단일 소유 위치는 settings.json config.
- DRY — `close_work`/`archive_work` 스크립트 패턴을 미러링.

## Chosen direction

A. W-46은 에스컬레이션 출구와 한계 config만 만든다.

- **에스컬레이션 헬퍼**: 열린 항목을 `blocked`로 전환하고, 이유를 담은 pending decision(DE)을 생성한다. `close_work`/`archive_work`처럼 재사용 가능한 스크립트/함수. 상한·막힘 도달 = `blocked` + 결정, 절대 `completed` 아님.
- **한계 config**: settings.json에 한계 섹션(예: `limits`) — 항목당 시도 상한, 전역 상한(반복 수·벽시계 등). 스키마 + 리더(review config 리졸버 패턴). 집행은 드라이버가 한다.
- **드라이버 런타임**(시도 카운트·무진전 감지·전역 예산 집행, 런타임 상태 위치/스키마)은 W-47이 필요할 때 정의한다(AHA).

## Reason

에스컬레이션 출구와 한계 값은 루프 없이도 정의·검증 가능한 독립 primitive다. 실제 감지·카운트·집행은 루프 안에서만 의미가 있어 드라이버로 미룬다(SoC/AHA). `blocked` 불변식으로 상한을 "완료"로 위장하는 것을 금지한다(Fail Fast). 이는 세 통제 장치 중 "에스컬레이션"의 출구·설정 부분을 구현한다.

## Follow-up

- 런타임 상태(시도 카운트·진행 지문)의 위치는 W-47에서 `.runtime/`로 정의.
- 무진전 판정의 동일성 기준(diff 해시 등)과 token 예산 포함 여부는 W-47/후속.
- `blocked` 항목의 사람 개입 후 재개 프로토콜.

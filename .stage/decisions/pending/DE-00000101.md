# DE-00000101 닫기 판정을 누가 하고, 실행을 어떻게 강제하고, 사람의 판정과 어떻게 맞춰 보는가

## Question

M-00000006 의 (다)에서 닫기 리뷰가 실제로 실행해 보고 회의적으로 판정하게 하려면 무엇을 고르는가?
선택지마다의 근거와 반대 관점은
[설계안](../../research/review-judgment/design.md), 세어 본 수치는 [근거](../../research/review-judgment/evidence.md) 에 있다.

큰 것부터 차례로 세 가지를 묻는다. 뒤의 질문은 앞의 답에 따라 뜻이 달라지지 않게 적었다.

1. 판정자를 누구로 두는가? 지금은 닫기 리뷰(모든 카드)와 검증 세션(에픽만, 2026-11-22 의 임시 규칙) 둘이다.
2. 리뷰어가 실행했다는 것을 어떻게 강제하는가?
3. 리뷰어의 판정을 사람의 판정과 어떻게 맞춰 보는가?

## Options

질문 1. 판정자

| 선택지 | 내용 |
|---|---|
| 1-가 | 닫기 리뷰 하나. 리뷰어의 실행 권한을 넓히고 검증 세션은 닫기의 관문에서 뺀다. 세션에서만 볼 수 있는 기준은 검증 세션이 해 보고 기록으로 남기면 닫기 리뷰가 읽는다. |
| 1-나 | 검증 세션 하나. `close_work.py` 가 검증 세션의 판정을 받아들이고 닫기 리뷰 명령은 돌리지 않는다(O-00000061 의 후보). |
| 1-다 | 카드마다 한 번만 판정하고 띄우는 길은 둘. 검증 세션을 띄운 카드는 그 판정을 가져오고 나머지는 닫기 리뷰를 돌린다. |
| 1-라 | 지금대로. 닫기 리뷰는 모든 카드, 검증 세션은 에픽에 더한다. |

질문 2. 실행의 강제

| 선택지 | 내용 |
|---|---|
| 2-가 | 판정 파일에 기준마다 판정 방법(실행함, 기록을 읽음, 판정할 수 없었음)을 적고, 실행이 필요한데 실행하지 못했으면 닫기가 실패한다. 자기 보고다. |
| 2-나 | 리뷰어의 도구 호출 기록에서 검사 명령이 실행됐는지를 닫는 쪽이 확인한다. venue 마다 읽는 코드가 따로 든다. |
| 2-다 | 카드의 검사는 지금처럼 닫기가 실행하고, 리뷰어는 실행이 필요한 기준마다 스스로 고른 명령을 실행해 본 것을 적는다. 마일스톤 완료 기준의 글자("카드의 검사를 직접 실행")와 다르다. |

질문 3. 사람의 판정과 맞춰 보기

| 선택지 | 내용 |
|---|---|
| 3-가 | 결함이 있었다고 기록된 과거 변경과 통과한 최종판을 리뷰어에게 주고 판정을 기록과 견준다. 사용자의 시간을 쓰지 않는다. |
| 3-나 | 사용자가 닫힌 카드 5장을 리뷰어의 판정을 보기 전에 기준마다 판정하고, 어긋난 기준을 기록한다. |
| 3-다 | 통과한 카드를 나중에 고치는 카드가 생기면 연결해 두고 뒤집힌 판정의 비율을 센다. |

작업 세션의 추천: 1-가, 2-가와 2-다를 함께, 3-가를 먼저 하고 3-나를 한 번.

## Principles applied

- SSOT — 판정 계약(판정 파일)은 하나로 두고, 누가 판정하든 그 계약으로 쓴다.
- KISS — 확인된 구멍(리뷰어의 실행 권한)을 메우는 데 필요한 것만 더하고, 하중을 재지 않은 장치는 더하지 않는다(M-00000006).
- Fail Fast — 실행하지 못한 판정은 통과가 아니라 실패로 끝난다(R-00000088 과 같은 방향).
- Honesty — 리뷰어가 무엇을 실행했는지가 커밋되는 기록에 남아 나중에 셀 수 있다.

## Chosen direction

고른 쪽: 메인 세션(session_018VXR6RJwybKUJRATYqvEuM)이 사용자의 위임 아래 2026-11-23 에 골랐다. 사용자가 그날 메인 세션에
남은 일 전부를 두고 한 말은 "이런거 묻지말고 물어보고 정지하지 말고 그냥 하라고"이다. 사용자가 선택지를 하나씩 보고 고른 것이 아니다.
작업 세션은 그 말을 메인 세션의 메시지로 전해 받았고 사용자의 대화에서 직접 확인하지 않았다.

| 질문 | 고른 것 |
|---|---|
| 1. 판정자 | 1-가. 닫기 리뷰 하나로 두고 리뷰어의 실행 권한을 넓힌다. 검증 세션은 닫기의 관문에서 뺀다. 세션에서만 볼 수 있는 기준이 있을 때만 검증 세션을 띄우고, 그 관찰은 카드의 `## Verification` 에 남겨 닫기 리뷰가 읽는다. |
| 2. 실행의 강제 | 2-가와 2-다. 판정 파일에 기준마다 판정 방법을 적고, 실행이 필요한데 실행하지 못했으면 닫기가 실패한다. 카드의 검사는 지금처럼 닫기가 실행하고, 리뷰어는 실행이 필요한 기준마다 스스로 고른 명령을 실행한다. |
| 3. 사람의 판정과 맞춰 보기 | 3-가만. 결함이 기록된 과거 변경과 통과한 최종판으로 잰다. |

- M-00000006 완료 기준의 "카드의 검사를 직접 실행"은 "실행이 필요한 기준을 직접 실행해서 판정"으로 읽는다. 이 읽기는 위임 아래
  정한 것이고 사용자가 그 문장을 보고 고른 것이 아니다.
- 3-나(사용자가 닫힌 카드 5장을 리뷰어의 판정을 보지 않고 판정)는 고르지 않았다. 사용자 자신의 시간이 드는 일이라 위임으로 정할 수
  없다. 사용자가 나중에 하기로 하면 할 수 있게 남긴다. 그때까지 M-00000006 완료 기준의 "사람의 판정"은 사람이 남긴 과거 기록으로
  채워지며, 글자 그대로의 대조는 없다.
- 3-다(닫은 뒤에 뒤집힌 판정 세기)는 고르지 않았다. W-00000405 가 남기는 기록에 얹을 수 있을 때 다시 본다.

## Reason

저장소에서 확인된 구멍은 리뷰어가 실행할 수 없다는 것이다. 리뷰어가 기록된 닫기 리뷰 36장 중 34장은 닫을 때 `audit_stage.py` 를
돌렸는데 대역 리뷰어는 `python3 -m unittest` 만 실행할 수 있고, 2026-11-23 에 같은 권한으로 시켜 보니 거부됐다. 1-가는 이것을 새 길을
만들지 않고 메우며 판정 파일을 리뷰어가 직접 쓴다. 2-가는 지금 문장에 묻힌 실행 여부를 기계가 읽는 칸으로 올린다. 같은 트리에서
같은 검사를 다시 실행해 얻는 것이 없어서 리뷰어에게는 자신의 탐침을 요구한다(2-다). 3-가는 사용자의 시간을 쓰지 않고, 권한과
지시문을 바꾸기 전과 후를 견줄 수 있다.

알고 고른 약점:

- 넓힌 권한의 리뷰어가 밀어 올리거나 저장소 밖을 바꿔도 지금의 앞뒤 비교(`reject_review_writes`)는 저장소 파일만 본다.
- 2-가는 자기 보고다. 실행했다고 적고 실행하지 않은 리뷰어를 잡지 못하고, 어느 기준이 실행을 요구하는지도 리뷰어가 정한다.
- 3-가의 정답은 사람의 판정이 아니라 과거의 기록이다. 쓸 수 있는 변경이 몇 건인지 아직 세지 않았고, 같은 모델이 찾은 결함은
  같은 모델이 다시 찾기 쉬워 수치가 좋게 나올 수 있다.
- 검증 세션이 닫기 리뷰보다 잘 판정하는지는 잰 적이 없다. 재지 않고 관문에서 뺐다.
- 대역 리뷰와 검증 세션의 비용은 기록에 없어 비용으로 견주지 못했다.

이 결정이 틀렸다고 볼 일: 3-가의 재기에서 권한을 넓힌 닫기 리뷰가 통과시킨 결함 있는 변경을 검증 세션은 떨어뜨린다(그러면 1-다로
옮긴다). 넓힌 권한의 리뷰어가 저장소 밖을 바꾸거나 밀어 올린 일이 한 번이라도 관찰된다. 리뷰어가 실행했다고 적은 명령으로는 볼 수 없는
것을 보았다고 한 판정이 나온다(그러면 2-나를 더한다). 결함이 기록된 변경이 다섯 건에 못 미친다(그러면 3-가는 수치가 아니라 사례
기록이고 3-나가 필요하다).

## Follow-up

- M-00000006 의 완료 기준 문장("닫기 리뷰어가 카드의 검사를 직접 실행하지 못하면")을 위의 읽기에 맞게 고칠지 사용자에게 보인다.
- 3-나를 할지는 사용자가 정한다.
- `stage-orchestrate` 의 임시 규칙(검증 세션은 에픽에만)을 1-가에 맞게 바꾼다.
- 고른 선택지를 만드는 구현 카드는 오케스트레이터가 등록한다.

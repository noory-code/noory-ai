# DE-00000001 Plainly configuration location and scope

## Question

Should Plainly persist user-global settings, shared `.noory/` settings, or project-owned settings?

## Options

- Keep user and project settings under `.noory/plainly/`.
- Keep a user-global configuration under the home directory and synchronize it separately.
- Persist only project configuration under `<project>/.plainly/` and commit it with the project.

## Principles applied

- SSOT: one persisted settings location owns the project's Plainly behavior.
- Honesty: the same checked-out project should expose the same communication policy on each PC.
- KISS: remove saved scope precedence instead of maintaining global and project copies.
- Fail Fast: confine project style paths to the project root and surface invalid configuration.
- Portability: relative paths in a committed `.plainly/` directory work across hosts and OSes.

## Chosen direction

Persist Plainly configuration only at `<project>/.plainly/settings.json`. Store project-owned custom
style files in the same `.plainly/` directory and reference them with project-relative paths.
Environment variables remain temporary runtime overrides; absence of project settings falls back to
the built-in default. Existing `.noory/` files are ignored and not automatically deleted.

## Reason

The user works on the same repositories across multiple PCs and wants the communication policy to
travel with each repository rather than with one machine's home directory.

## Follow-up

- Document `.plainly/` as trusted, model-visible project configuration that should be reviewed in
  version control.
- Retrospect on whether any legitimate user-global use case remains after project-only operation.

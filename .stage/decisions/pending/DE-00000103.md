# DE-00000103 사용자는 PO 세션하고만 이야기하고, 하위 세션은 PM, 서브에이전트는 전문가다

## Question

DE-00000099 는 오케스트레이터 아래에 토론, 계획, 작업, 검증 세션을 두었다. 토론 세션과 계획 세션은 사용자와 직접 이야기한다.
2026-11-25 에 사용자가 토론 세션과 지휘 세션을 오가며 답해야 했고 이렇게 물었다: "근데 니가 오케스트레이터인데 왜 내가 하위
세션에 가서 답변을 줘야하지?", "토론 세션 없앨까? 너무 왔다 갔다 하네..". 같은 날 지휘 세션은 사용자가 하위 세션에서 한 답
세 건을 세션의 메시지로만 받았다(R-00000419).

세션의 자리와 이름을 어떻게 두는가?

## Options

| 질문 | 선택지 |
|---|---|
| 사용자와 누가 이야기하는가 | 지금대로 지휘, 토론, 계획 세션 / 최상위 세션 하나만 |
| 하위 세션을 무엇으로 나누는가 | 직능(개발, 디자인, 기획 매니저) / 카드 한 장을 맡는 PM |
| 규칙 후보 모으기 | 따로 둔 역할(consolidation) / Research 세션에 주는 과제 |
| 검토 세션과 닫기 리뷰 | 따로 둔다 / 검토 세션이 닫기 리뷰까지 맡는다 |
| 실행 세션의 역할 이름 | `work` 를 둔다 / `pm` 으로 바꾼다 |

## Principles applied

- User intent: 구조와 이름을 사용자가 냈다.
- SSOT: 사용자의 말이 한 세션에서만 나온다.
- SoC: 세션은 흐름에서 맡은 자리로, 서브에이전트는 직업으로 나눈다.
- KISS: 역할 둘(discussion, consolidation)을 없앤다. 번호를 붙인 세션 이름을 두지 않는다.
- AHA: 전문가별 읽을거리와 점검 기준은 필요가 드러나기 전에 만들지 않는다.

## Chosen direction

사용자가 2026-11-25 에 지휘 세션 session_018VXR6NxmjDnZJNGb3TZWco 의 대화에서 정했다.

| 층 | 이름 | 하는 일 |
|---|---|---|
| 최상위 세션 | PO (Product Owner), 역할 이름 `po` | 사용자와 이야기한다. 일감을 등록하고 순서를 정한다. 결과를 받아 닫고 병합한다 |
| 하위 세션 | PM (Project Manager) | 카드 한 장을 맡아 조각내고, 전문가에게 맡기고, 검수한다 |
| 서브에이전트 | 전문가 | 조각 하나를 한다 |

하위 세션의 자리는 넷이다.

| 자리 | 역할 이름 | 하는 일 |
|---|---|---|
| 계획 | `plan` | PO 가 대화를 갈무리해 넘긴 것을 정리해 일감 초안을 쓴다. 등록은 PO 가 한다 |
| 실행 | `pm` | 카드 한 장. 여럿이 동시에 뜬다 |
| 검토 | `verify` | 세션 전체가 해 봐야 보이는 성공 기준을 관찰한다. 닫기의 관문은 닫기 리뷰 하나다(DE-00000101 그대로) |
| 리서치 | `research` | 대화 중에 생긴 조사를 하고 선택지와 근거를 돌려준다. 정하지 않는다. 거창한 연구가 아니다 |

사용자의 말:

- 누구와 이야기하는가: "난 너랑 이야기하고 토론은 없애고", "난 너랑 이야기 하면서 생기는 조사는 리서치가 하고 너랑 이야기 갈무리 하고
  정리한거 계획에 던지면 거기서 정리해서 일감 만들고 실행은 그 일감으로 일하고 검증은 검증하고"
- 층: "각 서브세션들은 하위에 서브에이전트들을 띄우죠? 이 서브에이전트들을 전문가여야하구요.", "개발 매니저가 아닐수 있네 PM 에
  가깞겠다. 서브 세션들은.", "총괄 세션을 PO 프로덕 오너 로 두고 하위 세션을 PM 프로젝트 매니저로하고"
- 자리: "계획서브세션 / 실행 서브세션1 / 실행 서브세션2 / 실행 서브세션3 / 검토 서브세션 / 리서치 서브세션", "최상위에 PO 오키?"
- 리서치: "연구라고 하면 거창한게 아니야."
- 이름: "뭐라 불리는건 상관안해요. 니가 알아서 할거지만 근데 네이밍 룰은 좀 정하자구요. 세션들 하고 서브에이전트들도"

### 네이밍 룰

지휘 세션이 냈고 사용자가 받았다("아하 ㅇㅋㅇㅋ").

```yaml
principles:
  - 세션은 흐름에서 맡은 자리로 부르고, 서브에이전트는 직업으로 부른다
  - 번호를 이름에 넣지 않는다. 맡은 카드 번호가 실행 세션을 구분한다
  - 기계가 읽는 이름은 영어 소문자 한 단어, 사람이 읽는 제목은 .stage 의 언어
session_title:
  po: "PO <프로젝트>"
  plan: "Plan <주제>"
  pm: "PM <카드 번호> <짧은 제목>"
  verify: "Verify <카드 번호> <짧은 제목>"
  research: "Research <질문>"
session_tags:
  - "stage-project:<저장소>"
  - "stage-role:<역할 이름>"
  - "stage-po:<PO 세션 id>"   # 하위 세션에만
subagent:
  name: 직업 명사 하나 (developer, designer, planner, writer, tester)
  run_description: "<직업> <카드 번호> <조각>"
  list: 미리 다 만들지 않는다. PM 이 실제로 부른 것만 생긴다
```

### 지휘 세션이 권했고 사용자가 받은 것

사용자가 2026-11-25 에 "왠만하면 니 추천을 따를 테니까 쭉쭉 진행해라"라고 했고, 아래는 장단 비교를 본 뒤 "네 추천대로"라고
답했다. 사용자가 보고 뒤집을 수 있다.

- 일감 등록은 PO 가 한다. 계획 세션은 초안을 쓴다. 클라우드 세션은 기록 번호를 원격에 잡지 못해 번호가 겹친 적이 있다
  (DE-00000094, W-00000407 과 W-00000408).
- 사용자가 제품의 주인이고 PO 세션은 그 대리다. 목적과 성공 기준은 사용자의 말에서만 온다.
- PM 은 여러 조각으로 나뉘는 카드를 전문가에게 맡기고 검수한다. 작은 카드는 직접 한다.
- 규칙 후보 모으기는 Research 세션에 주는 과제가 된다. 그 과제일 때만 목록 파일 하나를 쓴다.
- 검토 세션과 닫기 리뷰는 따로 둔다.
- 실행 세션의 역할 이름을 `work` 에서 `pm` 으로 바꾼다. 새 PO 는 옛 태그(`stage-orchestrator`, `stage-main-session:<id>`)를 단
  세션도 인수 목록에서 찾는다.
- `stage-orchestrate` 스킬의 이름은 바꾸지 않는다. 사용자가 치는 명령이라 따로 정할 일이다.

## Where this applies

`grep -rln "stage-orchestrator\|stage-main-session\|consolidation\|discussion\|--role\|orchestrat" stage` 로 셌다.

| 자리 | 지금 말하는 것 |
|---|---|
| `stage/skills/stage-orchestrate/SKILL.md` | 역할 표, 인수 절차의 태그, 브리핑 표, 세션 제목, 토론·계획·검증·consolidation 절 |
| `stage/scripts/subsession_brief.py` | `--role` 의 값(work, verify, discussion, planning, consolidation)과 역할마다의 브리핑 글 |
| `stage/scripts/started_cards.py` | 세션 태그와 지휘 세션을 가리키는 설명 |
| `stage/operations/cloud-execution.md`, `review.md`, `retrospective.md` | main session, work session, verification session 이라는 이름 |
| `stage/skills/stage-retrospective/SKILL.md`, `rule-promotion.md` | consolidation 세션이 목록을 쓴다는 문장 |
| `stage/skills/stage-handoff/SKILL.md`, `stage-drive/SKILL.md`, `stage-discuss/SKILL.md`, `stage/skills/README.md` | 오케스트레이터와 세션 역할을 가리키는 문장 |
| `stage/hooks/stage_memory_index.py` | 세션 색인이 consolidation 이 필요하다고 알리는 줄 |
| `stage/docs/BLUEPRINT.md`, `stage/README.md` | 역할의 설명 |
| 시험: `stage/scripts/tests/test_orchestrate_skill.py`, `test_subsession_brief.py`, `test_started_cards.py`, `stage/hooks/tests/test_session_index.py` | 위 글과 값을 고정한다 |
| 플랫폼의 세션 목록 | 이미 떠 있거나 보관된 세션은 옛 태그와 옛 제목을 달고 있다 |

`stage/templates/**/principles.md` 의 discussion 은 세션 역할이 아니라 원칙의 글이다. 해당 없음.

## Reason

DE-00000099 가 역할을 나눈 까닭은 지휘 세션의 맥락 비용이었다. 그 비용을 사용자가 창을 오가는 것으로 치렀고, 사용자의 말이
세션마다 흩어져 지휘 세션이 무엇이 정해졌는지 몰랐다. 대화를 한 곳에 두고 읽기와 정리만 하위 세션에 맡기면 맥락 비용의
대부분은 그대로 아끼고 사용자의 말은 한 곳에서 나온다.

알고 고른 약점:

- 대화가 전부 PO 세션에 쌓여 맥락이 더 빨리 찬다. 인수인계가 잦아진다.
- 계획 세션은 대화를 보지 못하고 PO 의 갈무리만 본다. 잘못 옮기면 그대로 일감이 된다. 갈무리에 사용자의 말을 원문으로 싣는다.
- 같은 모델에 직업 이름만 붙여서는 결과가 달라진다는 근거가 없다. 전문가의 실체는 읽을거리와 점검 기준인데 이번에는 만들지
  않는다.
- PM 이 검수만 하면 검수의 질은 조각의 완료 조건을 얼마나 분명히 적었느냐에 달린다.
- Research 가 "쓰지 않는다"에서 예외 하나(규칙 후보 목록)를 갖는다.

이 결정이 틀렸다고 볼 일: PO 세션이 맥락이 차서 카드 한두 장마다 인수인계해야 한다. 또는 계획 세션이 쓴 일감 초안의 목적이
사용자의 말과 달라서 등록 전에 되돌리는 일이 되풀이된다. 또는 사용자가 다시 하위 세션에 가서 답해야 하는 일이 생긴다.

선택지를 돌려 본 것: 2026-11-25 에 토론 세션 하나를 뒤쪽 절반은 Research 처럼 썼다. 질문과 선택지를 지휘 세션에 보내게 하고
지휘 세션이 사용자에게 물었다. 그 사이에도 사용자가 토론 세션에 직접 답한 일이 한 번 있었다.

## Follow-up

- W-00000420 이 "Where this applies" 의 자리를 고친다.
- DE-00000099 의 역할 표는 이 결정이 바꾼다. DE-00000099 의 다른 선택(오케스트레이터가 닫고 병합한다, 지휘 상태 파일을 두지
  않는다)은 그대로다.
- 전문가별 읽을거리와 점검 기준은 PM 방식으로 카드를 몇 장 해 본 뒤에 본다.
- `stage-orchestrate` 스킬의 이름을 바꿀지는 정하지 않았다.

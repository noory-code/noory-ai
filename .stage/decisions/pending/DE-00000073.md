# DE-00000073 플레인리를 훅에서 클로드 코드 output style 로 옮긴다

## Question

플레인리는 매 사용자 프롬프트마다 훅으로 스타일 글을 덧붙인다. 이 글을 클로드 코드의 output
style 로 옮길 때, 스타일 파일을 어디에 두고, 모든 스타일이 함께 지고 다니는 고정 규칙을 어디서
한 번만 쓰고, 훅과 그에 딸린 코드를 어디까지 지우고, 사람이 스타일을 고른 결과를 어디에 적을
것인가?

## Options

- **A. 훅을 그대로 두고 output style 을 더한다.** 두 경로가 같은 글을 한 턴에 두 번 넣는다.
  훅이 스스로 물러나는 조건을 코드로 판단해야 하는데, 훅이 받는 입력에 어떤 output style 이
  켜져 있는지가 들어오는지 확인되지 않았다. 판단 근거가 없으면 중복을 못 막는다.
- **B. 훅을 지우고 output style 만 남긴다.** 스타일을 고르는 일도 매 턴 넣는 일도 클로드 코드가
  한다. 플레인리는 마크다운 파일 묶음이 된다. 코덱스에서는 플레인리가 사라진다.
- **C. `force-for-plugin` 으로 스타일 하나를 강제한다.** 사람이 안 골라도 켜진다. 대신 한
  세션에 하나만 먹으므로 다섯 가지 중 고르는 기능이 죽는다. 이 키는 클로드 코드 안에서
  `@internal` 로 표시되어 있다.

## Principles applied

- **SSOT** — 고정 규칙은 한 곳에서 쓰고, 다섯 개 스타일 파일은 거기서 만든다. 손으로 다섯 번
  베끼면 소유자가 다섯이 된다.
- **SoC** — 스타일을 고르는 일은 호스트가 이미 한다. 플레인리는 스타일 본문만 소유한다.
- **Fail Fast** — 스타일 파일이 잘못되면 클로드 코드가 조용히 건너뛴다. 테스트가 먼저 잡는다.
- **Honesty** — 코덱스에서 안 돌면 코덱스 매니페스트를 지운다. 목록에 남겨 두고 아무 일도 안
  하면 거짓말이 된다.
- **User intent** — 사용자가 코덱스에서는 플레인리를 안 쓴다고 밝혔다. 코덱스를 지키느라 훅을
  남길 이유가 없다.

## Chosen direction

B 를 고른다. C 는 고르는 기능을 죽이고 문서에 없는 내부 키에 제품을 얹는다. A 는 중복을 막을
근거가 없다.

### 스타일 파일의 자리

`plainly/output-styles/` 아래에 다섯 개를 둔다. 플러그인 폴더에 이 이름의 폴더가 있으면 클로드
코드가 매니페스트에 아무것도 안 적어도 읽는다. 목록에는 `plainly:<파일이름>` 으로 뜬다.

파일 앞머리에 `name`, `description`, `keep-coding-instructions: true` 를 적는다. 마지막 키를
빠뜨리면 클로드 코드가 기본 코딩 지침을 시스템 프롬프트에서 빼 버린다. 플레인리는 문장이
읽히는 방식만 다루므로 코딩 지침을 밀어낼 이유가 없다.

`force-for-plugin` 은 안 쓴다.

### 고정 규칙을 한 번만 쓰는 방법

`plainly/styles/` 가 원본을 소유한다. 스타일 본문 다섯 개와 고정 규칙 한 개를 둔다.
`plainly/scripts/build_styles.py` 가 둘을 붙여 `plainly/output-styles/*.md` 를 만들고, 만든
파일을 커밋한다.

클로드 코드는 정적 파일만 읽으므로 실행하는 순간에 둘을 붙일 수 없다. 그래서 만든 결과를
저장소에 담는다. 테스트가 다시 만들어서 커밋된 것과 비교하고, 다르면 깨진다.

### 지우는 것

훅(`hooks/`), 스타일을 고르던 코드(`src/plainly/`), 스타일을 골라 적던 CLI(`scripts/configure.py`),
그 CLI 를 부르던 스킬(`skills/plainly-configure/`), 코덱스 매니페스트(`.codex-plugin/`).

### 버리는 플러그인으로 돌려 보니 앞머리 오타가 조용히 넘어간다

`--plugin-dir` 로 버리는 플러그인을 한 세션만 붙이고 `--settings` 로 스타일을 골라 실제로
돌렸다. 스타일 세 개를 넣었고 그중 하나는 `keep-coding-instructions` 를
`keep-coding-instruction` 으로 잘못 적었다.

| 넣은 것 | 나온 것 |
|---|---|
| 앞머리가 올바른 스타일 두 개 | `Loaded 2 output styles from plugin testplug default directory` |
| 앞머리에 오타 키를 담은 스타일을 더한 세 개 | `Loaded 3 output styles from plugin testplug default directory` |
| `--settings` 로 고른 스타일 | 스타일 본문에 심어 둔 표시가 답 첫 줄에 나왔다 |
| 세션에게 시스템 프롬프트 목차를 물음 | `Output Style: testplug:Probe Keep` 절이 목차에 있었다 |

오타를 담은 파일도 그대로 읽힌다. 클로드 코드는 모르는 키를 버리고 나머지를 쓴다. 그래서
`keep-coding-instructions` 를 잘못 적으면 스타일은 멀쩡히 켜지고 코딩 지침만 사라진다. 사람도
로그도 아무 말을 안 한다. 테스트는 "파일이 로드되는가"가 아니라 "키 이름이 글자 그대로
맞는가"를 봐야 한다.

`-p` 세션에는 코딩 지침 덩어리가 아예 없다. 스타일을 안 켠 기본 세션에서도 없었다. 그래서 이
키의 효과 자체는 이 방법으로 못 가른다.

### 사람이 고른 결과가 앉는 곳

클로드 코드의 `outputStyle` 설정이 소유한다. `/output-style` 로 고르거나
`.claude/settings.json` 에 직접 적는다. 플레인리는 이 값을 읽지도 쓰지도 않는다.
`.plainly/settings.json` 과 `NOORY_STYLE_PROFILE`·`NOORY_STYLE_FILE` 환경변수는 없어진다.

게이트는 없다. 플레인리의 `hooks.json` 에는 `UserPromptSubmit` 와 압축 후 `SessionStart` 둘뿐이고
둘 다 이번에 없어진다. 무엇을 막거나 허용하던 자리가 아니다.

## Reason

훅은 사용자 메시지 뒤에 글을 덧댄다. output style 은 시스템 프롬프트에 들어가고, 클로드 코드가
매 턴 "이 스타일이 켜져 있다"고 스스로 짚어 준다. 같은 글이라도 걸리는 힘이 다르다.

플레인리가 하던 일 가운데 스타일을 고르는 일과 매 턴 넣는 일은 호스트가 이미 한다. 플레인리가
따로 가질 이유가 없다. 지금 코드 약 700줄과 테스트 1160줄이 마크다운 다섯 개와 그 파일들이
원본과 어긋나지 않는지 보는 테스트로 줄어든다.

이 결정을 뒤집는 관측: 클로드 코드가 플러그인의 `output-styles/` 를 안 읽거나,
`keep-coding-instructions: true` 를 적었는데도 기본 코딩 지침이 사라지면 이 결정은 무너진다.

## Follow-up

- 진 쪽을 한 번 만들어 보는 절차는 적용하지 않았다. 두 갈래의 차이를 보려면 플러그인을
  릴리스해서 실제로 불러와야 하는데, 그게 바로 이 결정이 시키는 일이다. 버리는 시도가 될 수
  없다. 대신 규격은 설치된 클로드 코드 2.1.260 실행 파일에서 읽어 확인했다 — `output-styles/`
  폴더를 자동으로 읽는 경로, 앞머리 네 키의 스키마, `keep-coding-instructions` 가 참일 때만
  기본 코딩 지침을 남기는 조립 코드, 여러 플러그인이 `force-for-plugin` 을 켰을 때 첫 하나만
  쓰고 경고하는 경로.
- 실제로 도는지는 W-00000267 에서 본다. 릴리스하고 새 세션에서 스타일이 목록에 뜨는지, 골랐을
  때 문장이 달라지는지, 코딩 지침이 남아 있는지 확인한다.
- 코덱스에서 플레인리가 사라진다. 나중에 코덱스에도 스타일을 주려면 별도 카드로 다시 연다.

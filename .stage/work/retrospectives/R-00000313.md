# R-00000313 rag 서버에 ruff·mypy 를 들이고 지적을 정리한다

## Work

W-00000313. rag 서버의 dev 의존성에 ruff·mypy 를 넣고 evonest 와 같은 설정을 두었다. ruff 지적 22개와 mypy strict
오류 11개를 동작을 바꾸지 않고 정리했다.
외부 결과: rag 를 목적별 여러 검색 스타일로 넓히는 일을, 저장소 관례대로 깨끗한 바닥에서 시작할 수 있다.
내부 결과: rag 안에서 `uv run ruff check`, `uv run mypy src/` 가 오류 없이 끝나고, slow 를 뺀 시험 121개가 통과한다.

## Decision points

- 새 규칙을 만들지 않고 이미 깨끗한 evonest 설정을 그대로 따랐다.
- pydantic 의 `default_factory` 오류는 코드를 고치지 않고 pydantic mypy 플러그인으로 풀었다.
- 새 uv 가 `cuda-toolkit` extras 의 플랫폼 표시를 지운 줄 10개를 되돌려, lock 변경을 새 도구 추가로만 남겼다.
- `ruff format` 은 하지 않았다. 스타일만 바뀌는 17개 파일이 리뷰를 흐린다.

## Principles applied

Honesty: slow 시험 13개는 모델 내려받기가 이 환경의 프록시에 막혀 돌리지 못했다. 그 경로에서 바꾼 `encode_query` 는
가짜 모델로 따로 확인했고, 돌리지 못한 사실을 하지 않은 일로 적었다.
만든 쪽 ≠ 보는 쪽: 실행 맥락이 없는 별도 Claude 세션이 판정했다. 같은 모델 계열이라 교차 venue 판정은 아니다.

## Context that helped

- evonest 가 같은 저장소에서 ruff·mypy 관례를 이미 깨끗하게 지키고 있었다.
- uv 가 Linux 에서 캐시를 하드링크로 이어, worktree 에 5GB venv 를 하나 더 만들어도 디스크가 늘지 않았다.

## Context that was missing

- 처음 본 rag 오류(수집 실패 18개, mypy 13개)는 dev 의존성이 venv 에 없어 venv 밖 도구가 잡힌 결과였다. 플러그인
  상태를 볼 때는 그 플러그인의 venv 에 dev 의존성을 먼저 깔아야 한다.

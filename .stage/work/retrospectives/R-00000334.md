# R-00000334 세션 시작 글에 인라인 코드 규칙을 싣는다

## Work

세션 시작 글의 기본 안내에 한 줄을 넣었다. `.stage` 를 말하는 인라인 인터프리터 코드(`python -c`,
`node -e`, `bash -c`, 인터프리터 heredoc)는 거절되고, 대신 Write/Edit 나 이름 있는 스크립트 파일을
쓰라는 줄이다. 새 구조와 옛 구조 두 갈래가 같은 상수를 쓴다. 거절 조건과 거절 메시지는 건드리지
않았다. 시험 파일 하나, 문서 두 개, 변경 기록을 맞췄다.

## Decision points

- **줄을 한 자리에서 넣었다.** 두 갈래의 목록에 각각 적지 않고, 갈래가 끝난 뒤 상수 하나를
  덧붙였다. 두 갈래의 문구가 따로 어긋날 수 없다.
- **줄이 드는 예를 훅에 직접 넣어 확인했다.** 줄에 적은 네 가지 모양이 모두 거절되고, 대신 쓰라고
  한 두 가지(이름 있는 스크립트, `-m` 모듈 호출)가 통과하는 것을 시험이 본다. 안내가 실제 동작과
  어긋나면 시험이 깨진다.
- **세션 시작 글을 줄이는 일은 이 카드에서 뺐다.** 처음에는 열린 관찰 목록에 개수 상한을 두자고
  제안했다. 코드를 읽으니 `db9f74f1` 이 일부러 상한을 없앴다. 상한이 있을 때 열린 관찰 17건 중
  6건이 세션에 실리지 않았다. 제안을 거두고 사용자에게 알렸다.
- **감독 세션이 직접 실행했다.** claude venue 절차는 팀원에게 맡기라고 한다. 이 세션에는 팀
  기능이 없고 변경이 열두 줄이라 직접 했다. 만든 쪽과 보는 쪽은 닫기 리뷰(Claude 대역)와 사용자
  확인(DE-00000087)으로 갈랐다.

## Principles applied

- Fail Fast — 깨지는 시험을 먼저 쓰고 세 개가 깨지는 것을 본 뒤에 고쳤다.
- SSOT — 규칙 문구를 상수 하나에 두고 두 갈래가 함께 쓴다.
- Honesty — 거절 횟수가 줄었는지는 재지 못했다고 카드에 적었다. 처음 제안의 절감 추정
  (1,500~2,500자)이 재 보지 않은 숫자였다는 것도 사용자에게 고쳐 말했다.
- Completion — 코드만 고치지 않고 그 규칙을 설명하는 두 문서를 함께 맞췄다.
  `stage/operations/hooks.md` 는 "아래에서 다룬다"고 해 놓고 막는 행동 목록에 이 규칙이 없었다.

## Context that helped

- 세션 기록 50개에서 센 숫자. Stage 훅이 낸 거절 115번 중 67번이 이 규칙이었다. 어느 거절을 먼저
  다룰지 숫자가 정해 줬다.
- `open_observation_lines` 의 주석과 `db9f74f1` 의 커밋 메시지. 왜 상한이 없는지가 코드 옆에 적혀
  있어 잘못된 제안을 카드로 만들기 전에 거둘 수 있었다.

## Context that was missing

- 하위 에이전트와 드라이버 실행자가 세션 시작 글을 받는지. 받지 않으면 그쪽에서 나는 거절은 이
  줄로 줄지 않는다. 67번 가운데 몇 번이 그쪽에서 났는지도 세지 않았다.
- 긴 세션이 요약된 뒤 이 줄이 남는지. 남지 않으면 요약 뒤의 거절은 그대로다.

## Rule candidate

세션 시작 글의 크기만 보고 상한을 제안했다가, 상한을 없앤 결정을 뒤늦게 읽었다. 하루 전 릴리스
카드(W-00000333)에서도 플러그인이 어디서 읽히는지 확인하기 전에 완료 기준을 적었다. 기존 규칙
("관찰을 카드로 만들기 전에 전제를 돌려 본다", `stage-work`)이 다루는 자리와 가깝다. 새 규칙을
더하기보다 그 규칙에 "측정에서 나온 제안"을 보태는 쪽이 맞는지 볼 일이다.

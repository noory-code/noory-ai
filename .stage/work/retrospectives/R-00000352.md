# R-00000352 자식 프로세스 출력을 로캘 인코딩이 아니라 UTF-8 로 읽기

## Work

플러그인 코드에서 `text=True` 로 자식 프로세스를 띄우는 18곳에 `encoding="utf-8", errors="replace"` 를 줬다.
AST 로 플러그인 코드를 훑어 빠진 호출을 잡는 테스트와, 기본 인코딩을 cp949 로 바꿔 둔 채 close_work 의
`run_check` 가 UTF-8 한국어 출력을 지키는지 보는 테스트를 붙였다.

## Decision points

- 고칠 범위: 보고된 close_work 한 곳이 아니라 텍스트 모드 호출 전부를 고쳤다. 같은 원인이고, 가드 테스트가
  한 곳만 고치면 실패하기 때문이다.
- `errors="replace"`: 읽지 못하는 바이트가 있어도 출력을 잃지 않는 쪽을 골랐다. 검사 출력은 사람이 읽는
  증거라서, 글자 하나가 깨지는 것이 출력 전체를 잃는 것보다 낫다.
- macOS 에서 같은 상황을 만드는 방법: 자식의 `PYTHONIOENCODING` 이 아니라 부모가 기본 인코딩을 묻는 자리
  (`subprocess._text_encoding`, 3.9·3.10 은 `locale.getpreferredencoding`)를 바꿔 끼웠다. 버그는 부모가
  읽는 쪽에 있기 때문이다. 같은 조건에서 인코딩을 주지 않은 호출은 출력을 잃는다는 대조 테스트도 뒀다.
- 테스트 코드 안의 `text=True` 31개 파일은 고치지 않았다. 이 카드 범위가 플러그인 코드다.

## Principles applied

- Fail Fast: 새 호출이 인코딩을 빼면 테스트가 바로 실패한다.
- 고치기 전 코드에서 새 테스트가 실패하는지 확인했다. 가드는 18곳을 잡았고 close_work 테스트는 빈 출력을 받았다.

## Context that helped

- novel-workspace 에서 실제로 난 오류 메시지(`'cp949' codec can't decode byte 0xec`, `_readerthread`)가 어느
  쪽이 읽다가 깨졌는지를 바로 알려 줬다.

## Context that was missing

- 이 저장소의 테스트를 Windows 에서 돌린 기록이 없었다. 고치기 전 상태에서도 Windows 에서 16개가 실패한다
  (`python3` 가 Store 바로가기인 것, 테스트 도우미의 같은 인코딩 문제).

## Next changes

- 테스트 도우미의 `text=True` 호출도 UTF-8 로 읽게 하면 Windows 에서 실패하는 테스트 7개(오류)가 줄어든다.
  별도 카드로 다룰 일이다.

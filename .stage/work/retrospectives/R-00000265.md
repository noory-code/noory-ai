# R-00000265 스타일을 output style 로 낼 때 무엇을 어디에 둘지 정한다

## Work

DE-00000073 을 썼다. 스타일 파일의 자리, 고정 규칙의 단일 출처, 훅을 없애는 범위, 스타일 선택을
적는 곳을 정했다. 적용 자리 열여덟 군데를 세어 표로 남겼다.

## Decision points

- 훅을 남기고 output style 을 더할지, 훅을 없앨지, `force-for-plugin` 으로 강제할지. 훅을
  없애기로 했다. 사용자가 코덱스에서 안 쓴다고 밝혀서 훅을 남길 이유가 사라졌다.
- `force-for-plugin` 을 쓸지. 안 쓰기로 했다. 한 세션에 하나만 먹어서 고르는 기능이 죽고, 그
  키는 클로드 코드 안에서 `@internal` 로 표시돼 있다.
- 고정 규칙을 다섯 파일에 어떻게 넣을지. 한 곳에서 쓰고 빌드로 붙여 커밋하기로 했다. 이 결정은
  뒤에 스타일이 하나로 줄면서 필요 없어졌다.

## Principles applied

- **SSOT** — 고정 규칙은 한 곳이 소유한다. 손으로 다섯 번 베끼면 소유자가 다섯이 된다.
- **SoC** — 스타일을 고르는 일은 호스트가 이미 한다. 플레인리는 본문만 소유한다.
- **Fail Fast** — 스타일 파일이 잘못되면 클로드 코드가 조용히 건너뛴다. 테스트가 먼저 잡는다.
- **Honesty** — 코덱스에서 안 돌면 매니페스트를 지운다. 목록에 남겨 두고 아무 일도 안 하면
  거짓말이 된다.

## Context that helped

설치된 클로드 코드 실행 파일. 규격을 추측하지 않고 읽었다 — `output-styles/` 자동 읽기, 앞머리
네 키, `keep-coding-instructions` 가 참일 때만 코딩 지침을 남기는 조립 코드.

`--plugin-dir` 과 `--settings` 와 `--debug-file`. 버리는 플러그인을 한 세션에만 붙여 실제로
돌려 볼 수 있었다. 릴리스 없이 확인하는 길이 있다는 걸 늦게 알았다.

## Context that was missing

앞머리 스키마가 `strict` 로 선언돼 있어서 모르는 키를 거부한다고 읽고 그렇게 사용자에게 말했다.
돌려 보니 아니었다. 오타 키를 담은 파일이 그대로 로드됐다. 읽기만 하고 단언했다가 틀렸다.

`claude -p` 세션에는 코딩 지침 덩어리가 아예 없다. 그래서 `keep-coding-instructions` 의 효과는
이 방법으로 못 가른다. 대화형 세션이 있어야 한다.

## Next changes

`keep-coding-instructions` 가 실제로 코딩 지침을 남기는지 대화형 세션에서 확인한다. 지금은 조립
코드를 읽은 것이 근거의 전부다.

## Rule candidate

없음. 실행 파일에서 읽은 규격을 돌려 보기 전에 단언한 일은 이번 한 번이고, 기존 Honesty 원칙이
이미 그것을 금지한다.

그 결과를 사람이 아직 실제로 판정하지 않았다.

# R-00000141 결정이 예시로 적은 파일 이름이 그 결정의 전제였다

## Work

다른 프로젝트가 설명 문서 갱신으로 데이터를 잃은 보고를 받아, 원인이 코드가 아니라
DE-00000029 의 전제임을 확인하고 DE-00000042 로 규칙을 다시 세웠다. 구현은 W-00000142, 자동
갱신을 되찾는 후속은 W-00000143 으로 분리했다.

## Decision points

**버그로 볼 것인가 결정으로 볼 것인가.** 보고는 "문서 약속과 실측이 다르다"로 왔다. 도움말만
보면 코드 결함처럼 보였다. DE-00000029 를 열어 보니 첫 갈래가 `state/current.md` 를 **이름으로**
지목해 "통째로 교체한다"고 적어 뒀다. 결정된 동작이었다. **Fail Fast** — 전제가 틀렸다는 것을
먼저 세우지 않고 코드를 고치면, 고친 코드가 공식 결정과 어긋난 채로 남는다.

**어느 축으로 소유를 판정하나.** 후보 넷을 셌다. 목록으로 선언하는 두 안(C·D)이 정확하지만,
**이번에 깨진 것이 바로 목록에 없던 자리**였다 — DE-00000029 의 예시 목록은 `state/current.md`
를 안전한 쪽에 적어 뒀다. 그래서 목록이 아니라 "템플릿으로 설명되지 않는 줄"이라는 시험을 골랐다.
**AHA** — 새 선언 축을 만들기 전에 기존 정보(템플릿 본문)로 판정되는지 먼저 봤다.

**자동 갱신이 줄어드는 것을 받을 것인가.** 이 시험은 플러그인이 설명글을 고친 파일까지 기본
실행에서 뺀다. 갱신이 두 걸음이 된다. 받았다 — DE-00000029 가 스스로 "자동화의 편의보다 데이터가
우선"이라고 적었으므로 이 저울은 이미 기울어 있었다. 대신 자동을 되찾는 길(D)을 후속 카드로
남겼다.

## Principles applied

- **Fail Fast** — 전제가 틀렸다는 판정을 코드 수정보다 먼저 세웠다.
- **AHA** — 선언 축을 새로 만들지 않았다.
- **MECE** — DE-00000029 의 세 갈래 나눔은 유효했고 첫 갈래의 내용만 좁혔다. 결정 본문에 세
  갈래 표를 넣어 두 결정을 나란히 읽는 사람이 어느 것이 참인지 고를 수 있게 했다.
- **SSOT** — 구현 카드가 설계를 다시 하지 않도록, 적용 자리 표를 결정이 쥐고 카드는 그것을
  가리킨다.

## Context that helped

- 실측 보고가 잃은 파일 목록과 복구 방법까지 담고 있었다. 그 목록이 "표 없음" 갈래와 "빈 표"
  갈래 양쪽에 걸쳐 있어서, 결함이 하나가 아니라 둘(결정의 전제 + 행 합치기 구현)이라는 것이
  드러났다.
- 이 저장소의 `guidance_overrides` 네 줄. 같은 위험을 이미 손으로 막아 둔 흔적이어서, 위험이
  이론이 아니라는 증거로 바로 썼다.

## Context that was missing

- **`decisions/index.md` 가 대기 결정 다섯 장을 안 담고 있었다.** 새 결정을 등록하며 알게 됐다.
  감사가 그 방향은 안 보므로 조용히 비어 있었다. 이 회고에서 사실만 남긴다 — 지금 고치면 카드
  범위를 벗어난다.
- 갱신 명령이 실제로 무엇을 건너뛰는지 사람이 보는 화면이 없다. `--dry-run` 이 있지만, 데이터를
  가진 파일이 몇 개인지 먼저 알려 주는 자리는 아니다. W-00000142 의 회귀 시험이 출력을 고정하면
  그때 다시 본다.

## Next changes

- 구현 카드(W-00000142)가 결정을 코드로 옮긴다. 관측 O-00000012 는 그 카드가 닫힐 때 닫는다.
- 후속 카드(W-00000143, 계획)가 쌓이는 자리를 템플릿의 빈 그릇으로 옮겨 자동 갱신을 되찾는다.
- **결정이 예시로 적은 파일 이름은 그 결정의 전제다.** DE-00000029 는 `state/current.md` 를
  "표가 없으니 플러그인 것"의 예로 들었고, 그 한 줄이 데이터 손실의 근거가 됐다. 결정에 예시를
  적을 때 그 예시가 참인지 확인하는 것이 결정 본문을 쓰는 일에 포함된다.

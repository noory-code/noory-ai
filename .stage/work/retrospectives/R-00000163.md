# R-00000163 정한 대로 쓰기 직전 훅에 싣는다

## Work

세션에서 목적과 관련된 첫 쓰기를 한 번 막고, 테마 의도·마일스톤 목적·활성 최상위 작업의 목적과
사용자 가치를 막는 이유로 돌려준다. 글은 훅 코드에 복사하지 않고 기록에서 그때 읽는다. 같은
쓰기를 다시 하면 통과하고, 표시 파일이 활성 작업 id 를 들고 있어 작업이 바뀌면 다시 뜬다.

두 바퀴 돌았다. 시험 356 + 511 전부 통과.

## Decision points

- **활성 최상위가 여럿일 때 어떻게 할 것인가.** 첫 구현은 하나일 때만 뜨고 여럿이면 조용히
  사라졌다. DE-00000050 이 이 경우를 안 정한 것은 맞지만, 조용히 사라지면 사람은 알림이 도는 줄
  알고 목적을 안 본 채 쓴다 — 이 카드가 막으려는 사고가 아무 소리 없이 나는 자리다. 전부 싣는
  쪽으로 바꿨다.
- **낡은 시험을 이 카드에서 고칠 것인가.** 고친다. 계약이 깨진 게 아니라 시험이 낡았고,
  `stage/CLAUDE.md` 가 닫을 때 두 묶음을 다 돌리라고 한다. 카드 범위를 넓혔다.
- **리뷰어 창 안의 거짓 실패 둘을 여기서 고칠 것인가.** 안 고친다. 계획 카드 W-00000157 이 이미
  맡고 있고, 실행자와 드라이버의 검사 환경에는 그 변수가 안 들어간다.

## Principles applied

- SSOT — 싣는 글은 기록에서 읽는다. 셸 감지 설명은 `hooks/README.md` 가 소유하므로
  `operations/hooks.md` 의 중복을 지웠다.
- Fail Fast — 조용히 사라지는 대신 못 쓰게 세운다.
- Honesty — 판정한 쪽이 격리 작업공간에 훅을 붙여 직접 돌려 확인했다. 코드를 읽어 통과시키지
  않았다.
- MECE — 리뷰가 짚은 것을 하나씩 처분했다. 받은 것 넷, 미룬 것 둘, 각각 이유를 적었다.

## Context that helped

- **판정하는 쪽이 실제로 돌려 봤다.** 두 바퀴 다 격리 작업공간에 훅을 붙여 첫 쓰기가 막히는
  것과 두 번째가 통과하는 것을 실측했다. 이 저장소에서 세 번째로 값을 낸 방식이다.
- **감독자가 자기 손으로 훅에 막혔다.** 카드를 고치려는 첫 쓰기가 그대로 막히고 목적이 돌아왔다.
  카드의 "사람이 겪는 결과" 기준을 시험이 아니라 실제 경험으로 확인한 자리다.
- **`question_purpose_reminder` 가 뼈대를 줬다.** 세션당 한 번 막고 목적을 돌려주는 모양이 이미
  돌고 있어서 새 장치를 안 만들었다.

## Context that was missing

- **결정이 "활성 최상위가 여럿일 때"를 안 정했다.** 설계할 때 이 저장소에 활성 카드가 하나뿐이라
  단수를 전제하고 썼다. 실행자는 그 빈칸을 "조용히 아무것도 안 함"으로 메웠다. **결정이 안 정한
  자리는 실행자가 가장 조용한 쪽으로 메운다** — 값이 정해지지 않은 경계는 결정이 직접 말해야 한다.
- **닫는 규칙과 카드의 검사 명령이 어긋나 있었다.** 카드는 훅 묶음만 저장했는데
  `stage/CLAUDE.md` 는 두 묶음을 요구한다. 첫 바퀴 판정이 짚어 줘서 알았다. 카드를 만들 때
  프로젝트의 닫기 규칙을 안 봤다.

## Next changes

- 결정을 쓸 때 "이 값이 하나가 아니면 어떻게 되나"를 한 번 묻는다. 지금 이 저장소가 하나라는
  것은 근거가 아니다.
- 카드에 검사 명령을 저장할 때 프로젝트의 닫기 규칙(`CLAUDE.md`)이 요구하는 묶음을 같이 센다.

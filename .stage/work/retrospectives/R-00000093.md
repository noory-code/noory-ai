# R-00000093 드라이버 한 바퀴를 역할 계약으로 다시 세운다

## Work

드라이버 한 바퀴가 무엇을 주고받는지 정한 문서가 없었다. 그래서 사고가 날 때마다 그 자리에서
방어를 하나씩 만들어 넣었고, 카드가 열 장 넘게 늘었다. 계약을 DE-00000034 로 확정하고 구현
카드 셋(W-00000095, 96, 97)을 뽑았다.

## Decision points

- **원래 카드를 그대로 고칠 것인가.** W-00000094 는 "리뷰어 인덱스가 비면 막는다" 는 fix 로
  시작했다. 사용자가 "일감이 계속 생기는 건 조사를 안 했거나 설계를 잘못한 것" 이라고 지적했고,
  덧대기를 멈추고 설계로 돌렸다. 카드를 폐기하지 않고 같은 번호를 설계 카드로 다시 썼다.
- **리뷰 자료를 무엇으로 줄 것인가.** 세 안을 놓고 골랐다 — 방어 덧대기(A), 드라이버가 diff 를
  떠서 넘기기(B), 카드마다 로그 파일을 두고 경로만 넘기기(C). C 를 골랐다. A 는 다음 오염
  방식이 오면 또 는다. B 는 인덱스 문제만 없애고 대용품은 그대로 두며 입력 크기 한계에 다시
  닿는다.
- **구현을 어떻게 쪼갤 것인가.** 파일 단위로 쪼개면 카드끼리 같은 파일을 물어 겹친다. 계약의
  층 단위로 쪼갰다 — 관찰이 리뷰 입력이 되는 층, 로그가 공용 기록이 되는 층, 남은 항목이 다음
  바퀴로 흐르는 층.

## Principles applied

- **MECE** — 사고 열 건이 하나의 전제에서 나왔다는 것을 확인하고, 지금까지 덧댄 방어 아홉 개가
  계약 안에서 각각 어디로 가는지(폐기/유지/흡수/경계) 대조표로 덮었다. 빠뜨리면 구현하면서
  잃는다.
- **AHA** — 로그 파일이라는 새 장치를 먼저 만들지 않고, 같은 결핍(바퀴 사이에 정보가 안 흐른다)이
  사고 여러 건에서 반복해 보인 뒤에 도입했다.
- **SSOT** — 한 바퀴의 사실이 로그 파일 하나를 소유 위치로 갖는다. 카드의 `## Progress` 와
  겹치지 않게 경계를 정하는 일을 W-00000096 의 성공 기준에 넣었다.
- **DIP** — 계약을 역할로만 썼다. 도구 이름이 계약에 들어가면 도구마다 예외가 생긴다.
- **Honesty** — 무엇이 인덱스를 비웠는지 아직 모른다. 모른다고 적고, 몰라도 상관없게 만드는
  쪽으로 설계했다.

## Context that helped

- Q-00000001 의 실측(리뷰어 입력 9,016,382 바이트, 956/962 삭제). 원인 지목이 아니라 구조
  결함의 증거로 읽혔다.
- 아카이브된 카드 서른 장의 제목. 나열해 놓고 보니 전부 같은 질문의 조각이었다.
- 사용자의 되물음. "코덱스가 어질렀나", "git diff 로 하려고 해서 그런 거 아니냐", "PR 할 때나
  diff 보지" — 셋 다 내가 검증 없이 깔고 있던 전제를 하나씩 드러냈다.

## Context that was missing

- 드라이버의 목적과 경계를 선언한 문서가 `official/canon/` 에 없다. 결정 기록 열네 건이 전부
  "무엇을 하는가" 만 정했고 "무엇을 못 믿는가" 는 아무 데도 없었다.
- 리뷰어 명령이 프로젝트 설정에만 있고 플러그인엔 없다는 사실. 확인하기 전까지 플러그인이
  기본값을 갖고 있다고 가정하고 있었다.

## Next changes

- 계약(DE-00000034)이 구현으로 실현된 뒤 `official/` 로 올린다. 지금은 결정 기록이 소유한다.
- 리뷰 자료를 만드는 방식을 바꿀 때는 먼저 "이 리뷰가 언제 하는 무엇인가" 를 묻는다. PR 리뷰
  습관을 옮기다 사고가 났다.
- 사고가 났을 때 그 자리에서 방어를 만들기 전에, 같은 자리에서 이미 몇 번 났는지 센다. 두 번째
  부터는 방어가 아니라 설계가 답이다.

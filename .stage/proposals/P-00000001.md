# P-00000001 Codex 런타임의 Stage 플러그인 버전별 캐시 무효화

## Proposal

Codex CLI(openai-codex 플러그인)가 Stage 플러그인 훅을 버전별 캐시 경로
(`~/.codex/plugins/cache/noory-ai/stage/<version>/hooks/...`)로 해석한 뒤, 마켓플레이스가
새 버전으로 동기화돼도 실행 중 세션의 해석을 갱신하지 못해, 옛 경로가 사라지면 모든
셸/패치 작업이 훅 실패로 차단되는 문제. 근본 수정은 Codex 런타임 몫이므로, 이 저장소에서는
알려진 이슈로 기록하고 운영 완화책을 명시한다.

## Purpose

Stage의 "변경마다 버전 범프" 규칙과 Codex의 버전별 플러그인 캐시가 만나면, v4 빌드처럼 짧은
시간에 여러 번 범프할 때 활성 Codex 세션이 중간에 잠길 수 있음을 잊지 않게 한다.

## Alternatives

- Codex 런타임이 태스크마다 플러그인 캐시를 재해석/재동기화 (근본 해결, Codex 쪽).
- 빌드 중 Codex 설정에서 Stage 비활성화 (이번에 적용한 완화책).
- 버전 범프 빈도를 낮춤 (CLAUDE.md 규칙과 충돌 — 비권장).

## Cost

기록만: 없음. 근본 수정: Codex 런타임 코드 변경(제3자).

## Risks

기록하지 않으면 다음 빌드에서 같은 차단이 재발해 원인 재조사에 시간 소모.

## Decision criteria

- 증상: Codex가 "missing stage/<old-version>/hooks/stage_guard.py"로 저장소 접근 전 차단.
- 진단 확정: 2026-07-13. Stage 소스엔 버전 하드코딩 없음(hooks.json은 `${CLAUDE_PLUGIN_ROOT}`
  변수 사용). 원인은 Codex 런타임의 캐시 해석.
- 완화 적용: `~/.codex/config.toml`에서 `stage@noory-ai enabled = false` (v4 빌드 동안).

## 재발 (2026-07-25)

W-00000064를 Codex 창에 위임하려다 시작조차 못 했다. Codex가 0.39.1 경로의 훅을 찾았고,
그 폴더는 그날 0.40.0 → 0.40.1로 올리면서 사라졌다. 캐시에는 0.40.1이 이미 들어와 있었으므로
동기화 문제가 아니라, 이미 떠 있던 프로세스가 세션 시작 때 해석한 경로를 붙들고 있던 것이다.

이번에는 파일 쓰기만 막힌 것이 아니다. `CLAUDE.md`와 작업 카드를 **읽는 것**까지 막혀서
Codex는 지시를 확인할 방법조차 없었다. 위임이 통째로 죽는다.

더 나은 완화책을 찾았다. Stage를 끄는 대신 그 저장소의 Codex 브로커 프로세스만 내린다
(`pgrep -f "app-server-broker.*<저장소경로>"` 로 찾아 종료). 다음 호출에서 새로 뜨며 현재 버전을
해석한다. Stage를 끄면 그 세션에서 Stage 게이트가 통째로 사라지므로, 이쪽이 잃는 것이 없다.

## 두 번째 경로 (2026-07-25, W-00000069)

위임이 죽는 방식이 하나 더 있다. 위임을 걸기 직전 이 저장소의 브로커 프로세스가 하나도 없음을
확인했는데도 코덱스가 시작하자마자 막혔다. 옛 프로세스가 붙들고 있던 것이 아니다.

코덱스 마켓플레이스가 **세션이 열리는 바로 그 순간** 저장소를 다시 당긴다 (`~/.codex/config.toml`
의 `[marketplaces.noory-ai] last_updated` 가 세션 시작 시각과 같았다). 세션은 그 직전에 이미
플러그인 폴더 경로를 해석해 두었는데, 동기화가 끝나면서 그 폴더가 새 버전으로 갈리며 사라진다.
세션 시작과 동기화가 겹쳐서 나는 경합이다.

여기서 나오는 운영 규칙: **코덱스에 위임한 작업이 도는 중에는 push 하지 않는다.** 마켓플레이스가
GitHub 에서 당기므로 push 가 같은 동기화를 다시 일으킨다.

대응은 같다 — 그 저장소의 브로커만 내리고 다시 건다. 이미 동기화가 끝난 뒤이므로 새로 뜬
프로세스는 현재 버전을 해석한다. 이번에도 그것으로 풀렸다.

## 세 번 재발한 날 (2026-07-26)

하루에 세 번 밟았고, 세 가지 표정이 다 나왔다.

- W-00000083 위임: 코드 작업은 끝났는데 **마무리 단계에서** 캐시가 갈려(0.43.8 소멸) 카드
  기록과 감사만 막혔다. Claude 쪽에서 기록을 대신 마무리했다.
- W-00000085 첫 위임: push(0.43.10) 직후에 걸었더니 시작조차 못 했다. 두 번째 경로(위
  2026-07-25 절) 그대로다.
- W-00000085 재위임: 브로커를 내리고 다시 걸었는데도 죽었다 — 세션이 뜨는 도중에 마켓플레이스
  재당김이 겹쳐, 세션이 해석해 둔 0.43.9 폴더가 그 사이 0.43.10 으로 갈리며 사라졌다. 브로커
  재시작 자체가 재당김을 일으키므로, **내린 직후의 첫 위임도 경합 창 안에 있다.**

오늘 확인된 운영 절차: push 후 위임 전에 브로커를 내리는 것으로는 부족할 수 있다. 내린 뒤
캐시 디렉터리(`~/.codex/plugins/cache/noory-ai/stage/`)에 현재 버전이 **완전한 모습으로**
(훅 파일 포함) 들어와 있는지 확인하고 나서 위임한다. 캐시가 원격과 일치하면 재당김이 다시
일어날 이유가 없어 경합 창이 닫힌다.

드라이버 쪽에는 이날 이후 방어가 하나 생겼다: 아무것도 못 한 실행은 종료 코드와 무관하게
실패로 판정된다(W-00000083, DE-00000033). 이 문제로 위임이 죽어도 이제 조용히 통과하지는
않는다.

## Status

기록됨. 근본 수정은 Codex(openai-codex 플러그인) 측에서 처리 예정 — 소유자 결정 2026-07-13.
이 저장소에서는 추가 코드 조치 없음.

2026-07-25 재발로 우선순위가 올라갔다. Stage는 변경마다 버전을 올리므로 하루에 세 번 올린
날에는 위임이 세 번 죽을 수 있다. 위임 실행이 정식 흐름이 된 지금(`stage-handoff`의 위임
실행, 0.40.1) 이것은 간헐적 불편이 아니라 흐름 자체의 차단 요인이다.

2026-07-29 재발. 이번에는 **드라이버가 그 값을 물었다.** W-00000114 로 0.54.2 를 올린 직후
에픽 W-00000115 를 걸었더니 실행자가 첫 읽기에서 사라진 0.54.1 훅 경로에 막혀 아무것도 못
하고 끝났고, 드라이버는 그것을 카드의 시도 하나로 셌다(`W-00000115.json` 의
`W-00000116.attempt_count: 1`). 인프라 실패를 카드에 물리지 않는 규칙이 있는데도 그렇게 된
이유는, 실패가 전송 오류가 아니라 **정상 종료한 실행자의 본문 텍스트**로 왔기 때문이다 —
`infrastructure_failure()` 가 보는 표식(시간 초과, 명령 없음, 종료 코드 126/127, 시그널)에
아무것도 안 걸린다.

버리는 호출로 캐시를 맞추고(0.54.2 확인) 다시 걸어 풀었다. 이 사례가
[DE-00000039](../official/decisions/records/DE-00000039.md) 3 절이 정한 venue 사전 점검의
실측 근거다 — 점검이 있었다면 시도를 쓰기 전에 "이 venue 는 지금 일할 수 없다"로 끊었다.

**완화가 자동화됐다 (2026-07-30).** 두 겹이다 — `preflights.codex` 가 저장소 매니페스트 버전의
훅이 캐시에 있는지 실행 전에 확인해 없으면 재동기화 방법을 말하며 막고(W-00000118 구현,
설정은 이 저장소에 적용됨), 설령 뚫려도 인프라 실패는 카드 시도를 안 먹는다(W-00000133).
0.55.0 릴리스 직후 재동기화 → 점검 통과를 실측으로 확인했다. 사람이 기억할 절차가 없어졌다.
근본 수정(실행 중 세션의 캐시 재해석)은 여전히 코덱스 런타임 몫이다.

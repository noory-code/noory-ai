# P-00000001 Codex 런타임의 Stage 플러그인 버전별 캐시 무효화

## Proposal

Codex CLI(openai-codex 플러그인)가 Stage 플러그인 훅을 버전별 캐시 경로
(`~/.codex/plugins/cache/noory-ai/stage/<version>/hooks/...`)로 해석한 뒤, 마켓플레이스가
새 버전으로 동기화돼도 실행 중 세션의 해석을 갱신하지 못해, 옛 경로가 사라지면 모든
셸/패치 작업이 훅 실패로 차단되는 문제. 근본 수정은 Codex 런타임 몫이므로, 이 저장소에서는
알려진 이슈로 기록하고 운영 완화책을 명시한다.

## Purpose

Stage의 "변경마다 버전 범프" 규칙과 Codex의 버전별 플러그인 캐시가 만나면, v4 빌드처럼 짧은
시간에 여러 번 범프할 때 활성 Codex 세션이 중간에 잠길 수 있음을 잊지 않게 한다.

## Alternatives

- Codex 런타임이 태스크마다 플러그인 캐시를 재해석/재동기화 (근본 해결, Codex 쪽).
- 빌드 중 Codex 설정에서 Stage 비활성화 (이번에 적용한 완화책).
- 버전 범프 빈도를 낮춤 (CLAUDE.md 규칙과 충돌 — 비권장).

## Cost

기록만: 없음. 근본 수정: Codex 런타임 코드 변경(제3자).

## Risks

기록하지 않으면 다음 빌드에서 같은 차단이 재발해 원인 재조사에 시간 소모.

## Decision criteria

- 증상: Codex가 "missing stage/<old-version>/hooks/stage_guard.py"로 저장소 접근 전 차단.
- 진단 확정: 2026-07-13. Stage 소스엔 버전 하드코딩 없음(hooks.json은 `${CLAUDE_PLUGIN_ROOT}`
  변수 사용). 원인은 Codex 런타임의 캐시 해석.
- 완화 적용: `~/.codex/config.toml`에서 `stage@noory-ai enabled = false` (v4 빌드 동안).

## 재발 (2026-07-25)

W-00000064를 Codex 창에 위임하려다 시작조차 못 했다. Codex가 0.39.1 경로의 훅을 찾았고,
그 폴더는 그날 0.40.0 → 0.40.1로 올리면서 사라졌다. 캐시에는 0.40.1이 이미 들어와 있었으므로
동기화 문제가 아니라, 이미 떠 있던 프로세스가 세션 시작 때 해석한 경로를 붙들고 있던 것이다.

이번에는 파일 쓰기만 막힌 것이 아니다. `CLAUDE.md`와 작업 카드를 **읽는 것**까지 막혀서
Codex는 지시를 확인할 방법조차 없었다. 위임이 통째로 죽는다.

더 나은 완화책을 찾았다. Stage를 끄는 대신 그 저장소의 Codex 브로커 프로세스만 내린다
(`pgrep -f "app-server-broker.*<저장소경로>"` 로 찾아 종료). 다음 호출에서 새로 뜨며 현재 버전을
해석한다. Stage를 끄면 그 세션에서 Stage 게이트가 통째로 사라지므로, 이쪽이 잃는 것이 없다.

## Status

기록됨. 근본 수정은 Codex(openai-codex 플러그인) 측에서 처리 예정 — 소유자 결정 2026-07-13.
이 저장소에서는 추가 코드 조치 없음.

2026-07-25 재발로 우선순위가 올라갔다. Stage는 변경마다 버전을 올리므로 하루에 세 번 올린
날에는 위임이 세 번 죽을 수 있다. 위임 실행이 정식 흐름이 된 지금(`stage-handoff`의 위임
실행, 0.40.1) 이것은 간헐적 불편이 아니라 흐름 자체의 차단 요인이다.

# P-00000005 목적별 RAG — 제품 맥락, 지식, 경험

## Proposal

rag 를 "자료를 넣으면 검색되는 것"에서 **목적이 먼저 있고 그 목적에 맞춰지는 것**으로 바꾼다. 엔진(임베딩, 벡터,
그래프, 검색)은 하나로 두고, RAG 를 목적마다 여러 개 둔다. 각 RAG 는 목적 선언을 하나 가진다.

- 목적: 무엇을 위해 쌓는가
- 사는 곳: 프로젝트 안, 또는 사용자를 따라다니는 곳
- 무엇을 뽑을지: 색인할 때 세션에게 줄 지침과 엔티티 종류
- 완료 기준: 그 목적에서 끌어낸 probes
- 공유 정책

지금까지 나온 세 모습(2026-11-02 사용자와의 논의):

| | 1. 제품 맥락 | 2. 지식 | 3. 경험 |
|---|---|---|---|
| 무엇이 쌓이나 | 기획, 결정과 근거, **아키텍처 철학**(원칙, 경계, 불변식, 버린 대안) | 공부하며 정리한 개념과 연결 | AI 로 작업하며 겪은 어려움과 푼 방식, 노하우 |
| 문장 모양 | "이건 이래서 이렇게 했다" | "X 는 Y 다" | "이런 상황에서 A 는 실패했고 B 가 통했다" |
| 단위 | 결정, 원칙 | 개념 | 에피소드: 상황 → 시도 → 결과 → 교훈 |
| 진실의 기준 | 지금 유효한 결정과 지금의 코드 | 고쳐진 이해 | 그 상황에서 나한테 통했는가(조건부, 일인칭) |
| 시간의 의미 | 뒤집힌 결정은 이력 | 오해가 고쳐짐 | **변화 자체가 내용**: 초보에서 능숙으로 |
| 주인과 사는 곳 | 프로젝트, 저장소 안 | 나, 프로젝트를 넘음 | 나, 프로젝트를 넘음 |
| 나중에 오는 질문 | "이건 왜 이렇게 했지?" | "X 에 대해 내가 아는 게 뭐지?" | "이런 문제 전에 어떻게 풀었지?", "1년 전과 지금 내 방식이 어떻게 달라졌지?" |

코드의 구체적 위치는 1번의 몫이 아니다. 그건 코드를 직접 보는 도구(grep, 언어 서버)가 더 정확하다. 1번이 쌓는 것은
구조가 왜 그렇게 생겼는가다.

경험의 원재료는 **주로 AI 로 작업하면서 겪는 어려움**이다. 어디서 어떻게 모을지는 아직 열려 있다(아래 Status).
후보로 본 원천은 Stage 회고(R-기록의 도움이 된 맥락·빠졌던 맥락·다음에 바꿀 것), Claude 세션 기록, 다시나 일기다.

경험 RAG 는 다른 둘과 쌓는 주체가 다르다(사용자의 2026-11-02 정리).

- **사용자에게 묻지 않는다.** AI 가 사용자의 의도를 더 잘 파악하려고 작업하면서 **스스로 쌓아 간다.** 1·2 번은
  사람이 자료를 넣고 부를 때 동작하지만, 3 번은 작업의 부산물을 AI 가 알아서 모은다.
- **코치 역할도 좋다.** 쌓인 경험으로 "이 유형은 지난번에 이렇게 풀었다", "같은 실수를 반복하고 있다"를 짚어 주는 쓰임.
- **더 싸게 만들고 싶다.** 사용자가 언급한 Hermes 같은 에이전트가 경험을 스스로 쌓는다고 알려져 있지만, 그보다 적은
  비용으로 같은 효과를 내는 것이 목표다. 비용의 대부분은 무엇을 남길지 고르고 요약하는 LLM 호출에서 나온다.

## Purpose

제품을 만들고, 공부하고, AI 로 일하면서 생기는 맥락이 흩어지거나 사라지지 않고, 나중에 그 목적에 맞는 질문으로
다시 꺼낼 수 있게 한다. Stage 가 "일은 목적에 매달리고 독립적으로 판정한다"이듯, RAG 도 목적에 매달리고 probes 로
그 목적이 이뤄졌는지 판정한다.

## Alternatives

- **RAG 하나에 검색 스타일만 여러 개**(바늘 찾기, 전체 조망, 관계 추적): 2026-11-02 에 설계안까지 냈지만 사용자가
  "그런 스타일 말고 목적"이라고 바로잡았다. 검색 기법은 목적 안의 하위 선택지로 남는다.
- **RAG 하나에 목적 태그만 붙이기**: 비용은 싸지만 사적인 공부·경험 메모가 제품 답변에 끼어들고, 공유 정책이 꼬인다.
  사는 곳과 주인이 다른 것을 한 곳에 둘 수 없다.
- **목적마다 엔진까지 따로**: 중복이 크다. 엔진은 같다.

## Cost

- rag 는 지금 프로젝트 하나에 RAG 하나(`.noory/rag/`)다. 사용자를 따라다니는 RAG 는 담을 곳이 없어 새 위치와 이름
  체계가 필요하다.
- 색인 비용이 가장 크다. 세션이 자료를 읽고 조각과 엔티티를 뽑는다(340만 자면 토큰 백만 개 이상).
- 검색 속도는 병목이 아니다. 2026-11-02 측정(384차원, sqlite-vec, 무작위 벡터, 메모리): 조각 1만 개 7ms, 10만 개
  72ms, 30만 개 237ms. 이 저장소의 `.stage` 전체는 조각 약 2,300개다. 조각 수에 비례하므로 100만 개 근처에서는 근사
  색인이 필요하다.

## Risks

- 텍스트가 많아질수록 느려지기보다 **흐려진다**. 비슷한 조각, 낡은 판본, 뒤집힌 결정이 상위를 차지한다. 목적별로
  나누는 효과는 속도보다 품질에서 크다.
- 제품 맥락: 아키텍처 철학은 코드와 말없이 멀어진다. 문서만 믿으면 낡은 철학을 굳힌다.
- 경험: 한 번 통한 것을 규칙으로 굳힌다. AI 도구 노하우는 빨리 낡는다. 가장 사적이다.
- 넘나드는 질문("공부한 그 개념을 이 제품의 어느 결정에 썼지?")에는 여러 RAG 를 함께 찾는 기능이 필요하다.
- 같은 사건이 여러 RAG 에 다르게 들어간다(결정은 제품 맥락, 거기서 배운 것은 경험). 뽑기 지침이 그 차이를 맡아야
  한다.

## Decision criteria

- 목적 하나를 실제 자료로 세워 보고, 그 목적에서 끌어낸 probes 가 지금의 단일 RAG 보다 나은 답을 낸다.
- 사적인 RAG 의 내용이 프로젝트 RAG 의 답에 섞이지 않는다.
- 목적을 선언하는 부담이 "일단 넣고 보자"보다 크지 않다.

## Status

열림 — 아이디어 단계(2026-11-02). 더 생각할 것:

- 경험의 원재료를 어디서 어떻게 모을까. 경험은 적지 않으면 사라진다.
- 경험 RAG 는 AI 가 알아서 쌓고 코치처럼 먼저 짚기도 하는데, 이는 rag 의 "부를 때만 동작" 원칙과 부딪힌다. 이 원칙을
  경험 RAG 에서만 풀지, 경험 RAG 를 rag 밖(예: 다시나, Avatar)에 둘지 정해야 한다.
- 싸게 쌓는 방법: 매 작업마다 LLM 으로 요약하지 않고, 이미 생기는 기록(Stage 회고, 실패한 시험, 거절된 리뷰, 사용자의
  수정 지시)에서 규칙으로 후보를 고른 뒤 그때만 LLM 을 부르는 길이 있다. 무엇이 "어려움"의 신호인지가 열쇠다.
- 공부·경험 RAG 는 사용자 홈에 살까, 별도 저장소에 살까. 후자면 지금 구조로도 거의 된다.
- 제품 맥락 RAG 가 Stage 기록을 원천으로 읽으면 처음부터 쌓을 필요가 없지만, 플러그인 독립성과 부딪힌다.
- 네 번째 이후의 모습(조사, 창작 세계관, 사람·협업, 운영)은 1~3 의 변형인지 따로인지.

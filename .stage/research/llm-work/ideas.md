# 클로드와 코덱스가 일을 더 잘하게 만들 아이디어

**먼저 검토할 후보는 근거가 바뀌면 관련 판단을 다시 확인하는 도구와, 답에 필요한 조건까지 찾아 주는 검색입니다.**
첫 후보는 이미 한 일을 어디까지 다시 써도 되는지 다룹니다.
둘째 후보는 다음 판단에 무엇을 넣어 줘야 하는지 다룹니다.
정확도를 지키면서 반복 작업과 읽을 양을 줄일 수 있는지 시험할 수 있습니다.

이 문서는 2026-10-05에 마친 [연구](final-report.md)에서 아이디어를 뽑은 결과입니다.
아래는 제안 당시의 문제와 기대 효과입니다. 효과가 입증된 제품 목록은 아닙니다.
이후 여섯 가지를 모두 작은 시제품으로 만들고 1차 시험을 마쳤습니다.
실제로 구현한 범위와 Claude·Codex 비교 결과는 [시제품 시험 보고서](findings/2026-10-05-ideas-lab.md)에 정리했습니다.
현재 적용 권고도 그 보고서에서 확인합니다. 아래 기대 효과가 모두 입증됐다는 뜻은 아닙니다.
같은 판정의 반복 비용을 다룬 [실제 코드 리뷰 후속 시험](findings/2026-10-05-review-reuse.md)도 별도로 마쳤습니다.
실제 사용할 AI는 [Claude와 Codex](purpose.md#available-ai)로 한정합니다.

## 후보 여섯 가지

| 후보 | 사용자가 겪는 문제 | 바꿀 방법 | 기대하는 이점 | 검토 순서 |
|---|---|---|---|---|
| 근거가 바뀐 판단만 다시 확인합니다. | 매번 전부 다시 읽거나, 낡은 결론을 그대로 씁니다. | 판단과 그 근거를 연결하고 변경 영향을 추적합니다. | 재검토 범위를 줄이면서 놓친 변경을 찾습니다. | 먼저 검토합니다. |
| 답에 필요한 조건까지 검색합니다. | 관련 문서를 찾았지만 예외나 버전이 빠집니다. | 질문별로 필요한 근거와 아직 모르는 조건을 반환합니다. | 자료가 많아도 답하지 못하는 일을 줄입니다. | 먼저 검토합니다. |
| 오류 뒤 실제 상태부터 확인합니다. | 응답이 끊겨 같은 작업을 다시 실행합니다. | 완료·일부 완료·충돌을 구별한 뒤 남은 작업을 고릅니다. | 중복 변경과 불필요한 재시도를 줄입니다. | 다음으로 검토합니다. |
| 진행 상황을 답한 뒤 하던 일로 돌아옵니다. | 상태를 물었더니 AI가 일을 끝내 버립니다. | 원래 작업과 잠깐 끼어든 질문을 구별해 이어갈 행동을 보존합니다. | 사용자의 재지시를 줄입니다. | 기존 Stage 기능부터 확인합니다. |
| 실패한 구간을 다시 시험합니다. | 실패 원인을 몰라 지침과 설정을 이것저것 바꿉니다. | 당시 입력과 결과를 보존하고 조건 하나만 바꿔 비교합니다. | 엉뚱한 곳을 고치는 시간을 줄입니다. | 앞선 후보의 실험에 함께 씁니다. |
| 반복해서 성공한 절차를 도구로 옮깁니다. | 같은 검색·계산·형식 검사를 매번 AI가 다시 만듭니다. | 조건이 명확한 부분을 코드로 실행하고 예외는 AI에 돌려줍니다. | 반복 호출과 절차의 흔들림을 줄입니다. | 실제 반복이 쌓인 뒤 검토합니다. |

## 근거가 바뀐 판단만 다시 확인합니다

**예시:** 어제 “이 변경은 기존 동작을 유지한다”고 검토했습니다.
오늘 설정 파일 하나가 바뀌었습니다. 이전 결론 중 무엇을 다시 봐야 할까요?

제안하는 도구는 결론, 근거 파일, 적용 조건, 확인 시점을 연결합니다.
파일이 바뀌면 그 파일에 기대었던 결론을 찾아 재검토 대상으로 표시합니다.
관련 없는 결론은 남겨 둡니다. 의존 관계를 모르면 범위를 넓혀 다시 확인합니다.

- **개입할 동작:** 자료의 유효성을 확인하고 이전 판단을 재사용하는 단계입니다. 지도에서 C03·D08·M08에 해당합니다.
- **현재 기능과의 차이:** RAG는 파일 해시로 바뀐 자료를 찾습니다. Stage는 일부 항목을 다시 검토하고 이전 판정을 합칩니다. 제안은 자료의 변경을 개별 판단까지 연결하는 것입니다.
- **기대 이점:** 전부 다시 읽는 양을 줄이고, 과거에 통과했다는 이유만으로 넘어가는 일을 줄일 수 있습니다.
- **대가:** 근거를 연결하는 비용이 듭니다. 파일이 같아도 외부 환경이나 사용자 요구가 바뀔 수 있습니다. 해시 일치만으로 결론이 유효하다고 판정하면 안 됩니다.
- **최소 시험:** 바뀌지 않은 과제 4개와 코드·설정·요구가 바뀐 과제 4개를 비교합니다. 놓친 변경, 재검토한 양, 최종 결과, 기록 관리 시간을 셉니다.
- **근거:** [문맥과 기억 실험](findings/2026-10-05-followup.md)은 적용 조건을 남길 이유를 보여 줬습니다. 변경에 따라 판단을 갱신하는 방식은 새 가설입니다.

첫 구현을 검토한다면 로컬 파일과 명시된 요구에 한정합니다.
의존 관계를 모르는 테스트나 외부 서비스 검사를 자동으로 생략하는 기능은 첫 범위에 넣지 않습니다.

## 답에 필요한 조건까지 검색합니다

**예시:** “버전 3에서 이 기능을 사용할 수 있나요?”라고 물었습니다.
기능 소개는 찾았지만 지역별 예외와 실제 적용 버전이 빠졌다면 아직 답할 수 없습니다.

검색 전에 이 질문에 필요한 항목을 정합니다. 예시에서는 기능, 버전, 지역 조건입니다.
검색 결과에는 답을 뒷받침하는 대목, 예외, 출처와 빠진 항목을 함께 담습니다.
근거가 충돌하면 양쪽을 남깁니다. 다음 검색은 비어 있는 항목을 찾는 데 사용합니다.

- **개입할 동작:** 검색어를 만들고, 대목을 고르고, 증거가 충분한지 판단하는 단계입니다. R03·R07·R08·E05·E07에 해당합니다.
- **현재 기능과의 차이:** RAG의 검색 결과에는 본문과 자유 형식의 metadata가 있습니다. 확인한 검색 함수는 벡터 검색과 그래프 확장을 수행합니다. 제안은 질문에 필요한 조건을 명시하고 결과와 대조하는 것입니다.
- **기대 이점:** 관련 문서를 많이 읽는 데서 멈추지 않고, 답할 수 있는 근거를 모을 수 있습니다. 같은 결과를 계속 찾는 횟수도 줄일 여지가 있습니다.
- **대가:** 필요한 조건을 잘못 정하면 탐색이 좁아집니다. 조건 추출과 추가 검색에도 시간과 사용량이 듭니다. 처음에는 버전별 기능 확인처럼 답의 조건이 분명한 질문을 다룹니다.
- **최소 시험:** 답이 있는 경우, 예외가 있는 경우, 자료가 부족한 경우, 출처가 충돌하는 경우를 각 2개씩 만듭니다. 현재 RAG와 비교해 답의 정확도, 조건 누락, 중복 검색, 전체 사용량을 봅니다.
- **근거:** [문맥 실험](hypotheses.md#h03)에서 조건을 남긴 발췌는 판단을 유지했습니다. 다만 실험자가 발췌했으므로 자동 검색도 잘할 것이라는 증거는 아닙니다.

처음부터 모든 연구 질문을 처리하는 검색기로 만들 필요는 없습니다.
한 종류의 질문에서 어떤 근거가 필요한지 명확히 정하는 것이 첫 시험입니다.

## 오류 뒤 실제 상태부터 확인합니다

**예시:** 파일 저장 뒤 응답이 끊겼습니다. 저장은 끝났지만 AI는 실패했다고 보고 다시 쓸 수 있습니다.

작업 전에 예상 변경과 원래 상태를 기록합니다.
오류가 나면 다시 실행하기 전에 현재 상태를 읽습니다.
목표에 도달했으면 넘어가고, 일부만 끝났으면 남은 부분을 처리합니다.
다른 작업의 변경이 끼었거나 상태를 읽을 수 없으면 자동 재시도를 멈춥니다.

- **개입할 동작:** 실행을 기다리고, 결과를 읽고, 복구 방법을 고르는 단계입니다. A06·A08·V04에 해당합니다.
- **현재 기능과의 차이:** Stage와 Evonest는 검사 명령을 실행합니다. [Stage의 재개 처리](../../../stage/scripts/driver_supervised.py)는 저장한 저장소 상태와 현재 상태가 다르면 완료 단계를 건너뛰지 않습니다. 제안은 더 작은 도구 호출 단위에서 일부 완료와 중복 실행을 구별하는 것입니다.
- **기대 이점:** 중복 쓰기와 이미 끝난 작업의 재실행을 줄일 수 있습니다.
- **대가:** 작업마다 완료를 읽어 낼 방법이 필요합니다. 읽은 뒤 다시 상태가 바뀔 수도 있습니다. 재시도 직전에도 원래 조건을 확인해야 합니다.
- **최소 시험:** 정상 저장 뒤 응답 유실, 일부 저장, 잘못된 경로, 다른 작업의 동시 수정을 만듭니다. 중복 변경, 복구 성공, 사용자 개입 횟수를 비교합니다.
- **근거:** [결과 확인 실험](hypotheses.md#h04)은 상태를 주면 완료 여부를 구별할 수 있음을 보여 줬습니다. 복구가 더 잘되는지는 시험하지 않았습니다.

첫 대상은 임시 폴더 안에서 되돌릴 수 있는 파일 작업입니다.
결제나 발송처럼 반복 실행의 영향을 회수하기 어려운 행동으로 바로 확대하지 않습니다.

## 진행 상황을 답한 뒤 하던 일로 돌아옵니다

**예시:** 사용자가 “어디까지 했어요?”라고 묻습니다.
AI는 상황을 설명하고, 이미 허용된 남은 작업을 이어갑니다.
사용자가 중단을 요구하거나 범위를 바꾸면 그 지시를 먼저 반영합니다.

원래 목적, 완료 조건, 다음 행동을 작업 기록에 남깁니다.
새 메시지가 들어오면 상황 질문인지, 조건 변경인지, 중단인지 구별합니다.
짧은 확인 응답을 새로운 실행 권한으로 해석하지 않습니다. 기존에 허용된 범위에서만 이어갑니다.

- **개입할 동작:** 새 요청의 관계와 작업 종료 여부를 정하는 단계입니다. U03·U06·V07에 해당합니다.
- **현재 기능과의 차이:** Stage에는 작업 기록과 세션 요약이 있습니다. 확인한 종료 훅은 요약을 저장한 뒤 종료를 허용합니다. 제안은 대화 중 잠깐 다른 질문에 답한 뒤 원래 작업으로 돌아오는 처리입니다.
- **기대 이점:** 사람이 “계속하세요”라고 반복할 수고를 줄일 수 있습니다.
- **대가:** 잘못 분류하면 멈추라는 지시를 무시할 수 있습니다. 필수 정보나 승인이 없으면 대기해야 합니다. 호스트가 자동 재개를 지원하는 범위도 확인해야 합니다.
- **최소 시험:** 작업 중간에 상태 질문, 조건 변경, 명시적 중단, 짧은 확인 응답을 각각 넣습니다. 재지시 횟수와 잘못 계속한 횟수를 함께 셉니다.
- **근거:** [이 대화의 중단](findings/2026-10-05-failures.md)은 실제 관찰입니다. 기존 목적 시험은 장기 작업의 재개를 검증하지 않았습니다.

매 응답에 목적 문장을 더 쓰게 하는 방법과는 작동 방식이 다릅니다.
후자는 [기존 실험](hypotheses.md#h01)에서 이점을 확인하지 못했습니다.

## 실패한 구간을 다시 시험합니다

**예시:** AI가 잘못 답했습니다. 검색에 자료가 없었는지, 요약에서 예외가 사라졌는지 구별해야 합니다.

관찰할 수 있는 입력, 도구 호출, 응답, 실제 상태를 연결해 저장합니다.
실패한 구간을 임시 환경에서 다시 실행하되 조건 하나만 바꿉니다.
전체 자료를 주었을 때와 기존 발췌를 주었을 때의 차이처럼 원인을 좁힐 비교를 만듭니다.

- **개입할 동작:** 예상과 결과를 비교하고 오류 위치를 찾는 단계입니다. V01·V02·V03에 해당합니다.
- **기대 이점:** 검색 문제를 프롬프트 문제로 오해하는 식의 수정을 줄일 수 있습니다.
- **대가:** 기록과 재현 환경을 관리해야 합니다. 외부 상태와 서버의 비공개 입력은 완전히 재현하지 못합니다. 저장한 도구 응답을 주입하는 시험과 실제 도구를 다시 부르는 시험을 구별해야 합니다.
- **최소 시험:** 검색 누락, 잘못된 축약, 일부 파일 쓰기를 각각 의도적으로 만듭니다. 원인을 찾는 시간과 잘못 지목한 위치를 비교합니다.
- **근거:** [이번 실험 자료](experiments/README.md)는 입력·원본·해시를 보존했습니다. 이를 재사용할 수 있는 디버깅 도구로 만든 효과는 미검증입니다.

처음에는 다른 후보를 검증할 연구 도구로 사용합니다.
사용 빈도와 절약한 시간이 확인되면 독립된 제품으로 만들지 검토합니다.

## 반복해서 성공한 절차를 도구로 옮깁니다

**예시:** 매번 여러 manifest에서 버전을 읽고 같은지 비교한 뒤 보고서를 만듭니다.
비교 기준과 입력 형식이 정해졌다면 파일 읽기와 비교는 코드로 처리할 수 있습니다.

실제 작업 기록에서 반복되는 절차를 찾습니다.
입력 조건, 수행할 동작, 결과 확인 방법을 분리해 작은 도구로 옮깁니다.
조건이 맞지 않으면 자동으로 추측해 실행하지 않고 AI가 다시 판단하도록 돌려줍니다.

- **개입할 동작:** 입력 검사와 정해진 분기를 처리하는 단계입니다. D02·A02·A03에 해당합니다.
- **현재 기능과의 차이:** Stage에는 이미 여러 절차를 수행하는 스크립트가 있습니다. 기존 명령으로 처리되는 절차는 재사용합니다. 새 도구는 아직 반복해서 수작업으로 처리하는 구간에서 찾습니다.
- **기대 이점:** 같은 코드를 매번 다시 작성하거나 조건을 다르게 해석하는 일을 줄일 수 있습니다.
- **대가:** 규칙을 유지해야 하고, 범위 밖 처리를 AI에 돌려주는 비용도 듭니다. 한 번 성공한 기록만으로 절차가 일반적이라고 판단할 수 없습니다.
- **최소 시험:** 조건에 맞는 입력, 버전 변경, 누락된 값, 예상하지 못한 형식을 준비합니다. 최종 정확도, 전체 호출 수, 복구 비용을 비교합니다.
- **근거:** [로컬 규칙 시험](hypotheses.md#h06)은 명확한 입력의 분기를 코드로 처리했습니다. 작업 기록에서 절차를 자동 추출하는 방법은 시험하지 않았습니다.

첫 형태는 읽기와 비교만 수행하는 도구가 적합합니다.
파일 수정이나 배포까지 과거 절차에 묶어 자동 실행하는 기능은 별도 설계가 필요합니다.

## 기존 플러그인에서 시작할 위치

아래 내용은 현재 소스에서 확인한 범위입니다. 실행해 통합 동작을 검증한 결과는 아닙니다.

| 위치 | 이미 확인한 기능 | 아이디어에서 더 확인할 것 |
|---|---|---|
| [Stage 재검토](../../../stage/scripts/driver_supervised.py), [판정 병합](../../../stage/scripts/driver_review.py) | 이전 실패 항목과 변경 경로를 전달하고, 이번에 검토하지 않은 이전 판정을 남깁니다. | 어떤 변경이 이전 통과 항목에 영향을 주는지 근거와 연결합니다. 확인한 병합 함수에는 그 의존 관계가 없습니다. |
| [RAG 변경 감지](../../../rag/server/src/rag_mcp/application/indexer.py) | 파일 해시를 이용해 추가·변경·삭제를 찾습니다. | 파일 변경을 결론의 재검토와 연결할 수 있는지 봅니다. |

| [Stage 종료 처리](../../../stage/hooks/stage_guard.py) | 세션 요약을 파일로 남깁니다. | 상황 질문 뒤 기존 작업을 이어갈 경로를 별도로 검증합니다. |
| [Evonest 실행과 검증](../../../evonest/src/evonest/core/phases.py) | 작업을 수행하고 설정된 빌드·테스트로 검증합니다. | 오류 뒤 일부 완료된 상태를 읽고 안전하게 이어가는 범위를 확인합니다. |

Stage에는 반복 상태를 감지해 멈추는 기능과 재검토 범위를 줄이는 기능이 이미 있습니다.
이를 새로운 아이디어의 성과로 세지 않습니다. 기존 기능이 해결하지 못한 사례부터 확보합니다.

## 두 환경에 연결하는 방법

Claude Code와 Codex는 로컬 MCP 서버를 연결할 수 있습니다.
근거: [Claude Code 공식 문서](https://code.claude.com/docs/en/mcp), [OpenAI Docs](https://developers.openai.com/codex/mcp).

따라서 상태 읽기, 근거 조회, 변경 비교를 로컬 도구로 제공하는 방식을 검토할 수 있습니다.
이 사실만으로 모든 호출을 가로채거나 작업을 자동 재개할 수 있다고 보지는 않습니다.
그 동작은 각 호스트의 실제 연결 경로에서 따로 확인해야 합니다.
모델이 판단할 부분은 지금 사용하는 Claude와 Codex에 맡깁니다.
별도 AI 서비스를 도입하지 않아도 시작할 수 있도록 설계하되, 추가 모델 판단에는 기존 서비스의 사용량이 듭니다.

## 처음 시험할 후보를 고르는 기준

제 권고는 **근거가 바뀐 판단을 다시 확인하는 방법부터 좁게 시험하는 것**입니다.
Stage의 이전 판정과 RAG의 변경 감지가 출발점이 됩니다.
무엇을 재사용하고 무엇을 다시 봐야 하는지 미리 정한 과제로 비교할 수 있습니다.
다만 두 기능을 연결하는 구현이 이미 있다는 뜻은 아닙니다.

1. 로컬 파일과 요구 조건이 분명한 과제 8개를 만듭니다. 사람에게 기대 결과를 먼저 검토받습니다.
2. Claude와 Codex 각각에서 기존 방식과 바꾼 방식을 비교합니다. 상대 모델보다 각자의 기존 방식보다 나아졌는지를 봅니다.
3. 최종 결과, 놓친 변경, 불필요한 재검토, 시간과 사용량을 기록합니다. 기록 관리와 재시도 비용도 포함합니다.
4. 변경 때문에 무효가 된 결론을 그대로 재사용하면, 재검토를 줄였더라도 후보를 수정하거나 보류합니다.

이것은 처음 제안한 정식 비교입니다. 사람 검토를 포함한 이 계획은 아직 수행하지 않았습니다.
이후 사용자가 모든 후보의 시험을 요청해 합성 사례 24개로 범위를 좁혀 96번 비교했습니다.
그 시험을 위의 실제 과제·사람 검토 계획을 마친 것으로 취급하지 않습니다.
초기 시험을 통과해도 일반적인 개선율로 발표하지 않습니다.

## 지금 우선하지 않을 방법

- **매번 목적과 점검표를 더 길게 쓰게 하기:** 기존 시험에서 추가 지침의 이점을 확인하지 못했습니다.
- **모든 작업을 두 AI에게 보내 합의시키기:** 사용량과 대기가 늘어납니다. 같은 근거를 잘못 쓰면 둘 다 틀릴 수 있습니다. 독립 검토가 필요한 구간을 먼저 찾습니다.
- **모델이 적은 확률만으로 자동 실행하기:** 그 숫자와 실제 성공률의 관계를 확인하지 않았습니다.
- **모든 자료를 짧게 요약하기:** 기존 실험에서 예외를 지우자 답할 수 있던 질문도 보류했습니다.

이번 단계에서 고를 것은 제품 이름보다 **어떤 반복이나 실패를 얼마나 줄일 것인가**입니다.
그 답이 확인되면 기존 플러그인에 넣을지, 별도 도구로 만들지 결정할 수 있습니다.

## 이후 사용자가 제안한 별도 후보

사용자는 사람이 반복해서 쓰는 판단 기준을 모아 새로운 상황에 적용하는 아이디어를 제안했습니다.
[판단 기준 수집과 적용](decision-criteria.md)에 수집·동작·개선 방법과 검증할 질문을 기록했습니다.
앞선 여섯 시제품에 포함해 시험한 기능은 아닙니다. 현재는 연구 후보로 기록했습니다.

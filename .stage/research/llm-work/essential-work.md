# AI가 일을 할 때 필요한 기능과 줄일 수 있는 반복

**제품 기회를 찾을 때는 필요한 기능과 그 기능을 수행하는 방법을 나눠 봐야 합니다.**
판단은 계속 필요해도, 매번 같은 자료를 읽고 같은 판단을 새로 만들 필요는 없을 수 있습니다.
우선 살펴볼 곳은 현재 상태를 확인하는 일, 이전 판단이 여전히 유효한지 확인하는 일, 실행한 결과를 확인하는 일입니다.
이는 연구에서 제안하는 방향입니다. 시장 수요나 일반적인 절감 효과를 입증한 결과는 아닙니다.

## Jev에서 가져올 질문

Jev의 공식 발표는 비정형 자료에서 소프트웨어가 바로 쓸 수 있는 판단을 내는 모델을 설명합니다.
문자열을 순서대로 생성하는 대신 정해진 형식의 출력을 병렬로 계산한다고 밝힙니다.
속도와 비용 수치는 공급자가 정한 비교 조건에서 나온 값입니다.
우리는 Jev를 직접 실행하거나 그 절감량을 재현하지 않았습니다.
[공식 발표](https://typesafe.ai/blog/introducing-system-one-models-and-jev)

이 사례에서 얻는 설계 질문은 다음과 같습니다.

> 자주 필요한 기능 하나를 골라 입출력을 좁히면, 지금보다 적은 계산으로 수행할 수 있나요?

이 문장은 공개 자료를 읽고 도출한 해석입니다. 창업자의 내적 동기를 확정한 설명은 아닙니다.
우리에게는 Claude와 Codex를 바꾸는 대신, 이들이 반복해서 수행하는 일을 줄이는 방법이 열려 있습니다.

## 무엇이 반드시 필요한가요

여기서는 사용자가 맡긴 일을 여러 단계에 걸쳐 수행하는 AI를 다룹니다.
목표와 현재 상태가 있어야 다음 행동을 고를 수 있고, 선택한 행동은 결과로 이어져야 합니다.
그 일을 제대로 끝냈다고 알려면 결과를 목표와 대조할 근거도 필요합니다.
아래 기능들은 한 모델 호출 안에서 함께 처리될 수도 있습니다. 각각에 별도 모델이 필요한 것은 아닙니다.

| 필요한 기능 | 없으면 생기는 문제 | 반드시 별도 모델을 불러야 하나요 |
|---|---|---|
| 무엇을 달성해야 하는지 유지합니다. | 잘못된 목표를 끝내거나 사용자가 바꾼 조건을 놓칩니다. | 목적이 정해졌다면 기록으로 유지할 수 있습니다. 새 지시가 뜻을 바꿀 때 해석이 필요합니다. |
| 판단에 필요한 현재 상태를 확보합니다. | 이미 바뀐 파일이나 오래된 진행 상황을 근거로 행동합니다. | 파일·버전·실행 상태는 프로그램이 읽을 수 있습니다. 관찰 범위는 작업에 따라 다릅니다. |
| 자료에서 필요한 사실과 조건을 뽑습니다. | 관련 자료를 찾고도 버전이나 예외를 놓칩니다. | 구조가 정해진 자료는 코드로 읽을 수 있습니다. 자유 문서는 해석이 필요할 수 있습니다. |
| 다음 행동을 고릅니다. | 무엇을 실행하고 언제 보류할지 정하지 못합니다. | 명확한 규칙은 코드로 처리합니다. 열린 판단은 모델에 맡길 수 있습니다. |
| 선택한 행동을 실제 결과로 만듭니다. | 계획과 설명만 남고 파일이나 사용자에게 줄 결과가 나오지 않습니다. | 저장·호출·형식 변환은 도구가 맡을 수 있습니다. 새 글이나 코드를 만드는 일은 모델을 쓸 수 있습니다. |
| 결과가 목표를 충족했는지 확인합니다. | 일부만 끝났는데 완료했다고 말하거나 같은 작업을 다시 수행합니다. | 비교·테스트로 확인할 수 있는 조건은 코드로 검사합니다. 품질 판단에는 모델이나 사람이 필요할 수 있습니다. |

기능의 필요성과 구현 비용은 다릅니다.
예를 들어 현재 상태가 이미 입력에 정확히 담겼다면 이를 얻으려고 다시 검색할 필요는 없습니다.
사용자가 만족했는지와 테스트가 통과했는지도 서로 다릅니다. 검사 가능한 일부 조건만으로 전체 성공을 단정하지 않습니다.

## 결정을 중심에 두면 어디를 줄일 수 있나요

결정의 비용을 한 번 호출하는 가격으로만 보면 기회 일부를 놓칩니다.
같은 업무를 끝내는 데 다음 비용이 반복되는지 확인해야 합니다.

1. **자료를 얻는 비용:** 같은 파일·문서·설정을 다시 읽습니다.
2. **자료를 해석하는 비용:** 같은 내용에서 같은 사실과 조건을 다시 뽑습니다.
3. **판단을 만드는 비용:** 입력과 기준이 같아도 같은 질문을 다시 풉니다.
4. **결과를 확인하는 비용:** 이미 확인한 상태를 다시 검사하거나, 무엇을 검사할지 매번 새로 정합니다.
5. **잘못된 판단을 고치는 비용:** 사용자가 재지시하고 AI가 읽기·수정·검사를 반복합니다.

‘모든 것이 결정’이라는 관점은 이 흐름을 연결하는 데 도움이 됩니다.
제품으로 만들려면 한 질문의 입력, 출력, 유효한 조건을 더 좁혀야 합니다.
‘무엇이든 잘 결정한다’는 목표로는 무엇을 측정하고 어디까지 책임질지 정하기 어렵습니다.

## 제품을 구성할 공통 기능

| 기능이 답할 질문 | 입력과 출력 | 줄일 수 있을 비용 | 어려운 조건 |
|---|---|---|---|
| 지금 무엇이 바뀌었나요? | 확인할 대상과 이전 관찰을 받아 현재 값·변경점·미확인을 돌려줍니다. | 반복 읽기와 긴 문맥 전달 | 놓친 대상이 있으면 낡은 상태를 최신으로 오해할 수 있습니다. |
| 이전 판단을 그대로 써도 되나요? | 질문·근거·기준·현재 조건을 받아 재사용 가능 여부와 다시 볼 범위를 돌려줍니다. | 같은 자료의 반복 검토 | 질문과 파일이 같아도 권한·외부 상태·검토 목적이 달라질 수 있습니다. |
| 실행해서 무엇이 실제로 달라졌나요? | 예상한 변화와 실행 뒤 상태를 비교해 완료·남은 일·충돌·미확인을 돌려줍니다. | 중복 실행과 잘못된 완료 보고 뒤의 재작업 | 원하는 결과를 읽거나 시험할 방법이 있어야 합니다. |

이 중 두 번째를 시험했습니다. 첫 번째와 세 번째도 기존 시제품에서 일부 기능을 확인했습니다.
[앞선 여섯 시제품의 범위](findings/2026-10-05-ideas-lab.md)
어느 하나도 새로운 범주의 제품이라고 단정하지 않습니다. 캐시, 변경 감지와 실행 검증은 이미 널리 쓰는 방법입니다.
차별화할 수 있을지는 AI 업무에서 무엇을 안전하게 재사용할지 정하는 어려움을 실제로 줄이는지에 달려 있습니다.

## 현재 검토하는 세 가지 개선

사용자는 세 후보 모두 좋으며, 작업을 이어가는 기능도 Stage와 다르게 만들 수 있다고 말했습니다.
이후 Stage에 결정 기록도 있다는 점과 AI가 뛰어놀 무대라는 목적을 다시 강조했습니다.
현재는 세 가지 모두 Stage가 제공할 능력으로 함께 검토합니다. 기능별 검증은 유지합니다.
개인의 기준을 프로젝트 밖에서 모으고 본인의 선택을 돌아보는 [Avatar / Clone 구상](avatar.md)은 별도로 기록합니다.
사용자의 최신 요청에 따라 새 구현은 보류합니다.
기존 코드만으로 충분한지와 추가 기능이 필요한지를 먼저 확인합니다.
별도 제품으로 나눌지는 독립적인 쓰임새가 입증된 뒤 검토합니다.

| 후보 | 쌓아 두는 것 | 목적 | 확인한 범위 |
|---|---|---|---|
| 사람의 판단 기준을 모아 적용합니다. | 어떤 상황에서 무엇을 우선하는지, 그 근거와 예외 | 새 상황에서도 같은 기준을 일관되게 적용합니다. | 기존 Distill에 수집·규칙 생성·검색 코드가 있습니다. 이번 정책의 효과는 아직 시험하지 않았습니다. |
| 이전 판단이 여전히 유효한지 확인하고 다시 씁니다. | 특정 입력과 기준에서 내린 결론, 사용한 근거와 유효한 조건 | 같은 판단을 반복하는 시간과 사용량을 줄입니다. | 코드 리뷰에서 입력이 완전히 같은 경우만 시험했습니다. |
| 실제로 끝난 일을 확인하고 중단된 작업을 이어갑니다. | 실행 전 상태, 기대 결과, 실행 뒤 확인한 사실 | 끝난 일을 중복 실행하거나 일부만 끝내고 완료했다고 보고하는 문제를 줄입니다. | 로컬 파일의 제한된 복구 시제품을 시험했습니다. 범용 도구 복구나 제품 효과는 확인하지 않았습니다. |

첫 후보의 자세한 연구 질문은 [판단 기준 수집과 적용](decision-criteria.md)에 있습니다.
사용자가 제안한 [판단 순서](decision-criteria.md#decision-order)는 궁극적 목적을 먼저 확인하고, 부족하면 Distill을 조회한 뒤, 그래도 근거가 없을 때 사람에게 묻는 흐름입니다.
사용자는 Distill의 처음 목적은 룰 생성이었다고 설명했습니다. [기존 구현과의 관계](findings/2026-10-05-distill.md)를 정리했습니다.
첫 후보는 룰 생성에서 이미 해결한 부분과, 새 상황에 기준을 적용할 때 더 필요한 부분을 나눠 검증합니다.
Stage·Distill과 겹치는 기능을 신규 아이디어의 성과로 세지 않습니다. 세 후보가 별도 신제품이라는 근거는 아직 없습니다.
기준이 같아도 상황이 달라지면 다른 결론을 낼 수 있습니다. 일관성을 확보한다는 것은 적용할 기준과 예외를 일관되게 다룬다는 뜻입니다.

두 번째 후보는 코드 리뷰에만 한정하지 않습니다. 아래는 앞으로 적용을 시험할 수 있는 예시입니다.

| 적용 예시 | 다시 쓸 판단 | 다시 확인해야 할 변화 |
|---|---|---|
| 문서 분류 | 같은 문서를 같은 분류 체계에서 어디에 넣을지 | 문서 내용, 분류 기준, 분류 목적이 바뀌었는지 |
| 기획안 검토 | 특정 기획안이 정한 요구사항을 충족하는지 | 기획안, 요구사항, 판단에 사용한 사실이 바뀌었는지 |
| 도구 선택 | 특정 조건에서 어느 도구를 사용할지 | 목적, 도구의 기능·사용 가능 여부, 권한과 입력 조건이 바뀌었는지 |

이 예시의 효과는 아직 시험하지 않았습니다. 질문 문장이 비슷하다는 이유만으로 답을 재사용하지 않습니다.
판단에 영향을 주는 조건이 그대로인지 확인할 수 있어야 합니다. 새 관점의 검토를 요청했다면 다시 검토합니다.
과거에 도구를 골랐다는 판단을 재사용하는 것과 그 도구의 행동을 다시 실행하는 것도 구별해야 합니다.

세 번째 후보는 Stage의 실행·검증·재개 기능과 겹칩니다.
여러 세션에서 이어가는 문제는 [Stage의 작업·결정 기록을 연결하고 필요한 내용을 읽히는 방식](session-continuity.md)부터 검토합니다.
별도 실행기로 만든다면 도구 호출 하나가 실제로 끝났는지 확인하는 범위부터 검토합니다.
Stage 확장과 독립 실행기 중 어느 쪽이 나을지는 비교해야 합니다.

각 후보의 독립적인 쓰임새와 연결 방법은 [제품 구성과 구현 제안](product-design.md)에 적었습니다.
첫 번째가 제공한 기준을 두 번째가 사용한다면, 기준이 바뀔 때 관련 판단도 다시 확인해야 합니다.
세 번째는 판단을 재사용했더라도 현재 실행 조건과 실제 결과를 따로 확인해야 합니다.
이 연결은 설계 제안이며 아직 구현하지 않았습니다.

## 이번 실험을 고른 이유

저장소의 [리뷰 비용 관측](../../state/observations/O-00000024.md)에는 반복 검토의 부담이 기록돼 있습니다.
리뷰 때마다 자료를 새로 읽고 판정한다는 점에서 사용자가 말한 결정 비용과 직접 연결됩니다.
다만 과거 토큰 집계의 원본 계정 기록을 이번에 다시 분석하지는 않았습니다. 당시 기록의 한계도 함께 따릅니다.

최근 작업 로그 세 개를 확인했지만 코드·기준·리뷰 환경 전체의 해시는 없었습니다.
따라서 실무에서 완전히 같은 입력을 얼마나 다시 검토했는지는 아직 모릅니다.
이번에는 실제 과거 결함 두 개를 복원하고, 반복 비율을 정한 조건에서 비교합니다.
[실험 방법](experiments/review-reuse/README.md)
시험을 마친 뒤 [호출·시간·사용량과 적용 한계](findings/2026-10-05-review-reuse.md)를 정리했습니다.

반복 호출을 없앤 만큼 비용이 줄어드는 것은 예상할 수 있습니다.
확인할 것은 캐시를 만들고 검사하는 비용까지 포함해 얼마나 줄었는지, 변경 뒤에도 옛 판정을 내놓지 않는지입니다.
처음 판정이 틀렸다면 재사용해도 틀립니다. 재사용과 독립 재검토는 목적이 다릅니다.

## 제품 후보로 남길 기준

- 실제 업무에서 반복하는 입력이 충분히 자주 나와야 합니다. 실험자가 정한 반복 비율로 대신하지 않습니다.
- 근거가 바뀌면 판정을 다시 해야 합니다. 중요한 변경을 놓치면 비용이 줄어도 적용하지 않습니다.
- 새 관점의 재검토를 요청하면 기존 답을 돌려주지 않아야 합니다.
- 줄인 모델 비용이 기록·검사·운영 비용보다 커야 합니다.
- 잘못 재사용해서 생긴 재작업까지 포함해 사용자가 맡긴 일을 더 잘 끝내야 합니다.

**판단 한 번의 가격과 함께, 같은 판단을 왜 다시 하게 되는지를 기록하는 것**부터 시작해야 합니다.
실험에서 확인한 결과와 실무에서 더 관측할 조건을 함께 보고 다음 범위를 정합니다.

사용자가 이어서 제안한 [사람의 판단 기준을 모으는 아이디어](decision-criteria.md)는 별도 후보로 기록했습니다.
어떤 기준으로 선택하는지 수집하고, 그 기준을 새로운 상황에 적용하며 개선하는 연구입니다.

# 다른 AI가 바뀐 기준으로 이어서 일하는지 시험했습니다

2026-10-07. W-00000277. 이 문서는 처음 두 시험의 기록입니다. 이후 결과는 [기록 절차를 묶은 시험](2026-10-07-bundled-recording.md)에 있습니다.
**두 번째 시험에서 여섯 사례의 코드·기록은 맞았습니다. 정상 종료는 다섯 사례이며 한 사례는 시간 제한에 걸렸습니다.**
당시 전체 완료 검사는 실패했습니다. 첫 시험에서는 기준을 바꾸자 두 AI 모두 새 기준에 맞게 코드를 만들었지만 인계 기록은 세 사례에서 틀렸습니다.
처음에는 검사기가 이를 놓쳤고 Claude의 독립 리뷰가 찾아냈습니다. 후속 시험은 아래에 따로 기록합니다.
속도나 비용이 줄었다고 결론 내릴 자료는 아직 부족합니다.

## 무엇을 시험했나요

Claude와 Codex가 각각 프로젝트 기준을 저장하고 `parse_port`를 만들었습니다. 두 결과를 조건별로 복사했습니다.
다른 AI의 새 세션이 앞선 대화 이력 없이 `parse_host`를 만들었습니다. Stage가 만든 인계 글과 실제 파일을 받았습니다.
각 사례의 입력과 기대 결과는 [실행 계획](../integration/real-host-plan.md)에 먼저 고정했습니다.

기존 기준은 잘못된 입력에 `ConfigError`를 던집니다. 새 기준은 `None`을 반환합니다.
현재 기준을 주지 않는 비교 조건에서는 AI가 직접 방식을 고르고 이유를 적도록 했습니다.
이 조건에도 앞선 카드의 적용 기록과 `ConfigError`를 쓰는 코드가 남았습니다. 조회를 연결하지 않은 조건이며,
과거 기준의 영향까지 없앤 대조군은 아닙니다. 두 AI는 앞선 코드와 맞추려고 `ConfigError`를 골랐다고 답했습니다.
실제 개인 DB나 사용자 발언은 쓰지 않았습니다. Avatar에 넣은 선택·이유·확인도 명시한 시험용 자료입니다.

## 첫 시험의 실제 결과

| 보낸 AI → 받은 AI | 받은 기준 | 잘못된 입력의 실제 결과 | 앞선 파일 | 걸린 시간 |
|---|---|---|---|---:|
| Claude → Codex | 없음 | `ConfigError` | 그대로 | 151.1초 |
| Claude → Codex | 기존 기준 v1 | `ConfigError` | 그대로 | 89.8초 |
| Claude → Codex | 새 기준 v2 | `None` | 그대로 | 79.9초 |
| Codex → Claude | 없음 | `ConfigError` | 그대로 | 71.7초 |
| Codex → Claude | 기존 기준 v1 | `ConfigError` | 그대로 | 84.6초 |
| Codex → Claude | 새 기준 v2 | `None` | 그대로 | 53.1초 |

시간에는 코드 작성, 검사, 기준 조회, Avatar 기록이 모두 들어갑니다. 앞선 과제를 만드는 시간은 별도입니다.
Claude가 약 62.2초, Codex가 약 109.0초 걸렸습니다. AI 호출은 보낸 세션 2개와 받은 세션 6개입니다.
호출마다 내부 API 요청이 여러 번 오갈 수 있으므로 API 요청 8건이라고 세지는 않습니다.

받은 AI는 기준을 쓸 네 사례에서 공개 CLI로 현재 버전을 다시 확인하고 응답을 저장했습니다.
v2를 받은 두 사례는 v1 판단에 `superseded`를 남겼습니다. `parse_port`의 바이트는 여섯 사례 모두 바꾸지 않았습니다.
이전 파일을 자동으로 새 기준에 맞춰 고치는 기능은 이번 과제가 아니었습니다. 기준 적용 시점이 달라 두 함수의 오류 처리도 달라졌습니다.
저장한 답변을 읽었을 때 진행을 막는 질문은 없었습니다. 실행 중 추가 설명도 입력하지 않았습니다.
전체 도구 기록에서 모든 질문 문장을 분류한 수치는 아닙니다. 완결된 지시문을 줬으므로 재질문을 줄였다는 증거로 보지 않습니다.

Avatar에는 실제 고른 처리 방식과 적용 참조가 저장됐습니다. 시험용 개인 기준을 제안한 뒤 확인하면 @1을 보존하고 @2를 내보냈습니다.
기준을 적용한 네 사례에는 Distill의 이력도 첨부됐습니다. 확인되지 않은 기준과 다른 프로젝트의 기준을 제외하는 검사는
앞선 [공개 CLI 시험 27개](../integration/evidence/2026-10-06-contract/calls.json)가 담당합니다.

## 리뷰에서 확인한 실패

- Claude → Codex의 C0에서 현재 저장소가 없는데도 옛 기준을 `superseded`라고 적었습니다. 조회하지 못한 상태는 `unknown`입니다.
  어떤 새 기준이 대신했는지 근거 없이 단정했습니다. 코드 동작이 맞아도 이 기록은 틀렸습니다.
- Codex → Claude의 C1·C2에서는 `parse_host`를 끝내고도 `Next action`에 다시 구현하라고 남겼습니다.
  다음 AI가 끝낸 일을 남은 일로 오해할 수 있습니다.
- C1 검사기는 앞선 세션이 남긴 적용 기록만으로도 통과했습니다. 실제 두 수신 세션도 기록을 덧붙였지만,
  그 사실을 검사기가 증명한 것은 아니었습니다.

실패하는 테스트 세 개를 추가한 뒤 검사를 고쳤습니다. 이제 앞선 적용 기록의 개수를 빼고 새 기록을 봅니다.
근거 없는 `superseded` 기록과 끝낸 함수를 다시 구현하라는 기록도 실패로 처리합니다.
첫 시험을 다시 검사한 결과는 **여섯 사례 중 세 사례 통과**입니다. AI의 원본을 고치거나 다시 실행하지 않았습니다.
[독립 리뷰](../integration/evidence/2026-10-07-handoff/qa-review.json)와
[더 엄격하게 검사한 결과](../integration/evidence/2026-10-07-handoff/host-runs.json)를 보존했습니다.

## 검사기가 잘못 판정한 과정도 남겼습니다

첫 검사기는 `Applied criteria:`가 줄 맨 앞에 있어야 읽었습니다. Stage가 지원하는 `- Applied criteria:`를 놓쳤습니다.
그래서 Claude → Codex의 세 사례에서 코드와 실제 조회는 맞았지만 적용 기록이 없다고 판정했습니다.

글머리표와 날짜가 붙은 기록을 재현한 테스트가 실패하는 것을 먼저 확인했습니다. 검사기를 고친 뒤 여섯 개의 합성 테스트를 통과했습니다.
AI를 다시 호출하지 않고 보존한 파일을 다시 검사했습니다. 제품 코드와 기대 동작은 바꾸지 않았습니다.
[원래 판정](../integration/evidence/2026-10-07-handoff/host-runs-initial.json), [수정 이유와 두 검사기의 digest](../integration/evidence/2026-10-07-handoff/checker-correction.json),
[글머리표 수정 뒤의 판정](../integration/evidence/2026-10-07-handoff/host-runs-after-prefix-fix.json)을 모두 보존했습니다.
이때 여섯 사례를 통과시킨 판정은 이후 독립 리뷰에서 위 누락을 찾아 정정했습니다.

## 자동으로 확인하지 못한 기록

두 AI 모두 파일 해시를 `## Evidence`의 문장으로 적었습니다. 현재 Stage 계약은 `## Progress`의 `Evidence: {JSON}`을 읽습니다.
그래서 원래 packet에는 증거가 없다고 나왔습니다. 받은 AI는 원래 카드와 파일을 읽어 해시를 확인했고, 독립 검사기도 앞선 파일이 그대로인지 확인했습니다.
**Stage가 이 실행에서 앞선 파일 증거를 자동으로 대조했다고 주장할 수는 없습니다.**

시험 지시문에 해시를 남기라고만 적고 정확한 저장 형식을 주지 않았습니다. 후속 시험에서는
Stage 문서의 실제 기록 형식을 전달합니다. 제품 코드는 그대로 둡니다.
AI가 자유롭게 작성한 기록을 기계가 그대로 읽을 수 있다고 가정하면 중요한 근거가 빠집니다.

## 첫 시험의 비용에서 알 수 있는 것

| 받은 AI | 기준 없음 | 기존 기준 v1 | 새 기준 v2 |
|---|---:|---:|---:|
| Claude가 보고한 금액 | $0.319896 | $0.296213 | $0.268666 |
| Codex가 보고한 입력 토큰 | 351,528개 | 458,231개 | 351,239개 |
| 위 Codex 입력 중 캐시에서 읽은 토큰 | 333,056개 | 425,472개 | 331,008개 |

Claude의 금액은 CLI가 보고한 추정치이며 실제 청구액이 아닙니다. Codex는 금액을 보고하지 않아 계산하지 않았습니다.
두 서비스는 입력과 캐시를 보고하는 방식도 다릅니다. 표의 수치를 서로 같은 단위로 비교하지 않습니다.

기준을 저장하고 조회하는 명령 자체는 앞선 시험에서 27개 합계 약 2.39초였습니다. 이번 AI 작업은 사례당 약 53~151초였습니다.
다만 과제 범위가 다르므로 이 차이를 조회의 순수 효과로 해석하지 않습니다.
이번 기록에서 다음 연구로 살필 부분은 **작은 명령 결과를 받은 뒤 AI가 다시 문맥을 읽고 다음 명령을 고르는 과정**입니다.
단계가 많아지면 같은 문맥도 여러 번 입력됩니다. 정해진 기록 절차를 코드로 묶으면 이 반복을 줄일 여지가 있지만, 아직 비교 실험으로 검증하지 않았습니다.

각 조건을 한 번만 실행했고 앞선 결과를 세 조건이 공유했습니다. 캐시 상태와 실행 순서도 통제하지 않았습니다.
따라서 일반적인 성공률이나 비용 절감률을 제시하지 않습니다. 기준이 없는 조건과 기존 기준 조건은 같은 동작이 나와, 두 조건만으로는 기준 적용 여부를 구별하지 못했습니다.
새 기준 조건과 비교하고 실제 조회 기록까지 확인했을 때 기준 변경을 따른 차이를 확인할 수 있었습니다.

## 실행 환경과 원본

- Codex CLI 0.160.0, 요청 모델 `gpt-6-sol`, reasoning `high`.
- Claude Code 2.1.289, 요청 모델 `opus[1m]`; 원본 응답의 모델은 `claude-opus-5-5`입니다.
- macOS, 임시 프로젝트, 임시 DB. Claude 훅은 이번 실행에서 껐고 Codex의 사용자 config도 이번 실행에만 제외했습니다.
- 이전에 사용량 오류가 난 실행기는 `gpt-5.6-sol`을 호출했습니다. 이번 성공은 다른 모델·호출 경로에서 관찰했습니다. 기존 오류의 원인을 해결했다고 단정하지 않습니다.
- 공개 CLI 사용법을 명시한 시험입니다. 스킬 자동 선택, 설치된 플러그인의 자연스러운 호출, 무인 드라이버까지 검증하지 않았습니다.

조회가 파일 작성보다 먼저였는지는 검사기의 자동 판정 범위가 아닙니다. 첫 시험의 두 C2 원본에서는 독립 리뷰가 순서를 직접 확인했습니다.

## 기록 절차를 명시한 후속 시험

[후속 계획](../integration/real-host-followup-plan.md)을 새 AI 호출 전에 고정했습니다.
제품 코드는 그대로 두고 Stage의 JSON 형식, 모르는 상태의 처리, 다음 할 일 갱신을 지시문에 명시했습니다.
보낸 세션 두 개와 받은 세션 여섯 개를 새로 실행했습니다. 첫 시험의 실패를 새 결과로 덮지 않습니다.

| 보낸 AI → 받은 AI | 받은 기준 | 코드·기록 검사 | 호스트 종료 | 걸린 시간 |
|---|---|---|---|---:|
| Claude → Codex | 조회 연결 없음 | 통과 | 180초 제한, 종료 코드 124 | 180.0초 |
| Claude → Codex | 기존 기준 v1 | 통과 | 정상 | 129.0초 |
| Claude → Codex | 새 기준 v2 | 통과 | 정상 | 70.3초 |
| Codex → Claude | 조회 연결 없음 | 통과 | 정상 | 74.1초 |
| Codex → Claude | 기존 기준 v1 | 통과 | 정상 | 84.2초 |
| Codex → Claude | 새 기준 v2 | 통과 | 정상 | 59.5초 |

Stage는 여섯 인계 글에서 앞선 파일 해시가 일치한다고 보고했습니다. 여섯 결과의 앞선 파일도 그대로입니다.
새 적용 기록, 기준 상태, 다음 할 일, Avatar의 선택·개인 기준 확인을 따로 검사했습니다.
Distill 참조를 적용한 C1·C2 네 사례는 첨부한 이력에 해당 참조가 있는지도 확인했습니다.
C0 두 사례는 적용한 참조가 없으므로 이력 검사의 대상이 아닙니다. 검사 결과의 `avatar_applied_history: true`를 이력을 첨부했다는 뜻으로 읽지 않습니다.
[저장한 결과 검사](../integration/evidence/2026-10-07-handoff-followup/saved-case-observations.json)는 여섯 사례 모두 통과했습니다.

시간 제한에 걸린 Codex는 코드와 기록을 만들고 자체 검사도 마쳤습니다. 하지만 `turn.completed`와 최종 사용량을 받지 못했습니다.
따라서 정상 완료로 세지 않으며 사용량도 0으로 적지 않고 미확인으로 둡니다. 미리 정한 한도에 따라 추가 재시도는 하지 않았습니다.
이 두 번째 시험을 `--host-evidence .stage/research/llm-work/integration/evidence/2026-10-07-handoff-followup`으로 지정하면
`verify_integration.py --require-real-hosts`는 **종료 코드 1**입니다. 기본 대상은 이후 새 실험으로 바뀌었습니다.
이 검사를 완화해 통과시키지 않았고 W-00000277도 완료 처리하지 않았습니다.

보존한 답변 모음을 읽었을 때 같은 설명을 다시 요구한 질문과 작업을 막는 질문은 각각 0건이었습니다.
작업을 마친 Claude가 앞선 `parse_port`도 새 기준으로 바꿀지 물은 질문은 1건입니다.
실행 중 추가 답변은 입력하지 않았습니다. 이 수치는 저장한 Codex 메시지와 Claude 최종 답변을 읽은 결과이며 모든 내부 이벤트를 분류한 수치는 아닙니다.

후속 독립 리뷰는 C1·C2 네 사례 모두 조회가 파일 작성보다 먼저였음을 원본에서 확인했습니다.
Claude → Codex C1은 27~28번째 줄의 조회 뒤 29번째 줄에서 작성했고, C2는 14~15번째 줄 뒤 17번째 줄에서 작성했습니다.
Codex → Claude C1은 10번째 줄의 조회 뒤 13번째 줄에서 작성했고, C2는 15번째 줄 뒤 19번째 줄에서 작성했습니다.
줄 번호는 각 사례의 `model/stdout.jsonl` 기준입니다. 검사기가 순서를 자동으로 판정했다는 뜻은 아닙니다.

서로 다른 지시문을 썼고 반복 횟수도 적어, 첫 시험보다 일반적인 성공률이 얼마나 좋아졌는지 수치로 말하지 않습니다.

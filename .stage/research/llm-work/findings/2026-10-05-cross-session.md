# 다른 AI가 실제 코드 수정을 이어받게 했습니다

**현재 상태를 미리 읽혀 주면 일부 모델 호출을 줄일 수 있었습니다. 전체 시간과 품질이 좋아졌다는 결과는 얻지 못했습니다.**
이전 기록만 준 조건은 이어받는 동안 모델을 13번 호출했습니다. 현재 파일도 정리해 준 조건은 11번 호출했습니다.
그러나 독립 검증까지 걸린 시간은 각각 155.5초와 156.6초였습니다.

검사 구성에도 문제가 있었습니다. 한 사례의 전체 테스트는 AI에게 요구하지 않은 API 변경까지 검사했습니다.
이 실패를 AI가 인계를 잘못 받았다는 증거로 해석하지 않습니다.
원래 정한 판정과 실제로 통과한 검사, 평가 구성의 문제를 모두 남겼습니다.

## 무엇을 했나요

본래 연구의 질문은 **AI가 다음 행동을 고르기 위해 상황을 다시 파악하는 비용을 줄일 수 있느냐**입니다.
앞선 [입력 비교](2026-10-05-context-handoff.md)는 짧은 질문의 판정만 확인했습니다.
이번에는 AI가 고른 수정을 임시 파일에 적용하고, 다른 AI가 이어받아 실제 테스트까지 실행했습니다.

과거에 실제로 고쳤던 결함 두 개를 사용했습니다.

- 마일스톤의 완료 기준을 여러 번 주면 마지막 값만 남는 결함입니다.
- 다른 작업이 소유한 회고 번호와 충돌하면 새 번호로 넘어가는 결함입니다.

첫 AI가 파일을 한 번 수정한 직후 멈췄습니다. 수정은 적용됐지만 결과 응답은 다음 AI에게 넘기지 않았습니다.
같은 수정 상태를 복사해 아래 두 조건에서 시작했습니다.

| 조건 | 다음 AI가 처음 받은 내용 |
|---|---|
| 이전 기록 | 목적, 도구 사용법, 첫 AI의 공개 요청과 응답을 모두 받았습니다. 마지막 수정의 결과 응답은 없습니다. |
| 현재 상태 포함 | 같은 목적과 도구 사용법에 직전 수정 요청·이유, 앞선 검사 결과, 인계 시점의 파일 내용·해시를 붙였습니다. |

각 결함을 Claude → Codex, Codex → Claude로 넘겼습니다.
첫 구간은 네 번, 이어받기는 여덟 번입니다. 독립적인 결함은 두 개이며, 같은 조건을 반복 측정하지는 않았습니다.
회고 사례에는 두 조건 모두 인계 사이에 보존할 주석을 추가했습니다.

수정할 파일은 한 개로 제한했습니다. AI는 읽기, 정확한 문자열 교체, 지정한 검사, 완료 보고 중 다음 행동 하나를 골랐습니다.
프로그램이 그 행동을 수행하고 결과를 돌려줬습니다. 각 판단은 별도 CLI 프로세스에서 실행했습니다.
Claude Code·Codex의 내장 세션 재개나 현재 Stage 플러그인 전체를 시험한 결과는 아닙니다.

## 결과

아래 수치는 이어받기 네 번씩을 합한 값입니다. 첫 AI가 남긴 상태는 각 비교 쌍에서 같습니다.

| 측정한 값 | 이전 기록 | 현재 상태 포함 |
|---|---:|---:|
| 목적에 적은 결함의 회귀 검사 통과 | 4/4 | 4/4 |
| 미리 정한 전체 검사 통과 | 2/4 | 2/4 |
| 모델 호출 | 13번 | 11번 |
| 모델이 요청한 파일 읽기 | 3번 | 1번 |
| 프로그램이 미리 읽은 파일 | 0개 | 4개 |
| 모델이 요청한 검사 | 4번 | 4번 |
| 직전 수정과 같은 요청을 다시 보냄 | 0번 | 0번 |
| 거절된 수정 / 내용이 그대로인 쓰기 | 0번 / 0번 | 0번 / 0번 |
| 자료 준비부터 독립 검증까지 걸린 시간 | 155.5초 | 156.6초 |

첫 구간에서 두 방식에 공통으로 쓴 모델 호출은 10번입니다. 이를 포함한 전체 호출은 34번입니다.
첫 구간 네 번에는 복원과 첫 수정을 포함해 약 74.2초가 걸렸습니다.
위 비교 시간은 그 뒤 파일 복사를 마친 시점부터 잽니다. 자료 구성, 모델 호출, 도구 실행과 독립 검증을 포함합니다.
복사 시간과 자료 준비 시간도 원본에 따로 저장했습니다.

**파일을 읽는 일 자체가 줄어든 것은 아닙니다.** 프로그램이 미리 수행한 읽기까지 합하면 3번에서 5번으로 늘었습니다.
다만 무엇을 읽을지 모델에 먼저 물어보는 호출을 두 번 덜 했습니다.
현재 상태를 미리 넘겨 주는 비용과 모델 호출을 줄이는 효과를 함께 봐야 합니다.

모든 인계에서 대상 밖 파일은 바뀌지 않았습니다. 회고 사례 네 번 모두 추가한 주석을 보존했습니다.
다만 이 사례에서는 첫 AI의 수정만으로 지정한 회귀 검사를 통과했습니다. 다음 AI는 파일을 더 수정하지 않았습니다.
따라서 주석 보존 결과로 복잡한 동시 수정까지 안전하다고 주장하지 않습니다.

### 사용량은 줄었지만 전체 시간은 줄지 않았습니다

| 이어받은 AI | 조건 | 호출 수 | 보고된 입력 토큰 | 보고된 출력 토큰 | Claude 보고 비용 |
|---|---|---:|---:|---:|---:|
| Claude | 이전 기록 | 6번 | 96,792개 | 967개 | $0.396814 |
| Claude | 현재 상태 포함 | 6번 | 73,465개 | 1,503개 | $0.308866 |
| Codex | 이전 기록 | 7번 | 115,822개 | 628개 | 미제공 |
| Codex | 현재 상태 포함 | 5번 | 65,854개 | 530개 | 미제공 |

입력 토큰은 Claude 약 24.1%, Codex 약 43.1% 줄었습니다.
Claude의 이어받기 비용은 약 22.2% 줄었습니다. 첫 구간까지 포함한 Claude 보고 비용은 $0.808736입니다.
실제 청구서는 확인하지 않았고 Codex 비용은 계산하지 않았습니다.
Claude 입력에는 캐시를 만들거나 읽는 토큰을 포함했습니다. 두 호스트의 사용량을 같은 과금 방식으로 보지 않습니다.

검사를 포함한 시간은 비교 쌍 네 개 중 두 개에서 줄고 두 개에서 늘었습니다.
독립 검증에 쓴 시간도 조건별 합계가 약 73.0초와 87.5초로 달랐습니다.
CLI 시작과 서버 응답, 로컬 검사 시간의 변동을 제거하지 못했습니다.
각 조건을 한 번씩만 실행했으므로 속도가 개선됐다고 결론 내리지 않습니다.

Claude는 `claude-sonnet-5-5`, Codex는 CLI 기본 모델과 low effort를 요청했습니다.
CLI는 각각 2.1.289, 0.146.0이었습니다. 서버의 모델 버전을 양쪽 모두 고정한 비교는 아닙니다.
두 호스트의 성능 순위를 매기지 않습니다.

## 전체 검사에서 나온 실패는 어떻게 해석하나요

실험을 구성하면서 수정 후 커밋의 Stage 트리를 꺼내고 대상 파일만 수정 전 코드로 바꿨습니다.
알려진 수정 후 코드는 전체 모듈을 통과하는지 확인했습니다.
하지만 모델을 돌리기 전에는 수정 전 코드의 **전체 모듈 실패 내역**까지 확인하지 않았습니다.

회고 사례의 수정 커밋에는 두 변화가 함께 들어 있었습니다.

1. 다른 작업의 회고 번호와 충돌하면 중단합니다. 이것이 AI에게 준 목표였습니다.
2. 회고 번호를 구하는 함수를 작업 번호 하나만 받도록 바꿉니다. 전체 테스트는 이 새 API도 검사했습니다.

AI는 첫 번째 목표를 충족했습니다. 두 번째 테스트는 인자 수가 맞지 않아 실패했습니다.
이 테스트는 해당 커밋에서 추가됐습니다. 기존에 통과하던 검사를 AI가 망가뜨렸다고 볼 수 없습니다.
실험 도구는 지정한 회귀 검사만 실행할 수 있게 했고, 전체 모듈 실패를 모델에 돌려주지도 않았습니다.

원래 정한 기준상 전체 통과는 여덟 번 중 네 번입니다. 이 판정을 사후에 성공으로 바꾸지 않았습니다.
원본의 `false_completion`은 미리 정한 전체 검사와 완료 보고가 맞지 않았다는 뜻입니다.
이를 모델이 거짓 보고를 했거나 인계에 실패했다는 증거로 사용하지 않습니다.
원인은 목표와 평가 범위를 충분히 맞추지 못한 실험 구성에 있습니다.

별도 진단에서 모델을 다시 호출하지 않고 수정 전 상태의 전체 모듈을 실행했습니다.
94개 검사 중 목표로 삼은 결함 한 개와 새 API 검사 한 개가 실패했습니다.
AI가 수정한 뒤에는 목표로 삼은 검사만 통과했고, 새 API 검사는 그대로 실패했습니다.
원래 실행과 후속 진단을 분리해 보존했습니다.
[진단 코드](../experiments/cross-session/diagnose.py), [진단 기록](../experiments/cross-session/diagnostics.json)

## 새로 확인한 문제: ‘현재 파일’도 곧 과거 기록이 됩니다

Claude가 마일스톤 수정을 이어받은 한 번의 실행에서 다음 일이 일어났습니다.

1. 인계 때 받은 파일을 보고 남은 코드를 수정했습니다.
2. 수정 결과를 받았고 회귀 검사도 통과했습니다.
3. 그런데 인계 자료에 계속 남아 있는 파일과 새 해시가 다르다며 파일을 다시 읽었습니다.
4. 최신 파일을 읽은 뒤 완료를 보고했습니다.

인계 자료는 매 호출에 다시 붙었습니다. 따라서 첫 시점의 파일도 계속 `current_files`라는 이름으로 보였습니다.
이 실행의 공개 이유에는 그 혼동이 드러났습니다. 같은 현상이 일반적으로 발생한다고 입증한 것은 아닙니다.
[해당 실행 기록](../experiments/cross-session/runs/roadmap_repeated_criteria--codex-to-claude/state_packet/result.json)

**확인한 내용을 남길 때는 무엇을 확인했는지뿐 아니라 언제까지 유효한지도 다뤄야 합니다.**
다음 개선을 시험할 근거가 생겼습니다.

- 인계 순간의 파일은 그 시점의 관찰이라고 표시합니다.
- 이후 쓰기가 성공하면 어떤 관찰을 대체했는지 연결합니다.
- 테스트 통과 기록은 검사한 파일 버전과 함께 둡니다.
- 다른 세션이 파일을 바꿨다면 지금 하려는 행동에 필요한 부분을 다시 확인합니다.

이 설계가 효과를 냈다는 결과는 아직 없습니다. 오래된 자료를 모두 지우자는 제안도 아닙니다.
과거 기록은 이유를 설명하고, 최신 관찰은 지금 가능한 행동을 정하는 데 쓰도록 구별합니다.

## Stage에 무엇을 제안할 수 있나요

Stage에는 작업·결정·인계 기록이 이미 있습니다. 이번 결과는 별도 저장소가 필요하다는 근거가 아닙니다.
그 기록과 실제 파일·검사 결과를 연결하는 방법을 더 시험할 수 있습니다.

| 다음에 시험할 개선 | 기대하는 이점 | 함께 확인할 비용과 위험 |
|---|---|---|
| 다음 행동에 필요한 현재 사실을 프로그램이 먼저 확인합니다. | 단순한 확인을 요청하는 모델 호출을 줄일 수 있습니다. | 필요 없는 파일도 읽거나 오래된 관찰을 계속 제공할 수 있습니다. |
| 수정·관찰·검사 기록을 같은 버전과 연결합니다. | 무엇이 아직 유효한지 다시 추론하는 부담을 줄일 수 있습니다. | 기록을 갱신하는 비용과 갱신 누락을 확인해야 합니다. |
| 목적과 완료 검사를 실행 전에 대조합니다. | 요청 범위와 다른 검사 때문에 성공·실패를 잘못 세는 일을 줄일 수 있습니다. | 검사를 좁히다가 기존 동작의 문제를 놓치지 않아야 합니다. |

다음 비교에서는 목표와 전체 검사의 범위를 먼저 맞춥니다.
그 뒤 같은 최신 파일을 제공하되, 관찰 시점과 후속 변경을 분명히 연결하는 효과만 따로 비교합니다.
현재 Stage의 인계 절차를 제대로 따른 경우와도 대조해야 제품에 적용할 근거가 됩니다.

이번에는 두 결함과 제한된 파일 도구만 다뤘습니다.
기준 변경, 여러 파일의 의존 관계, 자율 검색, 동시 쓰기와 외부 API의 중복 실행은 검증하지 않았습니다.
프로세스가 실제로 죽은 시험도 아닙니다. 적용된 수정의 결과 응답을 가린 상황을 통제해 만들었습니다.

실행 수, 입력 해시, 실행기 해시, 호출과 도구 사건의 일치 여부를 검사했습니다.
저장한 수정들을 다시 적용해 첫 구간과 이어받기의 파일 내용도 대조했습니다. 불일치는 없었습니다.
제품 코드, 플러그인 버전과 원래 Stage 작업 카드는 바꾸지 않았습니다.

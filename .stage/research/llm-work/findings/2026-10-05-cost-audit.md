# 비용이 든 곳을 원본 기록에서 다시 확인했습니다

**시간과 금액은 서로 다른 곳에서 많이 들었습니다.**
실제 작업을 이어받은 실험에서는 CLI 실행 구간이 가장 길었습니다.
반면 같은 후속 실험의 Claude 보고 금액은 긴 자료를 읽고 다음 행동을 고르는 조건에서 가장 컸습니다.
입력 토큰 수만 보면 이 차이를 놓칩니다.

이 결과는 기존 실험을 다시 계산한 것입니다. 일반 업무 전체의 비용 순위를 확정한 결과는 아닙니다.
짧은 판단을 몇 번 하고 실제 작업을 몇 번 할지는 실험자가 정했습니다.
호출 횟수와 과제가 다른 묶음의 합계를 업무 한 건의 효율처럼 비교하지 않습니다.

## 확인한 범위

원본 CLI 호출 **125번**을 다시 집계했습니다.

| 실험 | 원본 CLI 호출 | 별도로 구별한 것 |
|---|---:|---|
| 실제 작업 인계·기준 적용·관찰 시점의 후속 시험 | 53번 | 서버 오류 6번, 추출 형식 검사 실패 1번 |
| 같은 판정을 다시 쓰는 시험 | 48번 | 저장한 응답 16개는 새 호출로 세지 않았습니다. |
| 인계할 자료를 줄이는 시험 | 24번 | 실제 작업 한 건의 질문 두 개를 반복했습니다. |

원본과 계획·기존 집계 등 파일 180개를 읽고 해시를 남겼습니다.
같은 호출이 여러 집계 파일에 나와도 원본 호출 파일 한 개만 셌습니다.
후속 실험의 53번·오류 6번·Claude 보고 금액을 기존 집계와 대조했습니다.
나머지 두 실험도 호스트·조건별 토큰과 보고 금액을 대조했습니다. 불일치는 없었습니다.

사용량을 반환하지 않은 호출은 누락으로 남겼습니다. 0원이나 0토큰으로 바꾸지 않았습니다.
금액은 CLI가 보고한 값입니다. 실제 청구서는 확인하지 않았고 Codex 금액은 반환되지 않았습니다.

## 1. 실제 작업에서는 CLI를 기다리는 구간이 가장 길었습니다

실제 파일을 읽고 수정하는 인계 시도 아홉 번을 합쳤습니다.
여덟 번은 정상 완료했고 한 번은 파일을 수정한 뒤 서버 오류가 났습니다.

| 측정 구간 | 시간 합계 | 측정한 전체 시간에서 차지한 비율 |
|---|---:|---:|
| CLI 실행 | 813.76초 | 83.25% |
| CLI 종료 후 독립 테스트 | 163.23초 | 16.70% |
| 조건별 준비·기록 등 나머지 | 0.53초 | 0.05% |
| 합계 | 977.52초 | 100% |

**83.25%를 모델이 생각한 시간이라고 부를 수는 없습니다.**
CLI 안에는 모델 응답 대기, 파일 읽기, 코드 수정, 테스트 실행이 함께 들어 있습니다.
도구마다 시작·종료 시각을 기록하지 않았으므로 이 안을 더 나누지 못했습니다.

호출별 시간을 더한 값이라 병렬 실행의 전체 경과 시간과도 다릅니다.
공통 초기화, 파일 복사, 앞선 세션이 초기 코드를 만드는 시간, 실험 개발 시간은 제외했습니다.
표의 독립 테스트는 테스트 프로그램입니다. 다른 모델이 수행하는 독립 리뷰와 다릅니다.

**해석:** 먼저 CLI 내부에서 모델을 기다린 시간과 도구를 실행한 시간을 나눠야 합니다.
이 표만 보고 테스트가 낭비라고 판단하거나 독립 검사를 없애면 안 됩니다.

## 2. 토큰이 가장 많은 작업이 보고 금액도 가장 크지는 않았습니다

후속 실험에서 Claude를 호출한 23번만 금액으로 나눴습니다.

| 수행한 일 | CLI 호출 | 입력 토큰 | 출력 토큰 | 보고 금액 | 이 실험의 Claude 금액 중 비율 |
|---|---:|---:|---:|---:|---:|
| 받은 관찰을 바탕으로 다시 읽을지 완료할지 판단 | 6번 | 74,666개 | 1,278개 | $0.311420 | 44.26% |
| 실제 코드를 읽고 수정하며 작업을 이어감 | 4번 | 269,336개 | 7,767개 | $0.276019 | 39.23% |
| 원문 또는 기준을 읽고 상황별 선택을 함 | 12번 | 20,440개 | 1,949개 | $0.101202 | 14.38% |
| 원문에서 기준을 추출 | 1번 | 1,402개 | 934개 | $0.014944 | 2.12% |
| 합계 | 23번 | 365,844개 | 11,928개 | $0.703585 | 약 100% |

실제 코드를 수정한 조건은 입력이 약 3.6배였지만 보고 금액은 더 작았습니다.
이 조건의 입력 269,336개 중 **231,286개, 약 85.9%가 캐시 읽기**로 기록됐습니다.
관찰 시점 판단의 캐시 읽기는 0개였고, 입력 대부분은 캐시 생성으로 기록됐습니다.

**해석:** 판단이 짧아도 긴 자료를 새로 입력하면 비용이 커질 수 있습니다.
다시 읽은 양과 캐시를 쓴 양을 함께 봐야 합니다.
과제와 호출 횟수, 출력도 달라서 차이 전부가 캐시 때문이라고 입증한 비교는 아닙니다.
후속 실험에서 이 순서였다는 뜻이며, 모든 Claude 업무의 비용 비중은 아닙니다.

여기서 공급자 캐시는 모델에 보낼 입력 일부를 재사용합니다.
아래의 판정 재사용은 이미 받은 답을 돌려주어 모델 호출 자체를 생략합니다. 두 방식은 따로 셉니다.

## 3. 줄인 호출의 이득은 로컬 확인 비용을 넣어도 남았습니다

같은 조건이면 앞선 판정을 돌려주는 실험의 원본을 다시 확인했습니다.

| 호스트·조건 | 요청 | CLI 호출 | 요청 시간 합계 | 그중 CLI 밖의 처리 시간 |
|---|---:|---:|---:|---:|
| Claude 매번 새로 판단 | 16번 | 16번 | 90.942초 | 0.028초 |
| Claude 같은 조건이면 재사용 | 16번 | 8번 | 44.876초 | 0.033초 |
| Codex 매번 새로 판단 | 16번 | 16번 | 121.177초 | 0.028초 |
| Codex 같은 조건이면 재사용 | 16번 | 8번 | 62.656초 | 0.034초 |

CLI 밖에서는 입력 읽기, 해시 계산, 캐시 조회·저장, 응답 파일의 첫 저장을 수행했습니다.
이 작은 입력에서는 이 시간이 절감 효과를 지우지 않았습니다.
CLI 실행이 없는 캐시 응답의 처리 시간도 표에 포함했습니다.

다만 요청 절반을 의도적으로 중복시켰습니다. 실제 업무의 반복 비율은 모릅니다.
이 실험은 제공한 파일과 기준을 확인했습니다. 모든 의존 파일과 외부 상태를 추적한 것은 아닙니다.
그 추적 비용과 잘못 재사용했을 때의 재작업 비용도 아직 포함하지 않았습니다.
새로운 독립 검토를 요청한 경우에는 이 결과를 적용할 수 없습니다.

## 4. 기준을 먼저 추출하면 짧은 기록에서는 오히려 더 들었습니다

Claude가 같은 상황 여섯 개를 판단한 조건을 비교했습니다.
이번에는 기준을 추출한 호출 한 번도 포함했습니다.

| 조건 | CLI 호출 | 입력 토큰 | CLI 시간 합계 | 보고 금액 | 기대 답과 일치 |
|---|---:|---:|---:|---:|---:|
| 원문으로 바로 판단 | 6번 | 9,206개 | 23.64초 | $0.046600 | 6/6 |
| 기준을 한 번 추출한 뒤 판단 | 7번 | 12,636개 | 31.56초 | $0.069546 | 6/6 |

기준을 추출한 조건은 보고 금액이 약 **49.2%** 더 들었습니다.
판단 결과는 같았습니다. 짧은 기록에서 준비 단계를 추가해도 비용이 줄지 않았습니다.
호출별 관찰값 한 묶음이므로 안정적인 시간 차이나 긴 기록의 효과로 확대하지 않습니다.

**제안:** 기준을 저장하는 목적은 출처·적용 조건·변경 이력을 이어가는 데 둡니다.
매 판단 전에 모델로 기준을 새로 추출하지 않습니다.
원문이나 사용자의 기준이 바뀔 때 갱신하는 방법은 후보이며, 비용 효과는 따로 검증해야 합니다.

Codex는 CLI 업데이트와 서버 오류가 끼어 있으므로 같은 환경에서 끝낸 비교로 합치지 않았습니다.
추출 시도 세 번에 44.46초가 들었습니다. 서버 오류 한 번과 출처 형식 검사 실패 한 번도 포함한 값입니다.

## 5. 실패한 호출에도 시간이 들었지만 금액은 알 수 없습니다

후속 실험의 서버 오류 여섯 번에는 CLI 시간 **118.51초**가 들었습니다.
이 가운데 실제 파일을 수정한 뒤 실패한 호출 한 번이 92.39초였습니다.
여섯 번 모두 사용량을 반환하지 않아 토큰과 금액을 계산할 수 없습니다.

118.51초는 재시도 사이의 대기, 사람이 원인을 확인한 시간, 다시 실행한 시간을 제외합니다.
파일 수정까지 진행한 실패도 있으므로 전부 쓸모없이 버린 시간이라고 부르지 않습니다.
실패 뒤 이미 바뀐 파일을 확인할 수 있느냐가 복구 비용을 좌우한다는 가설이 남습니다.

응답을 받았지만 출처 형식 검사를 통과하지 못한 기준 추출 한 번은 서버 오류와 구별했습니다.
그 호출에는 19.17초, 입력 7,464개와 출력 494개가 들었습니다.
이 값은 위 기준 추출 집계에 이미 들어 있습니다. 총량을 계산할 때 다시 더하지 않습니다.

## 기존 리뷰 비용 기록은 어디까지 말해 주나요

[운영 기록의 실행·리뷰 72쌍](../../../state/observations/O-00000024.md)에서는 리뷰 쪽 토큰이 더 많았습니다.
리뷰가 매번 쌓인 로그와 변경 파일을 다시 읽는다는 관측도 있습니다.
그 기록의 계정 원본을 이번에 다시 집계하지는 않았습니다.
시간으로 짝을 맞춘 한계와 캐시 집계 차이도 그대로 남습니다.

따라서 반복 리뷰는 여전히 먼저 조사할 후보입니다.
다만 그 기록만으로 리뷰가 청구 금액에서도 가장 크다고 결론 내리지 않습니다.
이번 재집계는 그 단정을 피해야 할 근거를 더했습니다.

## 무엇부터 개선할까요

| 순서 | 확인하거나 바꿀 부분 | 기대하는 효과 | 효과를 확인할 조건 |
|---|---|---|---|
| 1 | 판단에 실제로 필요한 자료를 좁혀 전달 | 새로 읽는 입력과 캐시 생성 비용 감소 | 정확도·누락·추가 읽기까지 포함해 비교합니다. |
| 2 | 조건이 그대로인 판정의 반복 비율 측정 | 불필요한 모델 호출 감소 | 파일·기준·목적·관련 상태가 같고 독립 재검토 요청이 없어야 합니다. |
| 3 | 기준이 바뀔 때만 다시 추출하는 방식 시험 | 준비 단계의 반복 감소 | 이전 기준의 잘못된 적용과 갱신 비용을 함께 셉니다. |
| 4 | 실패 뒤 실제 파일·검사 결과를 확인하고 재개 | 이미 한 작업을 다시 하는 시간 감소 | 실패 전후 파일과 실제 재실행 범위를 확인합니다. |

자료를 줄인 기존 실험에서는 입력이 줄었지만 시간은 줄지 않았습니다.
이 때문에 입력 감소만으로 작업 전체가 빨라졌다고 평가하지 않습니다.

### 다음에는 완료한 작업 한 건을 단위로 잽니다

현재 기록은 실험별 결과를 비교하는 데 적합합니다. 실제 업무의 전체 비용을 나누기에는 정보가 부족합니다.
다음 운영 시험에서는 구현·테스트·독립 리뷰·수정·재리뷰·종료를 한 작업 ID로 연결해야 합니다.

| 기록할 항목 | 필요한 이유 |
|---|---|
| 작업·시도·이전 시도의 ID와 실제 CLI 세션 ID | 시각만으로 실행과 리뷰를 짝짓지 않습니다. |
| 입력 자료·파일·기준·검토 목적의 해시와 버전 | 같은 판단이 반복됐는지 확인합니다. 빠진 의존 조건도 표시합니다. |
| 새 입력·캐시 생성·캐시 읽기·출력과 보고 금액 | 토큰 합계를 그대로 금액으로 바꾸지 않습니다. |
| CLI와 각 도구의 시작·종료, 동시 실행 관계 | 대기와 실제 실행을 나누고 겹친 시간을 두 번 더하지 않습니다. |
| 테스트·독립 리뷰의 결과와 반려 이유 | 결과를 유지하며 줄인 것인지 확인합니다. |
| 실패 뒤 남은 변경과 재실행한 범위 | 복구할 수 있었던 작업과 다시 한 작업을 구별합니다. |
| 사람에게 물은 횟수와 답을 기다린 시간 | 사용자가 쓰는 시간까지 포함합니다. |

**다음 개선의 성공 기준은 ‘완료한 작업당 전체 비용이 줄고, 결과의 정확도와 검토 품질을 유지한다’입니다.**
자료를 고르고 기록하고 확인하는 데 드는 비용도 같은 합계에 넣어야 합니다.
이번 보고서는 그 측정을 준비할 근거를 정리했습니다. 제품 적용과 전체 운영 시험이 끝났다는 뜻은 아닙니다.

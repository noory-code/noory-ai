# 정해진 기록 절차를 코드로 묶었습니다

2026-10-07. W-00000277. Avatar의 저장·제안·확인·이력 첨부를 실험용 명령 하나로 묶었습니다.
**새 수신 세션 여섯 개가 모두 정상 종료했고, 코드·기록·기준 변경·Avatar 이력 검사도 통과했습니다.**
한 번의 시험에서 앞서 180초 제한에 걸린 조건도 이번에는 약 118초에 끝났습니다. 제품에 배포한 기능은 아닙니다.

## 바꾼 것과 지킨 것

앞선 시험에서는 AI가 각 명령의 인자를 만들고 결과를 읽은 뒤 다음 명령을 골랐습니다.
이번에는 AI가 고른 값과 적용 참조를 한 번 전달하면 코드가 정해진 공개 CLI를 차례로 실행합니다.
실제 저장·조회는 여전히 각 제품이 담당합니다. 다른 제품의 내부 코드나 DB를 직접 읽지 않습니다.

AI는 목적과 기준을 읽고 구현 방법을 고릅니다. 선택 직전 조회, 코드 작성과 검사, Stage 카드 갱신도 AI가 수행합니다.
실험용 명령은 미리 제공한 시험용 발언만 받습니다. 정확한 개인 기준을 확인한 발언이 없으면 쓰기 전에 멈춥니다.
같은 요청은 같은 idempotency key를 쓰며, 중간 실패를 앞선 저장까지 되돌린 것처럼 보고하지 않습니다.

이 명령은 실제 사용자의 취향을 자동으로 추정하거나 확인하는 제품 기능이 아닙니다.
제품에 넣으려면 사용자 확인을 받는 시점과 중간 실패 뒤 재개 방법을 별도로 설계해야 합니다.

## 시험 조건

[실행 전에 정한 계획](../integration/bundled-recording-plan.md)에 따라 앞선 전달 세션 두 개를 재사용했습니다.
새로 호출한 것은 받은 세션 여섯 개입니다. 모델, 과제, 180초 제한, 동시에 두 개를 실행하는 조건을 유지했습니다.
받는 세션마다 임시 프로젝트와 DB를 새로 복사했습니다. 제품 소스의 해시도 앞선 시험과 같습니다.
확인 발언이 없거나 적용 참조가 부적격인 경우, 같은 요청의 반복, 바뀐 요청, 중간 CLI 실패를 테스트했습니다.
실험용 명령이 없을 때 테스트를 불러오지 못하는 실패를 확인했고, 구현 뒤 새 테스트 다섯 개가 통과했습니다.
기존 검사기 테스트까지 합쳐 15개가 통과했습니다.

## 결과

| 받은 AI | 조건 | 앞선 시험의 도구 호출 → 이번 | 앞선 시간 → 이번 |
|---|---|---:|---:|
| Codex | 조회 연결 없음 | 26회 → 22회 | 180초 제한 → 118.3초 완료 |
| Codex | 기존 기준 v1 | 24회 → 19회 | 129.0초 → 66.9초 |
| Codex | 새 기준 v2 | 18회 → 15회 | 70.3초 → 98.1초 |
| Claude | 조회 연결 없음 | 15회 → 15회 | 74.1초 → 65.9초 |
| Claude | 기존 기준 v1 | 12회 → 8회 | 84.2초 → 34.5초 |
| Claude | 새 기준 v2 | 14회 → 6회 | 59.5초 → 32.4초 |

다섯 조건에서 도구 호출이 줄었고 한 조건은 같았습니다. Codex의 v2 조건은 호출 수가 줄어도 더 오래 걸렸습니다.
따라서 도구 호출 감소가 매번 같은 비율의 시간 절약으로 이어진다고 보지 않습니다.
묶음 명령 안에서는 C0에 네 번, C1·C2에 여섯 번의 공개 CLI를 실행했습니다. 저장 단계를 생략하지 않았습니다.

기준을 바꾼 두 사례는 `None`을 반환했고, 기존 기준 두 사례는 `ConfigError`를 던졌습니다.
조회 연결이 없는 두 사례는 앞선 코드와 맞추어 `ConfigError`를 골랐습니다. 이전 파일은 여섯 사례 모두 그대로입니다.
Stage는 여섯 인계 글에서 이전 파일 해시가 일치한다고 확인했습니다. 받은 AI는 새 적용 기록과 다음 할 일을 남겼습니다.
Avatar는 여섯 선택과 시험용 개인 기준 확인을 보존했습니다. 적용한 Distill 이력은 C1·C2 네 사례에서 확인했습니다.
C0에는 적용한 참조가 없으므로 이력 첨부를 성공 횟수로 세지 않습니다.

저장한 여섯 답변을 읽었을 때 같은 설명을 다시 요구하거나 작업을 막는 질문은 각각 0건이었습니다.
기준이 바뀐 두 사례는 앞서 끝낸 `parse_port`도 바꿀지 후속 판단으로 남겼습니다. 추가 답변을 입력하지 않아도 이번 과제는 끝났습니다.
Codex 메시지와 Claude 최종 답변을 읽은 결과이며 모든 내부 이벤트에서 질문 문장을 분류한 수치는 아닙니다.
이것만으로 재질문을 줄였다고 결론 내리지 않습니다.

전체 명령 `verify_integration.py --require-real-hosts`가 종료 코드 0입니다. 기본 대상은 이번 실험 폴더입니다.
실행 당시 판정 조건은 유지했고 재사용한 전달 기록의 해시 검사만 추가했습니다. 앞선 실패 기록을 지정하면 여전히 실패합니다.
원래 기록과 실패를 이번 성공으로 덮지 않았습니다.

### 입력량과 금액

Codex의 기존 기준 조건에서 보고된 입력 토큰은 345,112개에서 202,235개로 줄었습니다.
새 기준 조건에서는 299,127개에서 211,742개로 줄었습니다. 모두 캐시에서 읽은 토큰을 포함합니다.
앞선 C0은 시간 제한으로 최종 사용량을 받지 못했으므로 비교하지 않습니다.

Claude가 보고한 금액은 C0 $0.341482 → $0.295151, C1 $0.283464 → $0.176510,
C2 $0.300408 → $0.250114입니다. 실제 청구액이 아니며 감독 세션·독립 리뷰 비용도 포함하지 않습니다.
Codex는 금액을 보고하지 않았습니다. 서비스별 토큰 집계 방식이 달라 두 서비스의 입력량을 같은 기준으로 비교하지 않습니다.

## 해석의 범위

한 번의 시험이며 순서·캐시·프롬프트 길이를 통제하지 않았습니다. 평균 비용 절감률이나 일반적인 성공률을 말하지 않습니다.
도구 호출 수는 AI가 실행한 도구의 ID를 세었습니다. 개별 모델 API 요청 수나 DB 명령 수와 같지 않습니다.
묶음 안의 공개 CLI 호출 수도 따로 남겨 실제 저장을 생략해서 빨라진 것처럼 해석하지 않게 했습니다.
현재 기준을 주지 않는 C0에도 앞선 기준과 코드가 남으므로, 과거의 영향까지 없앤 대조군은 아닙니다.

## 독립 리뷰와 보완

Claude의 독립 리뷰는 성공 기준 세 가지를 모두 통과시켰습니다.
[리뷰 원본](../integration/evidence/2026-10-07-handoff-bundled/qa-review-verdict.json)에 판단 근거와 읽은 범위를 남겼습니다.
처음 요청한 리뷰는 180초에 시간 초과로 끝났고 판정을 받지 못했습니다.
읽을 범위를 좁힌 두 번째 리뷰는 별도의 420초 한도 안에서 약 84초에 끝났습니다. 실험의 180초 제한은 바꾸지 않았습니다.

리뷰 뒤 검사기 두 곳을 보완했습니다. 재사용 목록이 없거나 실제 실행한 스크립트가 현재 검토한 파일과 다르면 실패합니다.
보존한 증거를 임시 폴더에 복사해 목록을 지우고 스크립트를 바꿨습니다. 두 테스트가 실패하는 것을 확인한 뒤 고쳤습니다.
보완 뒤 연구용 테스트 17개와 `verify_integration.py --require-real-hosts`가 통과했습니다.
검사기 보완도 [별도 독립 리뷰](../integration/evidence/2026-10-07-handoff-bundled/qa-repair-review-verdict.json)를 통과했습니다.
리뷰어가 읽지 않은 [보완 뒤 전체 검사 출력](../integration/evidence/2026-10-07-handoff-bundled/qa-repair-verification.txt)도 연결했습니다.
본 체크아웃과 세 제품 worktree의 `git diff --check`가 모두 통과했으며 작업 카드에도 적었습니다.
원래 AI 응답과 실행한 스크립트는 바꾸지 않았습니다.

리뷰어는 최종 카드 여섯 장과 원본 실행 기록 한 개를 읽었습니다.
Claude → Codex의 새 기준 조건에서 조회가 코드 작성보다 앞섰음을 확인했습니다. 다른 다섯 사례의 순서는 검토하지 않았습니다.
검사기도 조회 명령이 있는지만 확인합니다. 모든 사례의 순서를 자동으로 검증했다고 주장하지 않습니다.

인계 기록에 남은 한계도 있습니다. Claude → Codex의 기존·새 기준 조건은 새 `host.py`의 해시를 카드에 남기지 않았습니다.
Codex → Claude의 기존 기준 조건은 구현·검사 설명이 짧고 테스트 파일을 남기지 않았습니다.
이번 검사는 실제 파일을 직접 실행해 동작을 확인했습니다. 이후 세션으로 다시 인계할 때 기록만으로 충분한지는 확인하지 않았습니다.
검사기는 보존한 로컬 증거를 다시 확인합니다. 목록과 계획서까지 모두 바꾸는 경우의 진본성을 보장하지 않습니다.
목록 내부를 비우는 경우나 두 전달 세션 각각의 누락은 별도 테스트하지 않았습니다. 실제 두 목록의 파일 해시는 전체 검사에서 대조했습니다.

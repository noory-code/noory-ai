# 실제 CLI 인계와 판단 기준을 시험한 중간 결과

이 문서는 첫 실행 당시의 기록입니다. 이후 사용자가 요청한 [재시도 결과](2026-10-05-stage-retry.md)를 별도로 남겼습니다.

**목표와 검사 범위를 맞췄고, 실제 CLI가 수정을 이어받는 과정도 확인했습니다. 전체 비교는 아직 끝나지 않았습니다.**
Codex가 서로 다른 두 시험에서 서버 혼잡 오류를 반환했습니다. 실패 기록을 보존하고 추가 Codex 호출을 중단했습니다.
모델을 바꾸거나 성공한 실행으로 대체하지 않았습니다.

현재 가장 분명한 결과는 세 가지입니다.

- Stage 작업 기록에서 목적·대상·검사를 찾아 실제 수정을 끝낼 수 있었습니다.
- 관찰 파일을 따로 만들어 연결해도 AI가 반드시 읽지는 않았습니다.
- 짧은 기록에서 기준을 따로 추출하면 정확도는 같고 입력과 비용은 늘었습니다.

[남은 연구와 종료 기준](../followup-plan.md), [실험 방법](../experiments/stage-followup/README.md),
[원본에서 집계한 결과](../experiments/stage-followup/summary.json)

## 1. 먼저 목표와 검사 범위를 맞췄습니다

앞선 회고 사례에는 AI에게 요구하지 않은 새 API를 검사하는 테스트가 섞여 있었습니다.
이번 카드에는 회고 번호를 작업 번호 하나만으로 구하는 API와 충돌 처리 요구를 모두 적었습니다.
AI가 전체 검사 명령을 직접 실행하고 실패를 확인할 수 있게 했습니다.

과거 결함 두 개에서 공개할 전체 검사를 먼저 돌렸습니다.
마일스톤 사례는 수정 전 실패하고 알려진 수정 후에는 14개 검사를 통과했습니다.
회고 사례도 수정 전 실패하고 알려진 수정 후에는 94개 검사를 통과했습니다.
[사전 검사 기록](../experiments/stage-followup/runs/preflight.json)

기존 실험 결과를 고친 것이 아닙니다. 수정한 목표와 새 입력으로 후속 시험을 했습니다.
따라서 앞선 점수와 비교해 모델의 정확도가 올라갔다고 해석하지 않습니다.

## 2. 실제 Claude·Codex 도구로 일을 이어받았습니다

첫 AI가 남긴 수정은 앞선 실험의 원본을 재사용했습니다. 첫 AI를 다시 호출하지 않았습니다.
현재 Stage의 초기화·작업 등록 명령으로 임시 프로젝트에 작업 카드를 만들었습니다.
카드에 목적, 완료 기준, 이전 수정 요청, 결과가 미확인이라는 사실, 다음 행동과 검사 명령을 적었습니다.

다음 AI는 카드 경로를 받고 자신의 파일·명령 도구로 작업했습니다.
한 조건에는 카드만 줬습니다. 다른 조건에는 인계 시점의 파일 내용과 해시를 별도 파일에 저장하고 카드에서 연결했습니다.
이전 실험처럼 다음 행동 하나를 JSON으로 고르게 한 뒤 연구용 프로그램이 실행한 방식과 다릅니다.

### 정상적으로 완료한 비교

마일스톤 결함 한 개에서 두 방향과 두 조건을 모두 마쳤습니다.
네 실행 모두 대상 소스를 수정하고 전체 검사 14개를 통과했습니다. 완료 응답도 받았습니다.
각 조건은 한 번만 실행했습니다.

| 이어받은 AI | 받은 자료 | 도구 사용 | 입력 토큰 | 준비부터 독립 검증까지 |
|---|---|---:|---:|---:|
| Codex | 작업 카드 | 9번 | 200,820개 | 168.2초 |
| Codex | 카드와 관찰 파일 링크 | 8번 | 165,558개 | 129.2초 |
| Claude | 작업 카드 | 8번 | 60,173개 | 26.7초 |
| Claude | 카드와 관찰 파일 링크 | 7번 | 51,089개 | 25.3초 |

도구 사용 횟수는 모델을 호출한 횟수가 아닙니다.
시간은 공통 준비와 파일 복사를 마친 뒤부터 잽니다. 조건별 자료 구성, CLI와 독립 검증을 포함합니다.
두 호스트의 시스템 지침과 도구가 다르므로 이 표로 호스트의 성능 순위를 매기지 않습니다.

**관찰 파일을 제공한 두 실행 모두 그 파일을 여는 호출은 없었습니다.**
두 AI는 실제 소스와 테스트를 읽었습니다. 원본 도구 입력과 셸 명령을 확인했습니다.
따라서 시간·토큰 차이를 그 관찰 파일 덕분이라고 볼 수 없습니다.
카드에 링크를 더한 조건의 결과일 뿐, 관찰 내용이 모델에게 전달된 비교가 성립하지 않았습니다.

자료를 저장하고 연결하는 단계와 AI가 실제로 읽고 사용하는 단계를 각각 확인해야 합니다.
이 결과는 관련 파일을 스스로 읽는 좁은 동작을 확인합니다.
대상 경로와 검사 명령은 카드에 이미 적혀 있었으므로, 자유 문서에서 필요한 근거를 전부 찾아낸 시험은 아닙니다.

### 서버 오류 뒤에도 실제 파일은 확인할 수 있었습니다

다섯 번째 실행에서 Codex는 회고 번호를 구하는 함수와 파일 예약 기능을 분리해 수정했습니다.
그 뒤 `Selected model is at capacity` 오류로 끝났습니다. 최종 완료 응답과 사용량은 받지 못했습니다.

별도 프로그램이 남은 파일을 검사했습니다. 전체 테스트 94개가 통과했고, 보호한 주석도 남아 있었습니다.
추적한 파일 중 대상 밖의 파일은 바뀌지 않았습니다.
이 실행은 ‘정상적으로 완료했다’고 세지 않았습니다. **코드 검사 통과와 모델 실행 종료를 따로 기록했습니다.**
[중단된 실행](../experiments/stage-followup/runs/retrospective_owner_conflict--claude-to-codex/stage_card/cli.json),
[실제 파일의 검사 결과](../experiments/stage-followup/runs/retrospective_owner_conflict--claude-to-codex/stage_card/result.json)

이번 오류는 실험자가 만든 중단이 아닙니다. 실제 CLI가 반환했습니다.
오류 응답만으로 파일 수정도 실패했다고 판단하면 이미 끝난 수정을 반복할 수 있습니다.
실제 결과를 다시 확인하는 절차가 왜 필요한지 보여 준 사례입니다. 모든 외부 도구의 복구를 입증하지는 않습니다.

### 이 실행의 범위

임시 Stage 감사는 오류 없이 통과했습니다. 프로젝트의 검증 안내가 기본 양식과 다르다는 경고 한 개는 남았습니다.
모델은 작업 카드의 수명 주기 상태를 바꾸지 않았습니다. 드라이버, 모든 훅, 독립 모델 리뷰, 회고·승격은 연결하지 않았습니다.
따라서 코드 수정 완료를 Stage 작업의 공식 종료와 구별합니다.

파일 비교에서는 자동으로 생기는 `__pycache__`를 제외했습니다.
Codex가 상위 임시 폴더까지 `AGENTS.md` 파일명을 검색한 명령도 두 실행에서 관찰했습니다.
작업 디렉터리 밖의 접근까지 차단한 강한 격리 실험으로 보고하지 않습니다.
Claude가 검사를 파이프로 출력한 경우도 있어, 독립 검증은 별도 프로세스의 실제 종료 코드를 사용했습니다.

## 3. 관찰 시점을 표시하는 효과를 따로 봤습니다

이전 실험에서 Claude가 파일을 다시 읽었던 입력 한 개를 골랐습니다.
원본과, 같은 파일을 ‘인계 직전에 읽은 관찰’이라고 표시한 조건을 각각 세 번 실행했습니다.
실제 파일 내용과 수정·검사 결과는 바꾸지 않았습니다. 관찰 시점을 설명하는 문장은 추가했습니다.

| Claude가 고른 다음 행동 | 원래 입력 | 관찰 시점을 명시한 입력 |
|---|---:|---:|
| 파일을 다시 읽습니다. | 1번 | 0번 |
| 완료를 보고합니다. | 2번 | 3번 |

시점을 분명히 표시할 후보 근거는 얻었습니다. 사례 한 개에서 각 조건을 세 번 실행한 결과입니다.
앞선 결과를 보고 고른 입력이며, 새 과제 여섯 개의 성능이 아닙니다.
추가 읽기는 오답으로 채점하지 않았습니다. 이번에는 고른 행동을 실제로 실행하지 않았습니다.
전체 시간·안전성이 개선됐다고 주장하지 않습니다. Codex 비교 여섯 번은 서버 오류 때문에 실행하지 않았습니다.
[비교 입력과 실행 순서](../experiments/stage-followup/freshness-runs/manifest.json)

## 4. 기준을 따로 뽑는 것이 항상 이득은 아니었습니다

가상의 프로젝트 기록 다섯 개를 만들었습니다. 목적, 기본 원칙, 제한된 예외, 다른 프로젝트의 허용, 확인하지 않은 AI 추정을 담았습니다.
Claude가 이 기록에서 기준을 뽑게 했습니다. 추출 단계에는 평가할 상황과 기대 답을 주지 않았습니다.
이후 별도 상황 여섯 개에 원문을 주는 조건과 추출한 기준을 주는 조건을 비교했습니다.

| Claude 비교 | 기대한 판단과 일치 | 입력 토큰 | 보고 비용 |
|---|---:|---:|---:|
| 원문 기록 | 6/6 | 9,206개 | $0.046600 |
| 추출한 기준 | 6/6 | 11,234개 | $0.054602 |

기준 추출 자체에도 입력 1,402개와 $0.014944가 들었습니다.
판단 입력만 비교해도 약 22% 늘었고 정확도 차이는 없었습니다.
이번처럼 원문이 짧은 경우에 매번 기준을 따로 뽑도록 하는 정책은 채택하지 않습니다.
긴 기록에서 기준을 여러 번 재사용하는 효과는 별도로 확인해야 합니다.

예외의 범위, 새 사용자 지시, 다른 프로젝트의 기준과 AI 추정을 구별하는 판단은 이번 여섯 상황에서 맞았습니다.
이는 명시된 합성 기준을 적용한 결과입니다. 사용자의 실제 취향을 알아내거나 실무 재지시를 줄인 결과가 아닙니다.

인용이 원문에 있는지는 자동으로 확인했습니다. 그러나 인용만으로 모든 분류가 검증되지는 않습니다.
예를 들어 N4에는 프로젝트명이 없는데 추출 결과는 A로 분류했습니다.
해당 항목을 미확인 추정으로 남겨 이번 판단에는 영향을 주지 않았지만, 범위를 추정한 부분은 구별해야 합니다.
[추출 결과](../experiments/stage-followup/criteria-runs/extraction-check--claude.json)

Codex는 기준 추출 첫 호출에서 같은 서버 혼잡 오류를 반환했습니다.
Codex의 기준 추출 성공과 뒤따르는 판단 12번은 아직 확보하지 못했습니다.

## 5. 실무에서 판단이 반복되는 비율은 아직 계산할 수 없습니다

현재 저장소의 실제 드라이버 로그 73개와 판정 파일 43개를 조사했습니다.
로그에는 리뷰 보고 제목이 총 104개 있었고, 29개 로그에 제목이 두 개 이상 있었습니다.
이는 모델 호출 104번이나 재사용 가능한 판단 104개를 뜻하지 않습니다.

검사한 판정 파일 43개에는 당시 입력 전체, 기준 버전과 근거 파일 해시를 대조할 필드가 없었습니다.
따라서 두 판단이 같은 조건에서 이루어졌는지 확인할 수 없습니다.
재사용 비율을 0%라고 하지도 않고, 실험에서 정했던 50%를 적용하지도 않습니다.
[파일별 조사 결과](../experiments/stage-followup/reuse-audit.json)

실무 효과를 재려면 앞으로 판단할 때 다음 내용을 함께 남겨야 합니다.

- 무엇을 판단했고 어떤 입력·근거·기준·실행 설정을 사용했는지
- 그 조건이 유지됐는지 확인하는 데 얼마가 들었는지
- 새 독립 검토를 요구한 요청인지
- 재사용 뒤 수정이나 재작업이 발생했는지

수집 기능을 제품에 추가하거나 장기 측정을 시작하지는 않았습니다.
현재 자료로는 실무에서의 절감량을 권고할 근거가 부족합니다.

## 현재 후보별 판단

| 후보 | 현재 판단 | 근거와 남은 조건 |
|---|---|---|
| 목적·검사·남은 일을 담은 Stage 카드로 이어갑니다. | 유지할 후보입니다. | 실제 수정 네 건을 정상적으로 마쳤습니다. 모든 운영 절차까지 검증한 결과는 아닙니다. |
| 관찰 파일 링크를 추가하면 AI가 그 자료를 사용합니다. | 이번 방식의 효과를 보류합니다. | 제공한 두 실행에서 관찰 파일을 읽지 않았습니다. 전달 여부부터 확인해야 합니다. |
| 관찰 시점과 후속 변경을 분명히 표시합니다. | 작은 적용 후보입니다. | 골라낸 입력 한 개에서 추가 읽기 한 번이 줄었습니다. 더 넓은 효과는 미확인입니다. |
| 짧은 기록에서도 매번 기준을 추출합니다. | 이번 조건에서는 채택하지 않습니다. | 판단은 같고 입력·추출 비용이 늘었습니다. |
| 조건이 유지되는 판단을 재사용합니다. | 실무 적용은 보류합니다. | 실제로 재사용할 비율을 계산할 기록이 없습니다. |
| 모델이 오류로 끝나면 실제 결과를 따로 확인합니다. | 필요한 절차로 유지합니다. | 실제 서버 오류 뒤에도 파일 수정과 전체 검사 통과를 확인했습니다. |

## 남은 실행과 검증

이번 후속 실행을 모두 마쳤다고 표시하지 않습니다.

1. 실제 CLI 인계 세 번이 아직 실행되지 않았습니다. 서버 오류로 끝난 한 번의 기록은 그대로 유지합니다.

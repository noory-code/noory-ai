# 세션을 이어받을 때 읽는 자료를 줄여 봤습니다

**현재 결론: 기록을 줄이는 일과 현재 근거를 확보하는 일을 따로 다뤄야 합니다.**
실제 작업 기록을 줄인 조건에서 입력 토큰은 감소했습니다. 이번 작은 시험에서는 판정도 유지됐습니다.
응답 시간이 줄었다는 결과는 얻지 못했습니다.
여러 세션에서 실제 개발을 끝내는 전체 과정은 시험하지 않았습니다.

## 무엇을 확인했나요

본래 연구의 질문은 AI가 같은 상황을 다시 파악하는 데 드는 반복을 줄일 수 있는지입니다.
Avatar / Clone은 별도 아이디어로 보관했고, 이번에는 Stage의 인계 자료를 다뤘습니다.

1. 실제 열린 작업 여섯 건을 복사본에서 읽었습니다.
2. 현재 Stage 소스로 세션 문맥을 만들고, 대상 작업과 상위 작업의 원문을 붙였습니다.
3. 전체 작업 구조·진행 인덱스·리뷰 인덱스 세 부분을 뺀 자료와 비교했습니다.
4. 실제 릴리스 작업 한 건에서 질문 두 개를 Claude·Codex에 제시했습니다.

모델 비교는 세 조건을 두 번씩 실행했습니다. 호출은 총 24번입니다.
작업 24건의 결과가 아닙니다. 독립적인 실제 작업은 한 건이며, 근거를 구별하는 규칙도 질문에 명시했습니다.
[실험 방법](../experiments/context-handoff/README.md), [원시 집계](../experiments/context-handoff/summary.json)

## 실제 인계 기록에서 관찰한 것

열린 작업 여섯 건 모두 목적과 완료 기준은 적혀 있었습니다.
네 건은 `Next action`, `Progress`, `Verification` 본문이 비어 있었습니다.
아직 시작하지 않은 작업일 수도 있고 다른 곳에 근거가 있을 수도 있습니다.
빈 항목만으로 Stage의 결함이나 실제 인계 실패를 단정하지 않습니다.
다만 이 본문만으로는 어디까지 끝났는지 알 수 없으므로, 줄이기 전에 원래 정보가 있는지 확인해야 합니다.

전체 작업을 보여 주는 세 부분을 빼자 각 입력에서 2,477자가 줄었습니다.
대상 작업과 상위 작업의 본문은 모두 그대로 보존했습니다.

다른 작업의 상태가 이번 작업에 영향을 줄 수도 있으므로, 세 부분을 항상 빼도 된다고 해석하지 않습니다.

## Claude·Codex 비교 결과

릴리스 작업 W-00000267에는 과거에 0.6.0을 냈다는 기록이 있습니다.
측정 당시 현재 매니페스트는 0.7.1이었습니다.
과거 기록 자체가 틀렸다는 뜻은 아닙니다. 그 기록만으로 현재 버전을 확인할 수 없다는 뜻입니다.

첫 질문은 현재 버전을 파악할 다음 동작입니다.
둘째 질문은 사람이 한국어 답을 읽고 최종 확인했다는 근거가 기록에 있는지입니다.
세 번째 조건에는 현재 매니페스트와 같은 상위 작업의 후속 기록을 더했습니다.
이 추가 자료는 연구자가 골랐습니다. 자동 검색의 성공으로 세지 않습니다.

| 호스트 | 조건 | 판정 일치 | 입력 토큰 합계 | 요청당 평균 시간 | 보고 비용 |
|---|---|---:|---:|---:|---:|
| Claude | 기본 입력 | 4/4 | 31,033개 | 3.58초 | $0.130116 |
| Claude | 세 부분 제거 | 4/4 | 24,498개 | 3.76초 | $0.104566 |
| Claude | 제거 뒤 현재 근거 추가 | 4/4 | 46,564개 | 3.53초 | $0.192430 |
| Codex | 기본 입력 | 4/4 | 46,222개 | 6.23초 | 미제공 |
| Codex | 세 부분 제거 | 4/4 | 41,731개 | 6.90초 | 미제공 |
| Codex | 제거 뒤 현재 근거 추가 | 4/4 | 57,344개 | 7.05초 | 미제공 |

전체 24번의 판정이 기대값과 일치했습니다. 입력 해시·실행 수 검사 오류는 없었습니다.
기본 입력에서도 모두 맞았으므로 정확도가 향상됐다고 볼 수 없습니다.
입력 토큰은 자료를 줄인 조건에서 Claude 약 21.1%, Codex 약 9.7% 감소했습니다.
Claude의 보고 비용 합계는 약 19.6% 줄었습니다. 실제 청구서는 확인하지 않았습니다.

자료를 줄인 조건의 평균 응답 시간은 두 호스트 모두 더 길었습니다.
조건당 호출 네 번이라 시간 차이를 일반화할 수 없습니다.
CLI 시작, 서버 응답과 출력 길이의 영향도 있으므로 빨라졌다는 주장을 하지 않습니다.

현재 매니페스트를 주지 않은 조건에서는 두 AI 모두 파일을 더 읽어야 한다고 답했습니다.
이는 자료에 맞는 올바른 판정입니다.
현재 근거를 준 조건에서는 0.7.1을 답했습니다. 사람의 최종 품질 확인은 여전히 필요하다고 답했습니다.
같은 입력의 정확도 비교와, 근거를 추가해서 새로 알 수 있게 된 사실을 구별합니다.

Claude에는 `claude-sonnet-5-5`를, Codex에는 CLI 기본 모델과 low effort를 요청했습니다.
실제 모델 버전을 양쪽 모두 고정한 비교는 아닙니다. 두 호스트의 성능 순위를 매기지 않습니다.
Claude 전체 보고 비용은 $0.427112입니다. Codex는 금액을 반환하지 않았습니다.

## 이 결과에서 무엇을 배웠나요

### 과거 기록과 현재 상태를 나눠 확인해야 합니다

작업 기록은 왜 그렇게 했는지 설명합니다. 현재 파일은 지금 무엇이 있는지 보여 줍니다.
이 둘이 서로 다른 시점을 말할 때, 하나를 다른 하나의 대용으로 쓰지 않아야 합니다.
Stage의 결정·작업 기록을 유지하면서 행동 전에 필요한 현재 사실을 확인하는 방식이 후보입니다.

### 짧게 만드는 것만으로 빠진 정보가 생기지는 않습니다

이번에는 원문을 요약하지 않고 전체 목록 세 부분만 제거했습니다.
그 정도로도 입력은 줄었지만, 빈 진행 기록을 채우거나 최신 버전을 알아내지는 못합니다.
반대로 관련 자료를 통째로 더하면 확인할 수 있는 사실이 늘면서 입력 비용도 커집니다.
다음에 확인할 것은 어떤 사실이 다음 행동에 필요한지 좁혀 읽는 방법입니다.

### Stage에 이미 있는 구조를 먼저 활용할 수 있습니다

작업 번호, 부모 관계, 결정 원문과 인계 절차는 이미 있습니다.
이번 결과는 새 저장소가 필요하다는 근거가 아닙니다.
우선 확인할 대상은 기록 갱신, 관련 자료 선택, 현재 상태 확인이 실제로 이어지는지입니다.

Anthropic의 [긴 작업 실행 사례](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)도 진행 기록과 Git 이력을 읽는 절차에 현재 동작 검사를 함께 둡니다.
그 사례와 이번 결과가 같은 문제를 가리킨다는 해석은 가능하지만, 해당 사례로 Stage의 효과를 증명하지는 않습니다.

## 다음 실험이 풀어야 할 질문

다음에는 서로 다른 세션이 실제로 한 작업을 끝내는 과정을 비교해야 합니다.
기존 Stage의 인계 절차를 제대로 수행한 경우와 필요한 자료를 골라 읽히는 경우를 대조합니다.

- 같은 일을 다시 실행하거나 이미 정한 문제를 재논의하는 횟수가 줄어드나요?
- 중간에 기준·파일·다른 하위 작업이 바뀌면 이를 찾아내나요?
- 자료 검색과 기록 갱신까지 포함한 전체 시간이 줄어드나요?
- 무엇을 완료했는지 기록하기 전에 세션이 끝나도 실제 결과를 확인할 수 있나요?

이번 시험은 그 전 단계입니다. 실제 인계·자율 검색·동시 수정·프로세스 복구를 성공시켰다고 보고하지 않습니다.
제품 코드와 원래 작업 기록은 수정하지 않았습니다.

# 여러 AI 세션에서 하나의 작업을 이어가는 방법

**상태: 2026-10-05에 Stage 소스와 계약을 대조했습니다. 이후 제한된 도구로 실제 코드 수정을 이어받는 비교를 여덟 번 수행했습니다. 현재 Stage 전체를 연결한 효과는 아직 확인하지 않았습니다.**

이후 입력 자료를 확인하고 두 AI에서 근거를 구별하는 작은 비교 24번을 수행했습니다.
[인계 자료 시험 결과](findings/2026-10-05-context-handoff.md)는 전체 작업 인계의 효과와 구분합니다.
그 뒤 [실제 수정 인계 결과](findings/2026-10-05-cross-session.md)에서는 현재 파일을 미리 전달해 모델 호출을 줄였습니다.
전체 시간과 품질이 좋아졌다는 결과는 얻지 못했습니다. 관찰 시점의 혼동과 평가 구성의 문제도 확인했습니다.
이어 [실제 CLI 도구로 수행한 비교](findings/2026-10-05-stage-followup.md)에서는 네 번의 인계를 마쳤습니다.
다섯 번째는 파일 수정 뒤 Codex 서버 오류로 중단됐습니다. 전체 비교와 Stage 운영 절차의 검증은 아직 남아 있습니다.
그 뒤 사용자 요청으로 [재시도한 결과](findings/2026-10-05-stage-retry.md)를 별도로 남겼습니다.
Claude의 나머지 인계 두 조건은 각각 전체 테스트 94개를 통과했습니다. Codex는 다시 서버 오류가 나 남은 비교를 마치지 못했습니다.
이후 [업데이트 후 비교](findings/2026-10-05-stage-after-update.md)에서 Codex의 두 조건도 마쳤습니다.
실제 CLI 인계 여덟 조건에서 모두 정상 완료와 전체 검사 통과를 확인했습니다. Stage 전체 운영 과정은 별도 검증으로 남습니다.

목적은 세션이 바뀌어도 같은 일을 다시 설명하거나 실행하지 않고, 남은 일을 정확히 끝내는 것입니다.
앞선 로컬 파일 복구 시제품은 실행 중단의 일부만 다뤘습니다.
이번 질문에는 목적, 결정 이유, 현재 결과와 남은 일을 다른 AI가 이어받는 문제도 포함됩니다.

## 현재 제안

Stage의 작업 번호를 기준으로 목적·결정·결과·세션을 연결하는 방법부터 시험합니다.
세 가지 개선을 Stage가 제공할 능력으로 함께 검토한다는 [현재 방향](product-design.md)을 따릅니다.
새 저장소나 별도 제품이 필요한지는 그 결과를 보고 판단합니다.
세 번째 기능의 검증은 유지합니다. 현재 Stage로 충분한지, 추가 구현이 필요한지는 미정입니다.

묶으면 어떤 기록이 같은 일에 속하는지 찾기 쉬워집니다.
그러나 연결만으로 기록이 정확해지거나 현재 상태와 일치하지는 않습니다.
효과를 얻으려면 다음 세션이 관련 기록을 찾고, 현재 상태와 대조하고, 남은 행동을 고를 수 있어야 합니다.

## Stage에는 이미 무엇이 있나요

아래는 현재 소스와 절차에서 확인한 범위입니다. 이번에 새 실행 시험을 통과했다는 뜻은 아닙니다.

| 이미 있는 기능 | 확인한 내용 | 아직 입증하지 않은 범위 |
|---|---|---|
| 작업과 하위 작업을 연결합니다. | 작업 번호와 부모 관계로 같은 목적에 속한 일을 나타냅니다. | 여러 대화에서 작업 소속을 자동으로 정확히 찾는지 |
| 결정과 이유를 남깁니다. | 질문, 선택지, 원칙, 선택한 방향, 적용 범위와 이유를 적습니다. 작업과 결정도 서로 참조합니다. | 새 상황에서 관련 결정과 변경된 조건을 빠짐없이 찾는지 |
| 다음 세션에 일을 넘깁니다. | 작업 본문에 목적, 확인한 결과, 남은 문제, 완료 기준과 다음 행동을 적도록 합니다. | 작업자가 빠뜨린 내용을 자동으로 복원하는지 |
| 세션 시작 때 기록을 읽어 줍니다. | 작업 구조, 인덱스 일부, 관측과 최근 세션 요약을 넣습니다. 일부 항목은 길이를 제한합니다. | 지금 맡은 작업에 필요한 정보만 골라도 충분한지 |
| 완료한 실행 단계부터 재개합니다. | 저장한 체크포인트와 현재 저장소가 같을 때 완료한 단계를 건너뜁니다. | 임의의 도구가 실행되다 중단된 경우까지 복구하는지 |
| 병렬 작업을 분리합니다. | 별도 worktree를 만들고 선언한 수정 범위의 겹침을 검사합니다. | 같은 결과를 동시에 바꾸는 모든 세션의 충돌을 해결하는지 |

근거는 [작업 인계 절차](../../../stage/skills/stage-handoff/SKILL.md),
[결정 절차](../../../stage/skills/stage-decision/SKILL.md),
[결정 기록 양식](../../decisions/pending/_template.md),
[세션 문맥 생성](../../../stage/hooks/stage_context.py),
[재개 검사](../../../stage/scripts/driver_supervised.py),
[병렬 실행](../../../stage/scripts/drive_parallel.py)입니다.

특히 Stage는 결론만 보관하지 않습니다. 결정한 이유와 적용한 원칙도 기록하게 합니다.
따라서 판단 기준 연구와도 겹칩니다. Stage를 실행 전용으로 구분해서는 안 됩니다.

자동으로 저장하는 세션 요약에는 열린 작업 번호, 완료 차단 요소와 인계 안내가 들어갑니다.
그 세션의 구체적인 선택과 실행 결과를 대화에서 추출하는 코드는 해당 함수에 없습니다.
세부 내용은 작업 본문을 갱신하는 절차에 기대고 있습니다.
[요약 생성](../../../stage/hooks/stage_context.py), [저장 호출](../../../stage/hooks/stage_guard.py)

최근 요약은 파일의 수정 시각을 기준으로 고릅니다. 같은 시각의 요약도 함께 읽습니다.
현재 이어받을 작업 번호로 관련 세션을 고르는 방식은 아닙니다.
이는 해당 함수에서 확인한 동작이며, 실제 인계 실패를 재현한 결과는 아닙니다.
[최근 요약 선택](../../../stage/hooks/stage_runtime.py)

## 무엇으로 묶을까요

하나의 작업 번호 아래에 다음 기록을 연결하도록 제안합니다.

- 목적과 완료 기준은 해당 작업과 상위 작업을 참조합니다.
- 결정은 Stage의 원래 결정 기록을 참조합니다.
- 결과는 실제 파일, 변경 버전과 검사 결과를 참조합니다.
- 세션은 어느 작업의 어느 부분을 수행했는지 남깁니다.

세션 하나에서 여러 작업을 할 수 있고, 작업 하나가 여러 세션에 걸칠 수도 있습니다.
따라서 세션 전체를 작업 하나에 넣기보다 실제로 수행한 부분을 연결해야 합니다.
주제가 비슷하다는 이유만으로 같은 작업이라고 확정하지 않습니다.
긴 작업은 완료 여부를 따로 확인할 수 있는 하위 작업으로 나누고 상위 목적을 유지합니다.
세션이 새로 열렸다는 이유만으로 작업을 쪼개지는 않습니다.

## 기록이 커지면 어떻게 읽힐까요

보관한 자료의 양과 한 번에 AI에게 읽히는 양을 따로 관리합니다.
다음 세션에는 아래 내용을 먼저 줍니다.

1. 이번 작업의 목적, 완료 기준과 사용자가 최근에 바꾼 조건
2. 지금 이어받을 부분과 관련된 결정, 그 이유와 원문 위치
3. 실제로 확인한 결과와 확인한 시점·버전
4. 아직 모르거나 서로 충돌하는 내용
5. 다음 행동과 현재 담당한 세션

다른 하위 작업의 전체 대화는 기본 입력에서 제외하고 관련 결과와 의존 관계를 연결합니다.
결정 이유가 불분명하거나 근거가 바뀌었다면 원문과 실제 파일을 추가로 확인합니다.
전체 기록을 검색할 수 있게 두되, 작업과 연결된 기록을 먼저 좁혀 읽도록 제안합니다.

짧게 줄였다는 사실만으로 충분하다고 보지 않습니다.
빠뜨린 제약 때문에 잘못 판단하지 않는지 측정해야 합니다.
요약을 다시 요약하는 방식만으로 기록을 유지하지 않고, 원문과 검증 결과를 계속 참조합니다.
한 번에 읽을 양을 넘으면 생략한 자료를 표시하고 다음 행동에 필요한 부분부터 추가로 읽습니다.

## 세션마다 말이 다르면 무엇을 믿을까요

기록의 종류에 따라 확인하는 곳을 정합니다.
사용자의 현재 요청은 과거 추정보다 우선합니다.
프로젝트에서 채택한 결정은 원래 결정 기록과 이후 변경을 확인합니다.
파일을 저장했거나 테스트가 통과했다는 주장은 해당 파일·버전·실행 결과로 확인합니다.
나중에 작성한 요약이라는 이유만으로 이전 사실을 덮어쓰지 않습니다.

같은 부분을 두 세션이 동시에 맡을 때는 담당 범위와 기준 버전을 정해야 합니다.
공유 상태를 갱신하기 전에 읽었던 버전이 여전히 같은지 확인하는 방식을 검토합니다.
그사이 달라졌다면 변경을 비교한 뒤 반영합니다.
외부 행동이 실제로 끝났는지 확인할 수 없다면 미확인으로 남깁니다.
담당 세션이 사라졌다는 이유만으로 같은 행동을 다시 실행하지 않습니다.
이 동작들이 Stage의 모든 실행 경로에서 보장된다고 확인한 것은 아닙니다.

## Distill과는 어떻게 연결할까요

이 절은 기존 Distill과 연결할 가능성을 검토한 내용입니다.
이후 사용자는 개인의 기준과 메타인지 목적을 [Avatar / Clone이라는 별도 플러그인](avatar.md)으로 구분했습니다.
어떤 코드를 공유할지는 정하지 않았으며, 새 구현은 보류합니다.

개인의 판단 기준은 [프로젝트를 넘어 이어서 쓰는 역할](decision-criteria.md#person-across-projects)을 유지합니다.
여러 세션의 작업 진행을 연결하는 일과 여러 프로젝트에서 개인의 기준을 축적하는 일은 각각 검증합니다.
사용자는 첫 번째와 두 번째 후보를 판단 기준을 만들고 적용하는 흐름으로 연결했습니다.
Stage에 있는 결정과 이유는 그 흐름의 근거가 될 수 있습니다.
Distill이 이를 검색하거나 기준 후보를 만들 때 원래 작업·결정과 버전을 참조하도록 제안합니다.
Stage 결정 원문과 별개로 같은 결정을 관리하는 저장소를 새로 만들 필요는 없습니다.
검색용 사본을 만든다면 원문이 바뀌었는지 확인하고 다시 만들 수 있어야 합니다.

한 프로젝트의 선택을 사용자의 모든 프로젝트에 적용할 기준으로 일반화하지 않습니다.
기준을 형성하는 조건은 [판단 기준 연구](decision-criteria.md#forming-criteria)를 따릅니다.
조회 순서는 [궁극적 목적 → Distill → 사용자](decision-criteria.md#decision-order)를 유지합니다.
Stage의 목적과 현재 적용할 결정은 프로젝트 문맥을 제공하며, 별도의 사용자 질문 단계를 추가하지 않습니다.
같은 결론을 재사용할 조건은 [두 번째 후보의 설계](product-design.md)에 따릅니다.

## Stage로 충분한지 어떻게 확인할까요

현재 Stage의 인계 절차를 제대로 수행한 경우를 기준으로 삼아야 합니다.
기록을 일부러 빠뜨린 Stage와 새 방식을 비교하면 개선 효과를 과장할 수 있습니다.

| 비교할 방식 | 확인할 점 |
|---|---|
| 허용된 대화 기록을 모두 전달합니다. | 정보가 많을 때 드는 비용과 낡은 내용을 잘못 적용하는 횟수 |
| 현재 Stage의 작업·결정·인계 절차를 사용합니다. | 이미 있는 기능으로 재설명과 중복 실행을 얼마나 줄이는지 |
| Stage 기록에서 다음 행동에 필요한 내용을 골라 전달합니다. | 고르는 비용까지 포함해 시간과 사용량이 줄고 중요한 조건이 유지되는지 |

같은 작업을 Claude → Codex와 Codex → Claude 순서로 넘겨 비교하도록 제안합니다.
대화가 너무 커서 전부 전달할 수 없는 경우도 따로 기록합니다. 조용히 잘라 비교하지 않습니다.
다음 사례를 포함해야 합니다.

- 결정한 이유를 기억해야 같은 논의를 반복하지 않는 경우
- 실행은 끝났지만 완료 기록 전에 중단된 경우
- 인계 뒤 사용자가 기준이나 파일을 바꾼 경우
- 다른 하위 작업의 세션이 더 최근에 끝난 경우
- 두 세션이 같은 부분을 수정하려는 경우

측정할 값은 재설명 횟수, 중복 실행, 누락한 조건, 올바른 다음 행동까지 걸린 시간입니다.
입력을 준비하고 기록을 갱신하는 비용도 포함합니다.
현재 Stage만으로 충분하면 그 결과를 인정합니다.
추가 방식이 효과를 보일 때만 Stage 확장이나 독립 기능을 구체화합니다.
위 세 방식을 현재 Stage에 연결한 비교는 아직 수행하지 않았습니다.
후속 실험은 제한된 도구에서 이전 기록과 현재 파일을 미리 전달하는 두 조건만 비교했습니다.

# AI가 일하는 방식을 개선하는 연구 — 종합 정리

2026년 10월 6일까지의 조사와 실험을 정리했습니다.
**같은 조건의 판단을 다시 쓰면 호출과 시간이 줄었습니다. 검토 범위를 이미 알 때는 한 과제의 입력과 보고 금액도 줄였습니다.**
그러나 범위를 찾으려고 AI를 한 번 더 부르자 절약 효과가 사라졌습니다. 코드를 줄인 과제도 Claude 보고 금액은 12.1%, Codex 입력은 67.7% 늘었습니다.
작은 과제에서 확인한 결과입니다. Stage 전체 운영 과정과 실무에서 얼마나 절약되는지는 아직 검증하지 않았습니다.

## 1. 무엇을 알아보려 했나요

목적은 **AI가 일하는 과정을 잘게 나누고, 그중 무엇을 더 잘하거나 덜 반복하게 만들 수 있는지 찾는 것**이었습니다.
Jev의 사례에서는 필요한 판단 하나를 별도 문제로 다룬 접근에 주목했습니다.
그런 기회를 우리가 쓰는 Claude와 Codex에서도 찾으려 했습니다. 창업자의 내적 동기까지 확인한 것은 아닙니다.

공개 자료와 SDK 코드를 읽고 작업을 64개 동작으로 나눴습니다.
여섯 가지 아이디어를 작은 시제품으로 시험한 뒤, 아래 세 가지 후보를 더 살펴봤습니다.
비공개 모델 내부의 사고 과정을 밝혀낸 연구는 아닙니다.

## 2. 세 가지 후보는 무엇이 다른가요

| 후보 | 해결하려는 문제 | 바꾸려는 방식 | 좋아졌다고 판단할 조건 |
|---|---|---|---|
| 판단 기준을 모아 적용합니다. | 이미 설명한 우선순위와 예외를 다음 선택에서 놓칩니다. | 목적과 과거 결정의 이유를 찾아 새 상황에 적용합니다. | 재설명과 잘못된 선택이 함께 줄어야 합니다. |
| 유효한 판단을 다시 씁니다. | 조건이 그대로인데 같은 검토를 반복합니다. | 관련 조건이 유지되면 기존 판정을 돌려줍니다. | 유효성을 확인하는 비용과 잘못 재사용한 뒤의 수고까지 합쳐도 절약돼야 합니다. |
| 세션이 바뀌어도 일을 이어갑니다. | 앞선 AI가 한 일과 남은 일을 다시 파악해야 합니다. | 목적·관련 결정·실제 결과·남은 일을 작업 단위로 전달합니다. | 끝낸 일을 반복하거나 바뀐 조건을 놓치는 일이 줄어야 합니다. |

첫 번째는 **새로운 선택에 쓸 기준**, 두 번째는 **이미 내린 판단**, 세 번째는 **진행 중인 작업**을 다룹니다.
서로 연결할 수 있지만 효과는 각각 확인해야 합니다.
사용자가 지정한 Stage·Distill·Avatar 구현은 [별도 작업 묶음](../../work/current/W-00000272/_epic.md)에서 관리합니다.

## 3. 실제로 무엇을 확인했나요

| 시험한 방법 | 관찰한 결과 | 현재 판단 |
|---|---|---|
| 같은 조건의 판정을 다시 반환합니다. | 같은 요청이 절반 반복되도록 구성한 조건에서 모델 호출을 절반으로 줄였습니다. 평균 응답 시간도 약 절반으로 줄었고, 정한 판정 기준을 충족했습니다. | 절약할 가능성이 가장 분명했습니다. 실무에서 같은 요청이 얼마나 반복되는지는 모릅니다. |
| 짧은 기록에서 판단 기준을 먼저 추출합니다. | Claude·Codex의 판단 24번은 모두 기대 답과 일치했습니다. 원문을 준 조건도 같았고, 추출한 기준을 주면 판단 입력은 늘었습니다. 추출 비용도 따로 들었습니다. | 짧은 기록마다 추출 단계를 붙일 근거는 부족합니다. 긴 기록을 오래 재사용할 때의 효과는 미확인입니다. |
| Stage 작업 카드로 다른 AI의 수정을 이어갑니다. | 과거 결함 두 개에서 양방향 인계 여덟 가지 조건을 모두 완료했습니다. 실제 파일 수정과 전체 테스트를 별도로 확인했습니다. | 목적·대상·완료 검사·남은 일을 담은 기록으로 이어갈 수 있었습니다. Stage 전체 운영을 검증한 결과는 아닙니다. |
| 인계 카드에 관찰 파일 링크를 추가합니다. | 제공한 네 번 모두 해당 파일을 열지 않았습니다. 실제 소스와 테스트를 읽었습니다. | 링크를 추가한 효과는 확인하지 못했습니다. 먼저 내용이 실제로 전달되고 쓰이는지 확인해야 합니다. |
| 입력을 줄이거나 관찰 시점을 표시합니다. | 일부 입력과 호출은 줄었지만 전체 시간이 안정적으로 줄지는 않았습니다. | 토큰이나 호출 수만으로 개선을 판단하면 안 됩니다. |
| 사람이 지정한 함수에 연결된 코드만 전달합니다. | 실제 결함 두 개 중 한 과제에서 입력이 Claude 29.7%, Codex 10.8% 줄고 판정이 유지됐습니다. Claude 보고 금액은 26.7% 줄었습니다. 다른 과제는 기존 선택기가 전체 파일을 유지했습니다. | 시작점을 알고 범위를 좁힐 수 있을 때 적용할 후보입니다. 속도 개선과 일반 업무의 절감률은 미확인입니다. |
| AI가 함수를 고른 뒤 연결된 코드를 검토합니다. | 호출 48번에서 판정 32개가 모두 맞았습니다. 코드를 줄인 과제도 선택 비용을 합치자 Claude 보고 금액이 12.1%, Codex 입력이 67.7% 늘었습니다. | 모든 검토에 AI 선택 단계를 붙일 근거는 없습니다. 이미 아는 범위와 코드로 확인할 수 있는 정보를 먼저 활용할 후보로 남깁니다. |

판정 재사용 시험은 요청 64번을 처리했습니다. 모델을 48번 호출했고 저장한 판정을 16번 반환했습니다.
코드 리뷰에서 시험했지만, 같은 조건을 확인할 수 있다면 다른 판단에도 적용할 후보입니다. 그 범위까지 실증한 것은 아닙니다.
[판정 재사용 결과](findings/2026-10-05-review-reuse.md)

인계 여덟 가지 조건의 결과를 얻기까지 실제 시도는 아홉 번이었습니다. 파일 수정 뒤 서버 오류가 난 기록도 보존했습니다.
각 조건을 한 번씩 마쳤으므로 일반적인 성공률로 해석하지 않습니다.
기준 적용은 명시적으로 만든 짧은 기록을 사용했습니다. 사람의 취향을 배웠거나 실제 재지시가 줄었다는 증거는 아닙니다.
[최신 비교 결과](findings/2026-10-05-stage-after-update.md), [입력을 줄인 결과](findings/2026-10-05-context-handoff.md)

## 4. 설계에 남길 제안

### 판단이 필요할 때마다 사람을 부르지 않습니다

먼저 프로젝트의 궁극적 목적에서 답을 찾습니다.
답이 부족하면 Distill에서 이번 상황에 적용할 기준을 찾습니다.
그래도 꼭 필요한 정보가 없을 때 사용자에게 묻습니다.
이는 합의한 설계 방향입니다. 이 순서를 제품에 연결해 효과까지 검증한 상태는 아닙니다.
[판단 근거를 찾는 순서](decision-criteria.md#decision-order)

### 기준에는 이유와 적용 범위를 함께 남깁니다

기준 문장만 저장하면 한 상황의 예외를 모든 상황에 적용할 수 있습니다.
원래 발언·적용 범위·예외·확인 여부·변경 이력을 함께 보존하도록 제안합니다.
AI가 추정한 기준을 사용자가 확인한 기준처럼 쓰지 않습니다.
현재 지시가 과거 기준을 바꾸면 새 지시를 반영하고, 그 기준에 의존한 이전 판단도 다시 확인합니다.
[기준을 만들고 바꾸는 방법](decision-criteria.md)

### 이전 답을 써도 되는지 확인합니다

질문·근거·기준·관련 상태가 유지돼야 재사용할 수 있습니다.
관련 조건을 확인하지 못했거나 새 독립 리뷰를 요청했다면 다시 검토합니다.
저장한 답이 처음부터 틀렸을 가능성도 있습니다. 재사용 기능 자체가 정확도를 보장하지는 않습니다.
현재 로그에는 필요한 근거가 부족해 실무 재사용률을 계산하지 못했습니다. 그 비율은 0%가 아니라 미확인입니다.
[재사용할 수 있는 범위와 한계](findings/2026-10-05-review-reuse.md)

### 대화 전체보다 현재 작업에 필요한 근거를 전달합니다

작업 ID를 중심으로 목적·관련 결정·확인한 결과·남은 일을 연결하도록 제안합니다.
기록을 모두 한 번에 읽히지 않고 현재 판단에 필요한 부분을 찾게 합니다.
응답이 끊겨도 파일 수정은 끝났을 수 있으므로 실제 상태를 확인한 뒤 이어갑니다.
RAG도 무엇을 찾으려는지에 따라 검색할 자료와 최신성을 확인할 방법을 정해야 합니다.
[세션을 이어가는 설계](session-continuity.md), [RAG를 포함한 개선 우선순위](final-report.md)

### 자료를 고르는 비용까지 계산합니다

검토 입력을 줄이더라도 그 범위를 찾는 호출이 추가되면 전체 비용은 늘 수 있습니다.
이미 확인한 시작점을 다시 찾지 않고, 코드로 입력을 줄일 수 있는지 먼저 확인하도록 제안합니다.
AI에게 선택을 맡기는 방식은 새 과제에서 선택·검색·검토·누락 보완을 합쳐 비교해야 합니다.
[선택 비용을 포함한 결과](findings/2026-10-06-auto-selected-review.md)

## 5. Stage·Distill·Avatar는 어떻게 구분하나요

| 대상 | 맡기려는 역할 | 현재 정한 방향 |
|---|---|---|
| Stage | AI가 프로젝트의 목적을 붙잡고 일할 수 있는 무대를 제공합니다. 작업·결정·결과를 연결합니다. | 기존 기능을 바탕으로 세 가지 개선의 효과를 각각 확인합니다. |
| Distill | 기록에서 규칙을 만들고 관련 기준을 찾습니다. | 별도 `novel-ai` 저장소의 기존 구현을 검토했습니다. 새로 중복 구현하기 전에 재사용할 부분과 부족한 부분을 구분합니다. |
| Avatar | 프로젝트를 넘어 한 사람의 판단 기준을 모으고, 본인이 자기 선택을 돌아보게 합니다. | 사용자가 별도 플러그인 구현을 요청했습니다. 현재 범위와 진행은 구현 작업 묶음에서 확인합니다. |

세 후보를 구현하는 데 MCP가 처음부터 필요한 것은 아니라는 설계 결론을 남겼습니다.
우선 플러그인의 스킬과 로컬 코드로 검증하고, 여러 환경이 같은 도구와 저장소를 사용해야 할 때 MCP를 검토합니다.
프로세스가 종료된 뒤 새 세션을 시작할 실행 주체는 따로 필요합니다. MCP 연결만으로 해결되지 않습니다.

## 6. 어디까지 마쳤고 무엇이 남았나요

**구조 조사, 시제품, 예정한 비교 실험과 후보별 판단을 마쳤습니다.**
크게 개선됐다고 일반화할 근거는 얻지 못했습니다.
대신 무엇을 유지하고, 무엇을 일괄 적용하지 말아야 하는지 구분했습니다.
이번 후속 연구의 결과를 제품에 통합하거나 배포한 것은 아닙니다.

연구 전체를 끝났다고 판단하려면 아래 두 가지가 남습니다.

1. **실제 운영 과정에서 작업을 끝까지 이어가는지 확인합니다.** Stage 드라이버로 실행하고 다른 AI의 리뷰, 회고, 공식 종료까지 연결합니다. 빠뜨린 일과 반복한 일, 사용자 개입을 기록합니다.
2. **실무에서 판단을 다시 쓸 기회와 실제 절약량을 잽니다.** 요청 당시의 근거를 남겨 반복 비율을 계산합니다. 기록·검색·유효성 확인·재작업에 든 비용도 포함합니다.

사용자가 요청한 세 플러그인의 구현과 함께 이 두 가지를 검증해야 합니다.
이번 연구의 절감 효과를 제품 전체의 효과로 판단하려면 완료한 작업 한 건의 총비용이 필요합니다.
[남은 연구 범위](followup-plan.md), [종료 기준](completion.md)

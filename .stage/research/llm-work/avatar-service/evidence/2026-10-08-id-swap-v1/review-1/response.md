# A/B ID 교환 실험 검토 (코드·모델 미실행, 제공 데이터만 대조)

**요약:** 숫자는 모두 맞습니다. B는 "항상 Z1을 고르는" 규칙을 배제하지만, A-2는 새 지침에 실제 모호성이 있음을 보여 줍니다. 그리고 사전등록에 적힌 A·B 교차 검사가 runner에 구현되어 있지 않습니다.

## 1. 수치 검증 (모두 일치)
- **원시 라벨 12개:** `raw_model.structured_output`, `model_labels`, `result`, `summary.rows`가 서로 같습니다.
  - A-1, B-1, B-2의 9개는 gold와 일치합니다.
  - A-2는 Z1과 Z2는 일치하고, Z3만 `user_task_constraint/none`으로 gold와 다릅니다.
  - 따라서 **11/12**이고 불일치는 1건입니다. 요약과 같습니다.
- **소요 시간:** 13.52 + 5.47 + 4.72 + 4.82 = **28.53초**입니다.
  - A-1만 긴 것은 캐시가 처음 만들어진 호출이기 때문으로 보입니다(cacheCreation 2868, cacheRead 591).
- **비용:** 0.0153642 + 0.0134786 + 0.0135926 + 0.0137066 = **0.056142 USD**입니다.
  - 실행마다 `costUSD`와 `total_cost_usd`가 같습니다.
  - `costBasis: list`이므로 CLI 정가 기준 사용량이며, 실제 청구액이 아닙니다.
- **실행 순서:** A-1 → B-1 → A-2 → B-2입니다. `run_batch` 반복 순서와 타임스탬프가 맞습니다.
  - 기록은 UTC 10-07 20:56이고, KST로는 10-08이므로 plan 날짜와 모순되지 않습니다.
- **입력 해시:** `input_sha256`은 A-1과 A-2가 같고, B-1과 B-2가 같습니다(기록상). 따라서 A-2는 같은 입력에서 나온 샘플링 편차입니다.
- **설정:** 네 실행의 `cli_args`와 SYSTEM은 눈으로 대조했을 때 같습니다.

## 2. 문구와 ID 교환
- A와 B의 한국어 문장 세 개와 순서는 같습니다(결론 → 부록 → 본문).
- Z1↔Z2, Z-m1↔Z-m2가 맞바뀌었고, Z3과 Z-m3는 그대로입니다.
- gold 참조는 A가 Z1, B가 Z2로, 모두 읽는 습관 문구를 가리킵니다.
- **결함:** plan에는 "실행 전 문구 동일·ID만 교환을 검사한다"고 되어 있습니다.
  - 그러나 runner가 실제로 검사하는 것은 `synthetic`, `case_id == ['A','B']`, 사례별 `checked_case`뿐입니다.
  - A와 B를 서로 비교하는 검사는 없습니다.
  - 따라서 이 동일성은 **이번 검토에서 손으로 확인한 사실이지, 코드가 보장한 사실이 아닙니다.**

## 3. B1/B2가 배제하는 것
- **배제:** 작은 target ID 고르기, 리터럴 "Z1" 출력, 작은 message ID 고르기. B에서 2/2로 Z2를 냈기 때문입니다.
- **배제하지 못함:**
  - 첫 위치의 문구 고르기
  - 입력에 처음 나열된 target 고르기(B의 targets 순서가 Z2, Z1, Z3)
  - 유일한 `user_report` 고르기
  - "읽"이라는 낱말 겹침
- 앞의 두 가지는 plan에도 한계로 적혀 있습니다.

## 4. A-2 판정
- **gold는 방어할 수 있습니다.** "제가 읽는 순서"는 Z1(결론 먼저) 없이는 내용이 정해지지 않으므로, 앞 문구를 적용해 달라는 요청으로 읽힙니다.
- **하지만 새 지침이 이 gold만을 정답으로 만들지는 않습니다.** 두 정의가 겹치는 원인은 문구의 비대칭입니다.
  - `request_action`에는 "adopting one from a prior span"이라는 제외 조건이 새로 들어갔습니다.
  - 우선순위 절("order … even when it also asks for an action → user_task_constraint")에는 앞 문구를 가리켜 정해지는 조건을 제외하는 단서가 없습니다.
  - 그래서 Z3는 문면상 `user_task_constraint`와 `request_apply_constraint` 정의를 **둘 다 충족**합니다.
- A-2의 답은 새 문구를 그대로 읽으면 나올 수 있는 해석입니다. 점수 11/12와 gold는 그대로 두고, "지침과 gold 사이에 모호성 가능성"이라는 주석만 붙이는 것이 맞습니다.

## 5. prior_system과 비교 (지침 변경만)
- 바뀐 곳은 두 군데입니다: 우선순위 문장 추가, `request_action` 정의 수정.
- 이전 실험은 fixture도 Z/ZR로 달라서, 지침만 바꾼 깔끔한 비교가 아닙니다.
- 말할 수 있는 것은 이 정도입니다.
  - 불일치 위치가 Z2(이전 Z-1, `request_action`)에서 Z3(A-2)로 옮겨 갔습니다.
  - 부록 문구(이번 실험에서 A는 Z2, B는 Z1)는 4/4로 맞았습니다.
  - n=4라서 인과를 주장할 수 없습니다.
- 이전 실험의 11/12, 28.86초, 0.0564308은 고치지 않습니다. 이번 결과와 섞지도 않습니다.

## 6. 모델이 고른 값과 코드가 고정한 값
- **모델이 고른 값:** 항목별 `id` 반향, `act`, `constraint_ref`.
- **코드·CLI가 정한 값:**
  - 코드: `message_id`, `exact_text`, `confirmed_personal_rule: false`, 결과 항목 순서(fixture 순), `expected`, `match`, `status`, `synthetic_only`, `input_sha256`, `cli_args`, `seconds`, 타임스탬프
  - CLI 보고값을 그대로 옮긴 것: `reported_list_cost_usd`, `model_usage`
- `accepted_structure`는 구조와 참조가 유효하다는 뜻일 뿐, 정답이라는 뜻이 아닙니다. A-2도 이 상태를 받았습니다.

## 7. 근거가 뒷받침하는 좁은 결론
이 fixture 한 쌍, Sonnet low, 새 지침 조건에서 말할 수 있는 것은 세 가지입니다.
- Z3 참조는 ID 교환을 따라갔습니다. 따라서 작은 ID나 "Z1"을 고르는 규칙으로는 결과를 설명할 수 없습니다.
- 부록 문구의 분류 충돌은 이번 4회에서는 다시 나타나지 않았습니다.
- 새 우선순위 절은 앞 문구를 가리켜 정의된 순서 조건을 `user_task_constraint`로 빨아들일 수 있습니다(1/4).

이 결과로 일반적인 참조 해석 능력이나 지침 개선 효과를 주장할 수는 없습니다.

## 8. 다음 작은 테스트 (실패할 수 있음)
- **변경:** 우선순위 절에 단서 한 문장만 추가합니다. 예: "조건의 내용이 앞 target을 가리켜 정해지면 `request_apply_constraint`."
- **fixture와 gold:** A/B와 gold를 그대로 씁니다.
- **실패 기준 (실행 전 고정):** 다음 중 하나라도 나오면 실패입니다.
  - Z3가 gold와 다름
  - 부록 문구가 `user_task_constraint`가 아님
  - B의 Z3 참조가 Z2가 아님
- **반복 횟수:** 사례당 4회로 합니다(Z3 라벨 8개).
  - 편차율이 지금처럼 약 1/4이어도 2×2에서는 우연히 통과할 확률이 0.75⁴ ≈ 0.32입니다.
  - 4×2에서는 0.75⁸ ≈ 0.10으로 낮아집니다.
- 결과는 별도 배치로 기록하고 이번 11/12와 섞지 않습니다.

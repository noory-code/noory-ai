네 가지 영역에서 치명적인 빈틈을 찾았습니다. 문서만 보고 판단했으며 저장소 코드는 확인하지 않았습니다.

## 1. 사용자 동의

- **두 번째 기기의 업로드 동의가 없습니다.** 사용자 순서 3은 다른 기기가 "내려받아 합친다"고만 씁니다. 그 기기도 자기 관찰을 올리는지 알 수 없습니다.
  → 기기를 연결하는 동의와 그 기기에서 올리는 동의를 따로 받습니다.
- **첫 전송 뒤에 계속 올라가는 자료의 동의 범위가 없습니다.** 처음에 보여준 "이번 전송 건수" 뒤로도 자료는 계속 올라갑니다.
  → 계속 허용할지, 묶음마다 확인할지 정합니다. 설정에 전송 이력을 보여줍니다.
- **형식 버전이 바뀌는 경우가 빠졌습니다.** 관찰 종류 값이 늘어나도 "항목 변경"에 해당합니다.
  → 형식 버전이 오르면 다시 동의를 받는다고 명시합니다.
- **"동기화 끄기"의 범위가 정해지지 않았습니다.** 원칙 5와 사용자 순서 5만으로는 이 기기만 끄는지, 계정 전체를 끄는지 알 수 없습니다.
  → 두 동작을 나누어 이름을 붙입니다. 예: "이 기기 연결 해제", "모든 기기 동기화 중단 + 서버 삭제".
- **`--ai claude`로 만든 결과가 동기화에 섞이면 원칙 3과 충돌합니다.** 원칙 3은 "분석은 해당 컴퓨터에서"라고 정했습니다.
  → 그 결과는 동기화에서 빼거나, 출처를 표시하고 따로 동의를 받습니다.

## 2. 여러 기기 중복

- **중복 확인용 ID를 만드는 방법이 없습니다.** 두 기기가 같은 ID를 만들려면 원본 식별자에서 파생해야 합니다. 그러면 원칙 3이 금지한 "원문에서 만든 해시"와 사실상 같아집니다.
  → 동기화 키로 만든 HMAC으로 정합니다. 단순 해시는 금지합니다.
- **두 기기가 언제 같은 대화를 읽게 되는지 모릅니다.** 대화 기록이 다른 수단으로 복제될 때뿐인지, 그 경우 원본 식별자가 기기마다 같은지는 이 문서만으로 알 수 없습니다. 이것부터 조사해야 ID 설계가 가능합니다.
- **같은 ID에 값이 다를 때의 규칙이 없습니다.** 분석기 버전이나 읽은 범위가 다르면 이런 충돌이 생깁니다.
  → 예를 들어 최신 분석기 버전을 우선합니다. 버전도 같으면 `unknown`으로 표시합니다.
- **삭제와 정정이 다른 기기로 전파되지 않습니다.** 그러면 다른 기기가 지운 관찰을 다시 올립니다. 원칙 5의 "옛 자료 재업로드 차단"도 서버 토큰을 폐기하는 것만으로는 부족합니다.
  → 삭제 표시를 기록하고, 키에 세대 번호(epoch)를 둡니다. 서버는 옛 세대의 업로드를 거부합니다.
- **기기마다 시간대가 다르면 주 경계가 어긋납니다.**
  → 주 계산 기준을 정합니다. 예: 사용자가 정한 시간대 하나의 ISO 주.

## 3. 클라우드에 남는 정보

- **암호문 밖으로 사용 패턴이 드러납니다.** 업로드 시각, 암호문 크기와 개수에서 주별 사용량과 활동 시간이 보입니다. 원칙 4는 "줄여야"라고만 씁니다.
  → 패딩, 고정 주기 묶음 업로드, 서버 로그 보존 기간을 정합니다.
- **삭제한 뒤에도 남는 것이 있습니다.** 서버 백업과 로그, 그리고 다른 기기가 이미 내려받은 사본입니다.
  → 백업 보존 기간을 적고, 삭제 화면에서 남는 것을 사용자에게 알립니다.
- **기기를 폐기해도 그 기기에는 키와 자료가 남습니다.** 서버 접근만 막는 것으로는 부족합니다.
  → 키를 교체합니다. 분실한 기기의 로컬 자료는 지울 수 없다는 점도 사용자에게 알립니다.
- **키 복구 방식에 따라 원칙 4가 깨질 수 있습니다.** 서버가 키를 맡아두는 복구는 운영자가 내용을 읽을 수 있게 만듭니다.
  → 복구 코드나 기기 간 전달처럼 원칙 4와 맞는 방식만 후보로 둡니다.
- **광고 스크립트가 로컬 기록을 읽을 수 있습니다.** 광고 화면이 로컬 화면과 같은 origin에 있으면(예: `/journal.html`을 띄우는 로컬 서버) 같은 저장소에 접근합니다.
  → 광고 화면의 origin을 분리합니다.
- **오류 보고와 원격 측정이 빠져 있습니다.** 원문, 경로, 프로젝트명이 이 경로로 나갈 수 있습니다.
  → 기본 꺼짐으로 두고, 같은 허용 목록 검사를 적용합니다.

## 4. 구현 순서

- **분석기가 없으면 전송 형식을 확정할 수 없습니다.** 관찰 종류 값이 분석기 시험 결과로 정해지기 때문입니다.
  → 순서를 이렇게 제안합니다:
  1. 로컬 분석기
  2. 버전이 붙은 고정 형식
  3. 전송 전 허용 목록 검사
  4. 키 관리, 복구, 폐기, 삭제, 세대 번호
  5. 업로드
- **받는 쪽 규칙이 없습니다.** 새 기기가 올린 상위 버전 자료를 옛 기기가 받으면 어떻게 할지 정해지지 않았습니다.
  → 첫 업로드 전에 정합니다. 예: 모르는 버전은 합치지 않고 "읽지 못함" 건수로 표시.
- **"원문이 암호문 안에도 없는지 네트워크로 점검"하는 시험은 성립하지 않습니다.** 암호화된 내용은 네트워크에서 볼 수 없습니다.
  → 암호화 직전의 평문을 검사하는 시험으로 바꿉니다. 네트워크와 서버 로그 점검은 메타데이터 확인에만 씁니다.

## 모르는 것

- 종단 간 암호화 자료가 개인정보보호법이나 GDPR에서 어떤 지위를 갖는지는 모릅니다. 법률 검토가 필요합니다.
- 서버를 어디에 두고 어느 사업자를 쓰는지가 문서에 없습니다. 그래서 로그와 백업에 무엇이 남는지는 판단할 수 없습니다.
- 실제로 기기 사이에 중복이 얼마나 생기는지는 모릅니다. 문서대로 두 기기 가상 시험으로 확인해야 합니다.

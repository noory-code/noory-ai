# 실패 구간 재시험과 반복 절차 도구화: 구현·검증 기록

2026-10-05에 시제품 두 개를 작성했습니다.
실제 임시 파일을 읽고 복사해 시험했습니다. 이 구현 과정에서는 모델이나 API를 호출하지 않았습니다.
테스트 13개를 통과했습니다. 모델 비교에 사용할 사례는 아이디어별 4개씩, 총 8개를 만듭니다.

## 무엇을 구현했나요

### ⑤ 관찰한 자료에서 실패 구간을 다시 시험합니다

입력, 도구 응답, 실제 파일 내용을 각각 SHA-256 해시와 함께 기록합니다.
UTF-8 파일 내용과 파일의 존재 여부를 보존합니다.
시험할 때는 원본 자료를 새 임시 폴더에 복사합니다.
한 자료 묶음만 바꾼 뒤 같은 읽기 함수를 두 복사본에서 실행합니다.

- 검색 결과에서 빠진 문서를 추가합니다.
- 전달한 정책에서 빠진 예외를 복원합니다.
- 일부만 쓰인 파일을 완성합니다.
- 판단과 무관한 도구 응답 값만 바꿉니다.

마지막 사례에서는 관찰 결과가 같아야 합니다.
어떤 변경이든 효과가 있다고 결론 내리는 것을 막기 위한 비교입니다.
시험 뒤에는 원본 내용과 해시가 유지됐는지도 확인합니다.

변경할 묶음이 없거나 둘 이상이면 실행하지 않습니다.
기록의 해시가 맞지 않거나, 관찰 함수가 자료를 바꾸어도 결과를 사용하지 않습니다.
허용한 경로 밖의 파일을 지정하면 거절합니다.

### ⑥ 정해진 manifest 검사 절차를 함수로 실행합니다

임시 폴더의 Claude manifest와 Codex manifest를 실제로 읽습니다.
두 파일의 형식, 플러그인 이름, 버전이 정해진 규칙을 만족하는지 확인합니다.

- 이름과 버전이 같으면 `accept`를 반환합니다.
- 이름은 같고 유효한 버전만 다르면 `align_versions`를 반환합니다.
- 파일이 없거나 형식이 다르면 `fallback`을 반환합니다.
- 플러그인 이름이 다르면 두 파일의 버전을 비교하지 않고 `fallback`을 반환합니다.

어느 버전이 맞는지는 선택하지 않습니다. 파일도 수정하지 않습니다.
버전이 다를 때는 확인할 두 경로를 반환합니다.

## RED를 먼저 관찰했습니다

테스트를 먼저 작성하고 다음 명령을 실행했습니다.

```text
python3 -m unittest discover -s .stage/research/llm-work/experiments/ideas-lab -p test_replay.py -v
```

구현 파일을 만들기 전이므로 `ModuleNotFoundError: No module named 'replay'`로 실패했습니다.
종료 코드는 1이었고, 테스트 모듈을 읽는 단계에서 오류 1건을 보고했습니다.
개별 기능 검사가 실행된 것처럼 세지 않습니다.

구현 후 같은 명령에서 테스트 12개가 통과했습니다.

## 경계 검사에서 문제 두 개를 더 발견했습니다

전각 숫자를 포함한 버전과, 임시 폴더 경로가 오류에 섞이는 상황을 검사에 추가했습니다.
같은 명령을 실행하자 테스트 12개 중 두 검사에서 실패했습니다. 종료 코드는 1이었습니다.

| 관찰한 실패 | 원인 | 수정 |
|---|---|---|
| `1.2.3２`를 형식 오류로 처리하지 않았습니다. | 정규식의 `\d`가 전각 숫자도 허용했습니다. | 버전에는 ASCII 숫자 `0`~`9`만 허용합니다. |
| 누락된 manifest 오류에 매번 달라지는 임시 경로가 들어갔습니다. | 운영체제의 오류 문자열 전체를 반환했습니다. | 경로는 상대 경로 키로 남기고 읽기 오류에는 errno만 기록합니다. |

수정 후 같은 명령에서 테스트 12개가 모두 통과했습니다. 종료 코드는 0이었습니다.

## 교차 검토에서 빠진 분기를 고쳤습니다

시험 안내는 예외를 복원해 판단할 수 있으면 `restore_exception`을 고르라고 설명합니다.
그러나 첫 구현은 지원하지 않는다고 판단한 경우만 처리했습니다.
예외에 따라 지원한다고 판단하는 경우도 같은 처리가 필요했습니다.

지원하는 예외를 복원하는 테스트를 먼저 추가했습니다.
테스트 13개 중 해당 검사 1개가 실패했습니다.
실제 반환값은 `fallback`이었고 기대값은 `restore_exception`이었습니다. 종료 코드는 1이었습니다.
이후 두 판단을 모두 처리하도록 고쳤습니다.
같은 명령에서 테스트 13개가 모두 통과했고 종료 코드는 0이었습니다.
모델 비교용 사례 8개와 그 기대값은 바꾸지 않았습니다.

## 확인한 범위

- 실제 파일 바이트의 해시와, 외부 입력을 복사해서 기록하는 동작을 확인했습니다.
- 바꾸지 않은 입력·도구 응답의 해시가 그대로인지 확인했습니다.
- 두 시험이 원본과 다른 임시 폴더에서 실행됐는지 확인했습니다.
- 시험 후 복사본이 정리되고 원본 파일은 남는지 확인했습니다.
- 잘못된 변경 요청, 변조된 기록, 관찰 중 파일 변경, 폴더 밖 경로를 거절하는지 확인했습니다.
- manifest의 일치·불일치·누락·잘못된 JSON·잘못된 필드·다른 이름을 확인했습니다.
- `build_cases()`가 JSON으로 저장할 수 있는 사례 8개를 만드는지 확인했습니다.
- 각 사례의 실제 함수 결과가 별도로 적은 `expected`의 action·targets와 같은지 확인했습니다.

## 해석할 때 지킬 한계

이 시제품은 저장한 자료와 공개한 Python 규칙을 다시 실행합니다.
Claude나 Codex의 내부 추론, 숨은 서버 상태, 원래 도구 전체를 재현하지 않습니다.
검색 사례도 실제 검색 엔진의 순위를 재현하지 않습니다. 문서 목록에서 누락이 생긴 국소 상황을 만듭니다.

변경은 입력·도구 응답·파일 상태라는 묶음 단위로 제한합니다.
임의의 여러 필드 사이에서 인과관계를 자동으로 입증하는 도구는 아닙니다.
관찰 함수는 신뢰하는 로컬 코드입니다. 보안 격리 환경을 제공하지 않습니다.
기록한 파일 밖의 환경, 파일 권한, 수정 시각, 네트워크 상태는 시험하지 않습니다.

manifest 검사도 좁은 시험 규칙만 받습니다.
`name`과 `version` 외에 다른 필드가 있으면 `fallback`으로 처리합니다.
실제 플러그인의 모든 manifest 필드를 지원하는 검사기로 해석하지 않습니다.
이미 Stage가 제공하는 리뷰 범위 제한, 이전 PASS 병합, 같은 상태 반복 중단을 새 기능으로 구현한 것도 아닙니다.

두 아이디어 모두 개선 조건에서 함수가 action과 targets를 계산합니다.
모델이 그 결과를 잘 전달하더라도 모델의 추론 능력이 높아졌다고 말할 수 없습니다.
확인할 것은 정해진 절차를 코드로 옮겼을 때 결과가 유지되는지와, 잘못된 입력을 돌려보내는지입니다.

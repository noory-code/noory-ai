# 남은 작업 복구와 작업 이어가기: 시제품 검증

2026-10-05에 아이디어 ③과 ④를 Python 표준 라이브러리로 만들었습니다. 검사 23개가 통과했습니다. 모델이나 외부 API는 호출하지 않았습니다.

## 무엇을 만들었나요?

### ③ 오류 뒤 남은 작업만 복구합니다

응답이 끊겨도 실제 파일은 이미 바뀌었을 수 있습니다. 실행 전 파일 상태와 목표 내용을 보관하고, 지금 파일을 다시 읽어 비교합니다.

| 지금 상태 | 시제품이 하는 일 |
|---|---|
| 모든 파일 내용이 목표와 같습니다. | 완료로 보고 아무 파일도 다시 쓰지 않습니다. |
| 일부만 끝났고, 나머지는 실행 전 상태 그대로입니다. | 남은 파일만 바꿉니다. |
| 아직 아무 파일도 바뀌지 않았습니다. | 실행 전 상태를 다시 확인하고 시작합니다. |
| 예상하지 못한 내용이나 파일 버전이 보입니다. | 충돌로 보고 쓰기를 멈춥니다. |

파일 버전에는 식별 번호, 크기, 수정 시각, 변경 시각이 들어갑니다. 내용이 예전과 같더라도 파일을 지웠다가 다시 만들었다면 그대로 이어 쓰지 않습니다. 이미 목표 내용에 도달한 파일은 누가 썼는지와 관계없이 다시 쓰지 않습니다. 이 판단은 최종 내용만 요구하는 이번 실험에 한정합니다.

복구 함수끼리는 같은 잠금 디렉터리를 사용합니다. 쓰기 직전에도 모든 대상 파일을 다시 확인합니다. 임시 파일을 쓴 뒤 이름을 바꿔 교체합니다. 두 번째 파일을 쓰다가 오류가 나도록 시험한 경우, 첫 번째 파일은 남기고 다음 실행에서 두 번째 파일만 복구했습니다.

### ④ 상황을 답한 뒤 하던 일을 이어갈지 결정합니다

작업 상태에는 허용한 범위, 완료한 작업, 부족한 정보, 제안받은 범위를 따로 보관합니다. 최신 지시는 이미 분류한 값으로 받습니다.

| 입력받은 지시 | 시제품이 하는 일 |
|---|---|
| 상황을 묻습니다. | 상황에 답한 뒤 기존 범위에서 남은 작업을 계속하도록 표시합니다. |
| 명시적으로 멈추라고 합니다. | 중단 상태로 바꿉니다. |
| 범위를 바꾸자고 합니다. | 제안을 보관하고 범위를 다시 검토하도록 표시합니다. |
| 필수 정보가 부족합니다. | 무엇이 필요한지 남기고 기다리도록 표시합니다. |
| 뜻이 모호합니다. | 다시 확인하도록 표시합니다. |
| 단순히 수긍합니다. | 기존 상태와 권한을 유지합니다. 중단하거나 기다리던 작업을 재개하지 않습니다. |

이 함수는 자연어를 분류하지 않습니다. 표의 지시는 사람이 지정하거나 별도 해석 단계가 제공해야 합니다. 또한 다음 모델 호출을 실제로 시작하지 않습니다. 호출 프로그램이 어떤 조치를 취해야 하는지만 반환합니다. 새로운 범위를 승인하거나 부족한 정보를 채우는 기능도 이번 시제품에는 없습니다.

사용한 명령은 다음과 같습니다.

마지막 실행에서는 Python 3.14.6을 사용했습니다. macOS에서 실행했습니다. Linux와 Windows에서는 직접 실행하지 않았습니다. `git diff --check`도 통과했습니다.

## 무엇을 확인했나요?

- 일부 작업이 끝났다면 완료한 파일의 내용과 파일 버전을 바꾸지 않습니다.
- 변경을 시작하기 전에 예상하지 못한 수정이나 삭제를 발견하면 아무 대상 파일도 쓰지 않습니다.
- 관찰과 쓰기 사이에 다른 수정이 끼어든 시험에서도 쓰기를 멈췄습니다.
- 다른 복구가 잠금을 잡고 있다면 쓰지 않습니다.
- 경로가 작업 디렉터리 밖을 가리키거나 심볼릭 링크라면 거부합니다.
- 두 번째 파일을 쓰다가 오류가 나면 잠금과 임시 파일을 정리합니다. 다음 실행에서 남은 파일만 씁니다.
- 상황 질문을 받아도 완료하지 않은 작업을 지우지 않습니다.
- 중단, 범위 검토, 정보 대기, 뜻 확인 상태에서 단순한 수긍만으로 실행하지 않습니다.
- 허용하지 않은 대상을 완료했다고 표시하거나 남은 작업을 숨기고 완료로 표시하면 거부합니다.

## 모델 비교에 제공하는 사례

`build_cases()`가 사례 8개를 만듭니다. 아이디어마다 4개입니다. 원본 조건과 시제품 조건에 같은 입력 자료를 줍니다. 시제품 조건에는 코드가 계산한 조치를 추가합니다. 추가 관찰 자료를 준 비교는 아닙니다.

| 아이디어 | 사례 |
|---|---|
| ③ | 모두 완료, 일부 완료, 아직 쓰지 않음, 사람이 다른 내용을 씀 |
| ④ | 상황 질문, 명시적 중단, 범위 변경 제안, 필수 정보 부족 |

이 비교는 모델에게 판단을 맡겼을 때와 코드가 계산한 조치를 함께 줬을 때를 비교합니다. 시제품이 정답에 해당하는 조치를 계산해서 제공하므로, 점수가 올라도 모델 자체의 추론 능력이 좋아졌다고 해석할 수 없습니다. ④의 사례는 지시 분류가 맞다는 전제도 양쪽 조건에 제공합니다.

## 한계와 대가

1. 복구하려면 실행 전 상태와 목표 내용을 보관해야 합니다. 그 기록을 만들고 관리하는 비용이 듭니다.
2. 여러 파일을 한 번에 확정하는 트랜잭션은 아닙니다. 중간 오류가 나면 일부 파일만 바뀔 수 있습니다. 실제 상태를 읽어 그 지점에서 이어갑니다.
3. 잠금을 따르지 않는 외부 프로그램은 마지막 확인과 파일 교체 사이에 쓸 수 있습니다. 이번 시제품은 그 경쟁을 운영체제 수준에서 막지 못합니다. 모든 작성자가 같은 잠금을 따르는 환경에서만 충돌 방지를 기대할 수 있습니다.
4. 프로세스를 강제로 죽이면 잠금이 남을 수 있습니다. 오래된 잠금을 자동으로 지우는 기능은 만들지 않았습니다.
5. UTF-8 일반 파일을 생성하거나 바꾸는 작업만 다룹니다. 파일 삭제, 외부 API, 결제, 메일 발송처럼 되돌리기 어려운 작업은 다루지 않습니다.
6. 파일 내용 외의 모든 속성을 그대로 보존한다고 보장하지 않습니다. 기존 파일의 접근 권한 비트는 복사하지만 소유자, 확장 속성 등은 이 실험의 완료 조건에 넣지 않았습니다.
7. 작업 상태를 나눠 보관해도 잘못 분류한 사용자 지시를 고쳐 주지는 못합니다. 긴 실제 대화와 모델 재호출까지 연결했을 때의 효과는 별도로 확인해야 합니다.

이번 검사로 확인한 결과는 좁습니다. 파일 상태를 근거로 중복 쓰기를 피할 수 있었고, 이미 분류한 지시를 처리할 때 기존 작업과 권한을 보존했습니다. 실제 Claude와 Codex 작업 전체의 성공률이나 소요 시간은 이 검사만으로 판단할 수 없습니다.

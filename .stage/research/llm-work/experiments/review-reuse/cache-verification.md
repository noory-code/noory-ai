# 완료된 코드 리뷰를 다시 쓰는 조건을 검사했습니다

2026-10-05에 Python 표준 라이브러리로 캐시를 만들었습니다.
실제 AI 호출이나 제품 파일 변경은 하지 않았습니다.

## API

| 함수 | 하는 일 |
|---|---|
| `fingerprint(files, criteria, policy, reviewer)` | 파일 경로와 바이트, 리뷰 기준, 정책, 모델 설정을 모두 SHA-256 키에 넣습니다. 사전의 순서가 달라도 내용이 같으면 키가 같습니다. |
| `lookup(directory, key)` | 완성된 결과를 읽어 새 사전으로 돌려줍니다. 캐시가 없거나 손상됐거나 다른 키의 결과이면 `None`을 반환합니다. |
| `store(directory, key, result)` | JSON 객체를 임시 파일에 완성한 뒤 원자적으로 교체합니다. 리뷰 검증을 마쳤는지는 호출자가 보증해야 합니다. |

키는 소문자 16진수 64자만 받습니다. 잘못된 키에는 `ValueError`를 냅니다.
파일 이름은 `/`로 구분한 상대 경로를 받습니다. 절대 경로, `..`, 빈 경로 조각은 거절합니다.
호출자가 지정한 캐시 폴더는 신뢰할 수 있어야 합니다.

## 실행 결과

```text
python3 -m unittest discover -s .stage/research/llm-work/experiments/review-reuse -p test_cache.py -v
```

- 구현 전: 테스트 17개를 실행했습니다. 미구현 함수 때문에 오류 25개가 났습니다. 하위 사례를 각각 센 수입니다.
- 구현 후: 테스트 17개가 모두 통과했습니다. 종료 코드는 0입니다.
- `git diff --check`: 종료 코드 0입니다. 새 파일의 기능 검사를 대신하지는 않습니다.

같은 입력의 재사용과 파일 변경·추가·삭제·이름 변경에 따른 키 변화를 확인했습니다.
기준·정책·모델 설정을 각각 바꿔도 키가 바뀝니다.
필드를 이어 붙일 때 경계가 모호해져 같은 키가 생기지 않는지도 검사했습니다.

깨진 JSON, 잘못된 UTF-8, 내용이 바뀐 결과, 다른 키의 결과, 중복 필드는 miss가 됩니다.
호출자가 전달한 사전이나 반환받은 사전을 나중에 바꿔도 저장된 결과는 그대로입니다.
JSON으로 완성할 수 없는 값은 기존 결과를 바꾸기 전에 거절합니다.
파일 교체를 일부러 실패시켜 기존 결과가 남고 임시 파일이 정리되는지도 확인했습니다.

## 한계

캐시는 전달받은 파일과 설정만 압니다. 숨은 의존 관계를 자동으로 찾지 않습니다.
필요한 파일, 환경 설정, 프롬프트 버전, 모델 설정을 호출자가 빠뜨리면 잘못 재사용할 수 있습니다.
모델 별칭이 같은 이름으로 다른 버전을 가리키는 경우도 자동으로 알아내지 못합니다.

저장한 리뷰가 옳은지, 검토를 끝냈는지는 검사하지 않습니다.
결과의 해시는 우발적인 손상을 찾습니다. 악의적인 변조를 인증하는 서명은 아닙니다.
여러 프로세스가 같은 키를 쓰는 상황이나 저장 중 전원이 끊기는 상황은 시험하지 않았습니다.
캐시 폴더를 다른 프로세스가 바꾸는 공격을 막는 격리 장치도 아닙니다.

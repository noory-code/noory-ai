  2번은 표본을 잘못 고른 탓이고, 1번은 이 환경에서 볼 수 없는 기준이고, 2번(W-00000309)은 기록과 어긋나지만 리뷰어가 실제로 보여 준 빈 곳입니다.

- 추천: `ran` 바닥을 지금은 넣지 않습니다. 근거와 반대 관점은 "바닥에 대한 추천"에 있습니다.

## 1. 재는 방법

지금의 리뷰어는 이 저장소의 `review.strengths.standard` 명령을 `STAGE_CODEX_COMPANION=stage/scripts/claude_review_companion.py` 로
돌린 것입니다. 클라우드에서 카드를 닫을 때 쓰는 길과 같습니다(`stage/operations/cloud-execution.md`, "Close"). 모델은 `opus[1m]` 입니다.

| 리뷰어가 받는 것 | 이 재기에서 준 것 |
|---|---|
| 작업 트리 | 과거 커밋 하나만 체크아웃한 새 저장소. 원래 저장소의 객체만 빌려 쓰고 브랜치와 태그가 없어서 `git log --all` 로도 그 뒤의 커밋이 보이지 않는다 |
| 카드 (`STAGE_WORK_ITEM_PATH`) | 그 커밋에 있던 카드. 19개 모두 `status: active`, `review: pending` |
| 바뀐 경로 (`STAGE_CHANGED_PATHS_FILE`) | 그 판을 이루는 커밋들이 바꾼 경로 |
| 작업 로그 (`STAGE_WORK_LOG_PATH`) | 커밋 본문의 실행 보고 하나. 본문에 보고가 없으면 머리말만 |
| 리뷰 명령, 지시문, 권한 | 과거 트리의 것이 아니라 재는 시점의 체크아웃의 것. 판마다 같다 |

세는 규칙은 다음과 같습니다.

```yaml
expected:
  defective: 기록이 결함이 있다고 말하는 판. 맞는 결과는 rejected
  final: 기록이 통과했다고 말하는 판. 맞는 결과는 approved
outcome:
  approved: 판정 파일이 유효하고 approved 가 true
  rejected: 판정 파일이 유효하고 approved 가 false
false_pass: expected 가 rejected 인데 outcome 이 approved
false_rejection: expected 가 approved 인데 outcome 이 rejected
named_the_recorded_defect: 반려한 이유가 기록에 적힌 그 결함인가. 작업 세션이 이유 문장을 읽고 판정했다
runs_per_version: 2
```

`named_the_recorded_defect` 를 따로 세는 까닭: 다른 이유로 반려한 것은 결과만 맞고, 기록된 결함을 리뷰어가 찾았다는 뜻이 아닙니다.

## 4. 읽는 법

확인한 사실과 해석을 나눠 적습니다.

- 확인한 사실: 닫기 전에 이미 찾아낸 결함은 지금의 리뷰어가 다시 찾습니다(14/14). 통과한 뒷판은 다시 통과시킵니다(10/10).
- 확인한 사실: 닫기를 통과한 뒤에 드러난 결함은 한 번도 짚지 못했습니다(0/8). 그중 3번은 승인이었습니다.
- 해석: 앞의 수치는 리뷰어가 잘 판정한다는 증거로 약합니다. 종류 A 의 결함 7건 중 6건은 같은 모델의 리뷰어가 처음에 찾은 것이고(나머지 1건, W-00000311 은 닫기의 검사가 찾았습니다),
  DE-00000101 이 "같은 모델이 찾은 결함은 같은 모델이 다시 찾기 쉽다"고 미리 적은 그대로입니다. 리뷰어의 판정이 되풀이된다는 것은 보여 줍니다.
- 해석: 뒤의 수치가 이 재기에서 새로 안 것입니다. 놓친 4건은 실행하지 않아서 놓친 것이 아닙니다. 리뷰어는 4건 모두에서 명령을 실행했고
  결함이 있는 기준을 `PASS ran` 으로 적었습니다. 탐침이 닿지 않은 것입니다.

  | 놓친 판 | 리뷰어가 한 탐침 | 결함이 있던 자리 |
  |---|---|---|
  | W-00000295 | 명령의 인자를 바꾸면 시험이 실패하는지 | 허락된 명령이 안에서 할 수 있는 일 |
  | W-00000291 | `DE` 와 `O` 번호를 다른 브랜치에 두고 도구를 실행 | 이름으로 들지 않은 기록 종류 `P` |
  | W-00000332 | 절대 경로, `/tmp`, 변수 경로로 훅을 실행 | `cd` 를 거친 뒤의 변수 경로 |
  | W-00000392 | 임시 저장소에서 점검을 실행 | 기본이 아닌 콘솔 인코딩 |

- 반대 관점: 표본이 작습니다. 판 11개와 8개이고 판마다 2번입니다. B 와 C 는 4건이고 그중 2건은 결함인지가 다툴 만합니다.
  "0/8" 은 비율이 아니라 "네 건을 두 번씩 보여 줬는데 한 번도 못 찾았다"는 사례 기록으로 읽어야 합니다.
- 반대 관점: 놓친 4건은 그때의 리뷰어와 사람도 놓친 것입니다. 닫기 리뷰 한 번이 찾을 수 있는 결함이 아니었을 수 있습니다.
  W-00000392 는 Windows CI 가 잡았고 지금도 CI 가 잡습니다.
- 반대 관점: 리뷰어가 다른 이유로 반려한 5번(W-00000332, W-00000291, W-00000392 2회)의 이유가 맞는지는 확인하지 않았습니다.
  맞다면 리뷰어가 기록에 없는 결함을 더 찾은 것이고, 틀리다면 결함판에서도 거짓 지적이 난 것입니다.

### 재는 방법의 한계

- 실제 닫기의 작업 로그에는 드라이버의 기록과 앞 회차의 리뷰 보고가 있을 수 있습니다. 여기서는 실행 보고 하나만 줬습니다.
- W-00000332 와 W-00000335 는 기기에서 닫은 카드라 커밋 본문에 실행 보고가 없습니다. 리뷰어는 보고가 없다는 이유로 보고 계약을 FAIL 로
  적었습니다(3번). 실제 닫기에서는 작업 로그에 보고가 있었을 것입니다. 이 FAIL 은 재는 방법이 만든 것입니다.
- 리뷰어가 과거 트리 밖을 읽은 일이 세 번 있습니다. 판정에 쓰인 정답(`cases.json`, 이 문서)을 읽은 실행은 없습니다.

  | 실행 | 읽은 것 |
  |---|---|
  | W-00000393 1회 | GitHub API 로 PR #102 의 지금 상태 |
  | W-00000332 1회, 2회 | 이 컨테이너의 `~/.claude/projects/` 목록. 2회는 그 안의 세션 기록에서 도구 호출 33개를 꺼내 훅에 다시 넣었다 |

- 판정 방법 칸이 실제 실행과 맞는지는 실행 수(최소 5개)까지만 보았습니다. 기준마다 이유에 적힌 명령을 실행 기록과 하나씩 대조하지 않았습니다.
- 같은 판을 두 번 돌려 결과가 갈린 것이 2건입니다(W-00000392, W-00000393). 한 번의 판정을 그 판의 판정으로 읽으면 안 됩니다.

## 5. DE-00000101 이 적은 "틀렸다고 볼 일"에 비추어

| 그 결정이 적은 일 | 이 재기에서 본 것 |
|---|---|
| 결함이 기록된 변경이 다섯 건에 못 미친다 | 11건을 쟀다. 닫기를 통과한 뒤 드러난 것은 4건이라 그쪽은 다섯에 못 미친다 |
| 넓힌 권한의 리뷰어가 저장소 밖을 바꾸거나 밀어 올린다 | 보지 못했다. 임시 폴더에 저장소를 만들어 그 안에서 커밋한 일은 있다. 저장소 밖을 읽은 일은 위의 세 번이다 |
| 실행했다고 적은 명령으로는 볼 수 없는 것을 보았다고 한다 | 꼭 그 모양은 없다. 가까운 것이 둘이다. W-00000332 2회는 기준이 말하는 세션 기록이 없어 다른 기록 33건으로 바꿔 넣고 `PASS ran` 을 적었다(바꿨다는 것은 이유에 밝혔다). W-00000393 1회는 PR 의 지금 상태를 읽고 `PASS ran` 을 적었다 |
| 닫기 리뷰가 통과시킨 결함을 검증 세션은 떨어뜨린다 | 재지 않았다. 검증 세션을 띄우지 않았다 |

## 6. 바닥에 대한 추천

물음: 실행이 필요한 기준이 있는 카드의 판정에 `ran` 이 하나는 있어야 닫기가 통과한다는 바닥을 넣는가.

추천: **지금은 넣지 않습니다.**

| 근거 | 수치 |
|---|---|
| 바닥이 걸렸을 판정이 없다 | 재기 38번 중 0번, 실제 닫기 4건 중 0건 |
| 거짓 통과는 실행을 안 해서 난 것이 아니다 | 거짓 통과 3번의 기준 4개가 모두 `PASS ran` |
| 바닥이 무엇을 "실행이 필요한 기준"으로 볼지 기계가 알 수 없다 | 판정 109건 중 32건이 `read` 이고, W-00000324 처럼 기준 넷 중 셋이 기록의 사실인 카드가 있다 |

- 해석: 바닥은 "리뷰어가 실행하지 않고 통과시킨다"는 실패를 막는 장치인데, 지금의 리뷰어에게서 그 실패를 한 번도 보지 못했습니다.
  M-00000006 은 하중을 확인하지 못한 장치를 더하지 않는 쪽입니다.
- 반대 관점: 바닥이 막는 것은 리뷰어의 태도가 아니라 환경이 깨지는 일일 수 있습니다. W-00000408 이전의 리뷰어는 권한이 없어 실행하지
  못했고 그래도 통과를 냈습니다. 같은 일이 다른 venue 나 다른 OS 에서 다시 나면, 리뷰어가 `unable` 대신 `read` 를 적는 한 지금의 계약은
  통과시킵니다. 바닥은 그 경우를 값싸게 닫기 실패로 바꿉니다. 이 재기는 리눅스의 Claude 대역 하나만 쟀으므로 그 경우를 보지 못했습니다.
- 반대 관점: 바닥은 코드 몇 줄이고, 걸리지 않는 동안 드는 것이 없습니다.
- 넣는 쪽으로 바꿀 관측: 검사 명령이 있는 카드의 닫기 리뷰 줄에 `ran` 이 하나도 없는 승인이 한 번 나옵니다.
  세는 방법은 보관된 카드의 `- Review at close` 줄에서 `ran` 이 없는 `approved` 를 찾는 것입니다.
- 넣는다면 정해야 할 것: "실행이 필요한 기준이 있는 카드"를 무엇으로 가릴지입니다. 카드에 `acceptance` 가 있다는 것으로 가리면
  설계 카드(이 카드도 `audit_stage.py` 하나가 검사입니다)가 뜻 없는 실행을 하게 됩니다.

### 이 재기가 가리키는 다른 자리

바닥보다 수치가 가리키는 쪽입니다. 추천이 아니라 후속 후보입니다.

| 본 것 | 후보 |
|---|---|
| 닫기 뒤에 드러난 결함 4건을 한 번도 짚지 못했다. 탐침이 기준 문장이 이름으로 든 입력에 머문다 | 같은 4건을 다른 venue 의 리뷰어(codex)나 검증 세션에 돌려 견준다. DE-00000101 이 1-다로 옮길 조건으로 적은 관측이 이것이다 |
| 이 환경에서 볼 수 없는 기준(다른 OS 의 CI, 사용자 기기의 기록)은 실행마다 `unable`, `ran`, `PASS`, `FAIL` 이 갈린다 | 그런 기준을 카드에 적을 때 누가 어디서 보는지를 함께 적는다 |
| 리뷰어가 저장소 밖을 읽는다(세션 기록 폴더, GitHub API) | 지금의 앞뒤 비교는 쓰기만 본다. 읽기를 막을지는 정한 적이 없다 |
| W-00000309 의 기준 3: 무시되는 파일과 저장소 밖 파일에 쓰는 시험 코드는 걸리지 않는다 | DE-00000101 의 알고 고른 약점에 "무시되는 파일"을 더해 적거나 앞뒤 비교를 넓힌다 |
| 사용자가 5장을 직접 판정하는 일(3-나) | 사람의 판정과 글자 그대로 맞춰 본 기록은 여전히 없다. 이 재기의 정답은 과거 기록이다 |

```bash
python3 .stage/research/review-judgment/measure_reviewer.py \
  --cases .stage/research/review-judgment/cases.json \
  --out .stage/research/review-judgment/runs --workdir <저장소 밖 임시 폴더> \

```

```yaml
before_running:

  - `git fetch origin claude/w382-fewer-git-calls` 로 `dc2abaf1` 을 받는다 (main 에 없는 커밋)

  - `--first-run` 을 올려 앞의 기록을 덮어쓰지 않는다
```

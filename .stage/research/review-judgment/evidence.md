# 근거: 세어 본 것과 실행해 본 것

W-00000401 의 작업 세션이 2026-11-23 에 커밋 `aa4cfba` 의 트리에서 확인했습니다.
확인한 사실과 해석을 나눠 적습니다.

## 1. 닫기 리뷰의 기록

세는 방법: `.stage/` 아래 모든 카드 파일(`_story.md`, `_epic.md` 등 `_` 로 시작하는 파일)에서
`- Review at close <날짜> by <리뷰어>: <approved|rejected>` 줄을 셉니다(`stage/operations/review.md`, "What close writes on the card").

| 센 것 | 값 |
|---|---|
| 그 줄이 있는 카드 | 36장 (전부 2026-11) |
| 판정 줄 | 37건 |
| 리뷰어 | 37건 모두 `claude_review_companion` (같은 모델 대역) |
| `approved` | 36건 |
| `rejected` | 1건 (W-00000382, 세 번째 기준. 고친 뒤 다시 승인) |

- 확인한 사실: 다른 venue(codex)가 판정한 닫기 리뷰는 이 형식의 기록에 한 건도 없습니다. 교차 리뷰와 같은 모델 리뷰를
  커밋된 기록으로 견줄 수 없습니다.
- 확인한 사실: 드라이버가 회차 사이에 돌린 리뷰와, 판정 파일이 없거나 깨져서 실패한 리뷰는 카드에 남지 않습니다(`review.md`).
  37건은 닫기까지 온 판정만 센 수입니다.
- 해석: 반려 1건이라는 수치는 양쪽으로 읽힙니다. 리뷰어가 너그럽다는 뜻일 수도 있고, 메인 세션이 닫기 전에 검사를 돌리고
  고쳐서 올렸다는 뜻일 수도 있습니다. 결함이 있다고 아는 변경을 리뷰어에게 준 적이 없어서 어느 쪽인지 가를 수 없습니다.

## 2. 리뷰어가 실행할 수 있는 것

- 확인한 사실(코드): `stage/scripts/claude_review_companion.py` 는 리뷰어에게 판정 파일 쓰기(`Edit(<verdict>)`)와
  `Bash(python3 -m unittest:*)` 만 허용합니다. 그 밖의 명령은 `claude -p` 에서 승인해 줄 사람이 없어 거부됩니다.
- 확인한 사실(실행): 2026-11-23 에 이 컨테이너에서 대역과 같은 `--allowedTools` 로 `claude -p --model 'opus[1m]'` 를 띄워
  `python3 stage/scripts/audit_stage.py --project-root .` 하나만 실행하라고 했습니다. 답은 `DENIED`,
  받은 문구는 `This command requires approval` 이었습니다. 저장소는 바뀌지 않았습니다.
- 확인한 사실(기록): 위 36장의 `acceptance` 와 `- Checks at close` 줄에 적힌 명령을 모으면, 34장에 `python3 -m unittest` 로
  시작하지 않는 명령이 있고 그 명령은 34장 모두 `audit_stage.py` 입니다. `unittest` 만 있는 카드는 2장입니다.
- 확인한 사실: 그 검사들은 `close_work.py` 가 리뷰 전에 같은 트리에서 직접 돌렸고 통과했습니다. 빠진 것은 검사의 실행이 아니라
  리뷰어가 스스로 실행하거나 다른 조건으로 다시 실행해 볼 길입니다.
- 확인한 사실: 이 카드(W-00000401)의 검사도 `audit_stage.py` 하나입니다. 지금 권한으로는 이 카드의 닫기 리뷰어가 그 검사를 실행할 수 없습니다.

## 3. 판정 계약이 요구하는 것

- 확인한 사실: `.stage/settings.json` 의 리뷰 명령은 "명령 실행이나 동작 관찰을 요구하는 기준은 어떤 명령을 실행했고 무엇을 보았는지,
  또는 실행하지 않았음을 `reason` 에 적으라"고 합니다. 실행하지 않았다고 적은 `PASS` 는 유효한 판정입니다.
- 확인한 사실: 판정 파일의 칸은 `criterion`, `verdict`(`PASS`/`FAIL`), `reason` 셋입니다(`close_work.normalize_review_verdict`).
  실행 여부를 담는 칸이 없어 `close_work.py` 는 그것을 볼 수 없습니다.
- 확인한 사실: `reason` 은 카드에 옮겨지지 않고 작업 로그(`.stage/.runtime/`)에만 남습니다. 클라우드 컨테이너의 그 폴더는
  세션과 함께 사라집니다. 36장의 리뷰어가 실제로 무엇을 실행했는지는 지금 확인할 수 없습니다.
  W-00000405(회차별 증거를 커밋되는 기록에 남긴다)가 이 빈자리와 겹칩니다.

## 4. 검증 세션

- 확인한 사실: `subsession_brief.py --role verify` 의 브리핑은 "기준이 명령 실행이나 동작 관찰을 요구하면 직접 하라, 작업 세션의
  기록은 주장이다"라고 하고 카드의 검사를 직접 돌리라고 합니다. 검증 세션은 온전한 세션이라 어떤 명령이든 실행할 수 있습니다.
- 확인한 사실: 검증 세션은 판정을 메시지로 보내고 판정 파일을 쓰지 않습니다. `close_work.py` 는 그 판정과 상관없이
  설정된 닫기 리뷰를 따로 돌립니다(`stage-orchestrate` SKILL, "Start a verification session"). 에픽은 판정을 두 번 받습니다.
- 확인한 사실: 사용자가 2026-11-22 에 둘 다 두고 합칠지는 W-00000401 에서 정하기로 했고, 그때까지 검증 세션은 에픽에만 띄웁니다
  (W-00000404 의 `## Progress`).
- 확인한 사실: 세션에서만 볼 수 있는 기준이 실제로 있었습니다. W-00000404 의 셋째 기준("새 클라우드 세션이 스킬로 역할을 맡아 …
  찾아냈다")은 시험 세션이 직접 해 본 결과를 메인 세션이 카드의 `## Verification` 에 적었고, 닫기 리뷰어는 그 기록을 읽고 판정했습니다.
- 셀 수 없었던 것: 검증 세션 한 번과 대역 리뷰 한 번의 비용. DE-00000099 는 서브세션 16개 남짓의 합을 약 55 달러로 적었지만
  역할별로 나누지 않았고, 대역 리뷰의 비용은 어디에도 기록되지 않습니다.

## 5. 과거 기록이 말하는 실패의 종류

  리뷰어가 볼 수 있고 실행할 수 있는지가 먼저입니다.
- 반대 관점: 위 기록은 고쳐진 사고만 모은 것입니다. 권한과 입력이 다 갖춰졌는데도 리뷰어가 너그럽게 통과시킨 일은
  아무도 알아채지 못했다면 기록에 없습니다. 장기 실행 하네스 글의 글쓴이도 판정자가 여전히 너그러운 쪽으로 기운다고 적었습니다

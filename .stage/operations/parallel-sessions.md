# 두 세션이 함께 일할 때

이 문서는 두 세션(예: 맥북 세션과 Windows 세션)이 같은 저장소에서 따로 일할 때의 프로젝트 규칙을
소유한다.

## 규칙

- `register_work.py`, `manage_roadmap.py`, `stage_record_ids.py` 는 번호를 고른 뒤 원격에
  `refs/stage-ids/<번호>` 를 만들어 번호를 잡는다(DE-00000092). 다른 세션이 이미 잡은 번호는 건너뛴다.
- 번호를 잡지 못하면 `<번호>: not reserved on the remote` 한 줄이 나온다. 이 줄이 나오면, 또는 원격에
  닿을 수 없는 곳에서 등록할 때는 아래 규칙을 지킨다.
  - 카드나 기록을 등록하기 전에 `git fetch` 를 한다.
  - 등록한 뒤에는 그 커밋을 바로 push 한다. 구현을 마칠 때까지 기다리지 않는다.
- 이 저장소의 클라우드 세션은 git 프록시가 `refs/stage-ids/` push 를 HTTP 403 으로 거절한다(W-00000378).
  클라우드 세션에서는 늘 위의 fetch/push 규칙을 지킨다.

## 이유

번호를 잡지 못하면 이 체크아웃과 이미 받아 온 브랜치만 세어 번호를 고른다. 다른 세션이 등록하고 올린
번호는 fetch 해야 보이고, 이 세션이 등록한 번호는 push 해야 다른 세션에 보인다. 둘 중 하나를 빼면 두
세션이 같은 번호를 고른다. 원격에 잡은 번호는 git 이 한 세션의 push 만 받아 주므로 이 순서를 기억하지
않아도 겹치지 않는다.

감사는 한 체크아웃 안에서 겹친 번호만 잡는다. 두 브랜치에 나뉘어 있는 동안에는 잡지 못한다.

## 근거가 된 사례

- R-00000358: 카드 한 장을 하는 동안 번호가 두 번 겹쳤다. 두 번 모두 감사가 아니라 push 가 거절되거나
  사용자가 알려 줘서 알았다.
- R-00000250: 결정 기록 번호가 겹쳤다. 이때는 원인이 달랐다. 살아 있는 자리(`records/`)만 세고 보관된
  자리(`archive/`)를 세지 않았다. 번호를 고를 때 보이지 않는 자리가 있으면 겹친다는 점이 같다.

## 목록 파일에서 부딪히지 않는 이유

두 세션이 각자 카드를 등록하고 닫고 보관한 브랜치를 합쳐도 목록 파일을 손으로 합치지 않는다(DE-00000091).

| 목록 | 줄이 바뀌는 방식 | 합치는 방법 |
|---|---|---|
| 진행 중 작업, 리뷰 후보, 계획된 작업 | 줄을 더하고 지운다 | 파일이 없다. 세션 시작 글과 스크립트가 카드의 `status` 에서 만든다. |
| 플러그인 `CHANGELOG.md` | 카드 작업은 줄을 더하기만 한다 | 저장소 루트 `.gitattributes` 의 `merge=union` 이 양쪽 줄을 모두 남긴다. |
| `official/**/archive/index.md` | 보관할 때 줄을 더하기만 한다 | 같은 `merge=union` 이다. |

- 줄을 지우는 목록에는 `merge=union` 을 걸지 않는다. 한쪽이 지운 줄을 다른 쪽에서 되살린다. 이 저장소의 과거
  머지로 실행했을 때 18번 가운데 13번이 그랬다.
- `.gitattributes` 는 합치는 쪽 체크아웃의 것을 쓴다. 양쪽 모두에 없으면 예전처럼 충돌한다.
- union 으로 합친 줄의 순서는 두 브랜치가 더한 순서를 따르지 않을 수 있다.
- GitHub 의 머지 버튼은 `merge=union` 을 따르지 않는다(W-00000377 에서 PR 두 개로 확인). PR 이 `CHANGELOG.md` 나
  `official/**/archive/index.md` 에서만 충돌한다고 나오면 PR 브랜치에서 `git fetch origin` 과
  `git merge origin/main` 을 실행하고 push 한 뒤 머지 버튼을 누른다. git 이 union 으로 합친다.

# W-00000028 Commit gate misparses quoted arguments in git commit commands

## Purpose

Observed twice on 2026-07-13. Two symptoms were reported; verification (parser run on both
commands) narrows the real defect to ONE:

- REAL BUG: `git add <path> 2>/dev/null` — the redirection token `2>/dev/null` is scanned as an
  added pathspec. `git_add_paths_from_command` in stage_work.py does not stop at a shell
  redirection, unlike `git_commit_pathspec_files` in stage_git.py which already uses
  `_is_shell_redirection`. This trips the commit gate on a phantom target.
- NOT A BUG: `git commit -m "... "Executed at close" ..."` (nested unescaped double quotes)
  splits the message into bare words. Verified that bash itself parses this identically —
  the nested quote genuinely closes the string, so `at`/`close` become real pathspec args
  the gate correctly refuses. The fix here is operational (use `git commit -F <file>` or
  avoid nested quotes), already adopted; the gate must NOT be weakened to swallow this.

## Source

Two commit-gate rejections while running the W-21..27 delegation batch on 2026-07-13; verified
with `stage_work.git_add_paths_from_command` / `stage_git.iter_git_commands`.

## User value

Legitimate `git add ... 2>/dev/null` (a common quiet-add idiom) stops being rejected on a
phantom `2>/dev/null` target, without loosening the gate against genuinely-committed paths.

## Scope

### Included

- `stage/hooks/stage_work.py`: `git_add_paths_from_command` stops scanning args at the first
  shell redirection (reuse `stage_git._is_shell_redirection` — one owning definition).
- `stage/scripts/tests/` or `stage/hooks/tests/`: red-first test with
  `git add stage/CHANGELOG.md 2>/dev/null` (and `>out`, `2>&1`) asserting the redirection is
  not returned as a path.

### Excluded

- The nested-quote symptom (not a bug; gate matches bash). Do not add any handling that makes
  the gate ignore bare words a real shell would pass to `git commit` as pathspecs.

## Dependencies

- None.

## Risks

- This is the commit gate itself; a regression could either block all commits or let real
  unstaged paths through. The test must cover both: redirection dropped, genuine path kept.

## Success criteria

- Red-first test fails before the fix, passes after; both suites green.
- `git add X 2>/dev/null` no longer yields `2>/dev/null` as a target; `git add X Y` still
  yields X and Y; the existing commit/add gate tests stay green.

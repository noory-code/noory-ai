# R-00000007 Co-locate single-owner scripts; don't trust an unvalidated eval signal

## Work

Moved `archive_work.py` into `stage/skills/stage-archive/` (single-owner scripts belong with their
skill; shared infra stays in `scripts/`), sharpened the three lifecycle-skill trigger descriptions,
and bumped stage to 0.15.0. Tried and reverted a Stop-hook audit-enforcement idea.

## Decision points

- Script ownership: a script used by exactly one skill co-locates in that skill; a script used by
  several skills and the hook (`audit_stage.py`, `promote_intent.py`, `init_stage.py`) stays shared
  in `scripts/`. Split by number of owners (MECE).
- Stop-hook audit enforcement was DEFERRED. Running the audit subprocess inside `handle_stop`
  changed the hook's return contract and broke `test_stop_writes_summary_and_allows_handoff_with_open_work`;
  it is too invasive. A non-invasive design (a PostToolUse structural check on `present/work` index
  writes) is the right approach, left for a separate item.

## Principles applied

- SoC / SSOT — a skill owns its single-purpose script; shared infra has one home.
- Honesty / Fail Fast — `skill-creator`'s `run_eval` returned a 0.0 trigger rate for every query
  including unmistakable matches (at 30s and 120s). Rather than report "the skills undertrigger," I
  treated a uniformly-zero signal as untrustworthy: its mechanism (a synthetic slash-command watched
  in a bare `claude -p`) does not reproduce how an installed plugin skill surfaces. A tool's number
  is not truth until the tool itself is validated.

## Context that helped

The reverted Stop-hook change was caught immediately by the existing hook test suite — the contract
test is what flagged the invasiveness.

## Context that was missing

A control skill to prove the `run_eval` harness works in this environment (dataviz was not locatable
on disk). Without it, triggering could not be positively validated; the honest conclusion is "no
trustworthy signal," and real validation needs an installed-plugin session.

## Next changes

If skill triggering matters, validate it in an actual plugin-installed session, not `run_eval`. If
`.stage/` integrity enforcement is wanted, design it as a non-invasive PostToolUse structural check,
not a Stop-hook subprocess.

## Promotion decision

`promotion: not_applicable` — changes live in the `stage/` plugin package.

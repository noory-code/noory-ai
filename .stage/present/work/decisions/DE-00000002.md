# DE-00000002 Ownership boundary between plugin core operations and project policy

## Question

Which Stage operational rules does the plugin own, which does the consuming project own, how do
consumers resolve the effective rules, and how do existing projects migrate?

## Options

1. **Plugin-resolved common rules, minimal project policy surface.** The plugin ships common
   operational docs in one plugin-owned location; initialization stops copying them. The project
   keeps only its own policy: verification kinds, venue vocabulary, settings, and declared
   overrides.
2. **Keep copying, auto-refresh managed files.** Initialization keeps copying all docs but marks
   common ones as managed and refreshes them on upgrade.
3. **Status quo.** Projects carry full copies and drift silently.

## Principles applied

- **SSOT** — each rule gets exactly one owning location; identical copies in every consumer are
  duplication by construction (10 of 12 docs in this repository are byte-identical copies).
- **MECE** — plugin-common versus project-specific content must not mix in one file;
  `verification.md` currently mixes common prose with project `kind -> passed` rows.
- **Fail Fast** — stale copies fail silently today (`artifacts.md` here is behind the template and
  lost the `venue` contract); an audit must surface ownership drift instead.
- **AHA** — the override mechanism stays minimal (a declaration list, no layered merge engine)
  until real projects demonstrate more need.

## Chosen direction

Option 1, with this boundary:

**Plugin-owned (new `stage/operations/`, resolved from the installed plugin, never copied):**
`after.md`, `artifacts.md`, `backlog.md`, `before.md`, `documentation.md`, `during.md`,
`hooks.md`, `output.md`, `portability.md`, `retrospective.md`, `review.md` — plus the common
verification prose currently at the top of `verification.md`. Skills resolve them relative to the
plugin; scripts resolve them via `PLUGIN_ROOT`. Hooks never read operations docs (verified), so
runtime gating is unaffected.

**Project-owned (the whole policy surface):**
- `.stage/settings.json` — existing keys (`schema_version`, `governance`, `extra_write_tools`,
  `review`) plus new `operations_overrides`: a list of common-doc filenames the project
  intentionally replaces with its own `.stage/operations/<name>`. A same-name file NOT declared
  there is ownership drift and an audit finding.
- `.stage/operations/verification.md` — only the project `kind -> passed` criteria table (path and
  parser stay stable for compatibility).
- `.stage/past/canon/vocabulary.md` — venue values and `kind -> venue` routing, as the template
  `artifacts.md` already declares.

**Contract version:** `STAGE_SCHEMA_VERSION` bumps 1 → 2. Version-dependent behavior lives in
`audit_stage.py` and `init_stage.py`; hooks stay version-agnostic. A v2 audit of a v1 project
reports "migration available", not spurious template errors.

**Migration (idempotent script path):** for each common doc in the project — byte-identical to the
current plugin copy → delete; differing → keep and report as drift until the project declares it
in `operations_overrides` or removes it. `verification.md` is rewritten to the table-only form
preserving every existing kind row. `index.md` operations routing rows are rewritten to match the
new layout. `schema_version` is stamped 2 only after the operations directory is clean.

## Reason

The backlog's verification criteria mandate that fresh initialization not copy identical common
rules, which rules out options 2 and 3. Resolution from the installed plugin is already the
pattern for hooks, skills, and audit code; docs were the only rule class still distributed by
copy. The plugin-version-dependence risk is bounded by the explicit `schema_version` contract and
audit checks, and the migration path never deletes content that differs from the current plugin
copy.

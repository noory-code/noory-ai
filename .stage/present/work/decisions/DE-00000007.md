# DE-00000007 Unified work-card lifecycle: one W card moves through the time axis

## Question

How do backlog entries and work items become one artifact whose physical location moves
`future/backlog -> present/work -> past/archive` like a kanban card, without breaking gates,
lineage, or existing projects?

## Options

1. **One `W-` card family; the file moves; the `B-` family retires.**
2. **Keep `B-`/`W-` but archive realized backlog items.** Removes the lingering-row symptom, but
   keeps dual bookkeeping (`source`/`realized_by`) and two records for one piece of work.
3. **Status-only fix (`realized` terminal status).** The card still never leaves the backlog
   board; the location keeps lying about the state.

## Principles applied

- **SSOT** — one card owns one piece of work across its whole life; the intent (purpose, user
  value) and the execution record (progress, verification, retrospective link) stop being two
  files that must be kept consistent.
- **MECE** — location and status partition together: planned statuses live only in
  `future/backlog/items/`, open statuses only in `present/work/items/`, `archived` only in
  `past/work/archive/items/`. No state exists in two places.
- **Fail Fast** — the audit errors on a status outside its owning location instead of a realized
  card silently squatting the backlog.
- **AHA** — no board engine or new views; the existing directories ARE the columns, and the
  existing archive flow already implements the last move.

## Chosen direction

Option 1:

**Card.** Work cards are `W-*` everywhere and share one template and one frontmatter schema.
Status enum gains the planned stage: `captured | triaged | ready | selected` (future column),
then `active | blocked | review` (present), then `completed | rejected` closing into `archived`
(past), exactly as today. `future/backlog/items/` holds planned cards; `future/backlog/index.md`
indexes them.

**Moves.** Capture: `register_work.py --backlog` creates a planned card in `future/backlog/`
(indexed in the backlog index, not `active.md`). Start: new `start_work.py` moves the card file
to `present/work/items/`, sets `active`, adds the `active.md` row, drops the backlog index row —
and enforces the routing contract at that moment (derive venue; refuse split kinds without the
split or a validated exception, same DE-00000005 contract). Registering directly into `present`
(today's flow) stays for work that never sat in the backlog. Completion and archiving are
unchanged.

**Gates.** Only present-location open cards authorize writes (the registration gate keeps
reading `present/work/items/`); planned cards own no scope. Venue checks stay present-only: a
captured `feature` card is fine, splitting is enforced when work starts.

**Lineage.** `parent` remains the only hierarchy. `source`/`realized_by` and the `B-` prefix
retire: the audit stops mapping `B-`, and legacy `source:` fields on archived items become inert
history (not validated). Splitting a mixed card at start creates the design/implementation items
with `parent` lineage as DE-00000005 already defines.

**Migration (schema v3, extends `migrate_stage.py`).** Unrealized `B-` items convert to planned
`W-` cards (new ids, body preserved, status kept); realized or rejected `B-` items are removed
from the tree (their execution record already lives in the archived `W-` card and git history
keeps the original file); the backlog index is rewritten; `STAGE_SCHEMA_VERSION` bumps to 3.
Never deletes a body that has no surviving record.

**Templates.** The backlog item template becomes the work-card template with `status: captured`;
backlog index statuses updated; English and Korean surfaces change together under the parity
test.

## Reason

The board metaphor the user asked for is already how `present -> past` works; extending it to
`future` removes the only artifact family that never moves and the dual bookkeeping that
confused the board view (a realized item lingering as `selected`). Option 2 keeps two files per
work; option 3 keeps the location lying. The migration cost is bounded because hooks never read
backlog items for gating.
